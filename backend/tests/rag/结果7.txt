结果7 深度分析

召回率/命中率/MRR 全面恢复
  合并后 chunk 粒度从中位数 11 字提升到 ~100+ 字，top_k=5 能覆盖更多相关内容。
  召回率 86.1% 已超过 fixed 模式 85.6%，说明 speaker 模式在合理粒度下检索能力不弱于 fixed。
  MRR 0.5061 vs fixed 的 0.5836，差距缩小到 0.08，相关文档排名接近。

平均相似度下降的原因分析

  结果6（0.8451）→ 结果7（0.6028），下降幅度大，看似矛盾，实则合理：

  结果6 的高相似度是"幸存者偏差"：
  - 碎片 chunk（11字）与 query 匹配时，命中的那几个 chunk 语义极度纯粹，相似度极高
  - 但大量相关 chunk 根本没进入 top_k，召回率只有 59.6%
  - top_k=5 里的 5 个结果都是"精准命中"的碎片，平均相似度自然虚高

  结果7 的低相似度是"覆盖面扩大"的代价：
  - 合并后每个 chunk 包含多条发言，语义更丰富但也更"杂"
  - query 与 chunk 的相似度不再是"一句话对一句话"的精准匹配
  - 更多相关文档被召回，但这些 chunk 的相似度分布更分散，拉低了平均值

  结论：相似度下降不是质量退步，而是召回覆盖面扩大的正常代价。
  召回率/命中率/MRR 才是检索质量的核心指标，这三项全面恢复。

与 fixed 模式的差距分析

  命中率 67.3% vs fixed 72.6%，差距 5.3pp；MRR 0.5061 vs 0.5836，差距 0.077。
  可能原因：
  1. SPEAKER_MIN_CHUNK_SIZE=100 合并粒度仍偏小，部分文档 chunk 数量仍多于 fixed 模式
  2. 纯 Markdown 文档（doc 3/8/12/13/14/19）fallback 到 fixed 切分，与 speaker 文档混合
     导致 chunk 粒度不一致，影响整体检索均匀性

 优化方向（按优先级排序）

 方向1：调大 SPEAKER_MIN_CHUNK_SIZE（推荐先试）

 问题根因：100字阈值下，speaker 文档仍产生较多小 chunk，top_k=5 坑位不够用。
 fixed 模式 512字/chunk，speaker 合并后平均约 100-150字/chunk，粒度仍细 3-5 倍。

 改动：config.py
 SPEAKER_MIN_CHUNK_SIZE: int = 200  # 从 100 调到 200

 预期效果：
 - chunk 总数从 ~200 降到 ~100，与 fixed 模式粒度接近
 - 命中率预计恢复到 70%+，MRR 接近 0.55+
 - 平均相似度可能进一步下降（chunk 更"杂"），但这是正常代价

 风险：过大会导致 chunk 语义过于混杂，相似度继续下降。建议梯度测试：150 → 200 → 300。

 ---
 方向2：调大 EVAL_TOP_K（快速验证上限）

 问题根因：当前 top_k=5，而相关内容可能分散在同一文档的多个 chunk 中。
 评估指标按 document_id 计算，只要 top_k 内有任意一个该文档的 chunk 即算命中。

 改动：config.py
 EVAL_TOP_K: int = 10  # 从 5 调到 10

 预期效果：
 - 命中率和召回率直接提升（更多坑位）
 - MRR 变化不大（第一个命中的排名不变）
 - 可以快速验证"检索能力上限"——如果 top_k=10 命中率仍低，说明是 chunk 质量问题而非数量问题

 注意：这是评估参数，不影响线上 TOP_K_DEFAULT=5。

 ---
 方向3：修复纯 Markdown 文档的 fallback 策略

 问题根因：doc 3/8/12/13/14/19 是纯 Markdown 格式（# 标题、- 列表），
 parse_speech_text 解析出 0 条发言，fallback 到 split_chunks(content)。
 但这些文档本身不超过 512 字，split_chunks 只产生 1 个 chunk，向量质量差。

 改动：document_service.py 的 _create_vector_chunks，fallback 时改用更小的 chunk_size：
 else:
     # fallback：对短文档用更小粒度切分，避免整篇文档变成 1 个大 chunk
     fallback_chunk_size = min(settings.CHUNK_SIZE, len(content) // 3 + 1)
     chunks = self.text_process_service.split_chunks(
         content,
         chunk_size=max(100, fallback_chunk_size)
     )

 或者更简单：直接把 fallback 的 chunk_size 改为 200：
 chunks = self.text_process_service.split_chunks(content, chunk_size=200)

 预期效果：纯 Markdown 文档从 1 个 chunk 变成 2-4 个 chunk，检索覆盖更细。
