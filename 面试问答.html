这是一个面向会议场景的智能助手系统，核心功能包括会议问答、纪要生成、待办抽取和争议点分析。技术上采用 LangGraph 构建 Plan-Execute-Reflect 工作流，结合 RAG 实现检索增强。整个系统从文档解析、知识检索到 Agent 推理形成完整链路。

Q3：你在项目中主要负责哪些工作？

推荐回答：

  1. 设计 Speaker Chunking 策略优化会议文档切片

  3. 基于 LangGraph 搭建 Agent 工作流

Q4：你是如何将检索 Recall 从 59.6%提升到 86.1%的？

推荐回答：

主要通过三个方面的优化：

  1. Chunking 策略优化：设计了 Speaker Chunking 策略，针对会议场景中短发言多的特点，实现短发言自动合并，避免碎片化导致的检索效果下降
  2. 多路召回：采用 BM25 + 向量检索的组合方式，覆盖不同类型的检索需求
  3. 重排序：引入 BGE-Reranker 对召回结果进行精排，提升最终结果的相关性

推荐回答：

我认为有几个亮点：

  2. 完整评估体系：自建了 200+ 条评估数据集，集成 RAGAS 指标体系，通过 Recall、MRR 等指标持续优化
  3. 拒答机制：实现了对无答案问题的准确识别和友好回复，避免产生幻觉
  4. 工程化能力：采用异步架构、统一异常处理、配置化管理，具备生产环境部署能力

Q6：项目中遇到过什么困难？如何解决的？

推荐回答：

在开发过程中遇到的主要挑战是检索效果不佳的问题。一开始单纯使用向量检索，Recall 只有 59.6%。后来分析了 bad case，发现主要原因是会议文档碎片化严重，短发言太多。

解决方案：

  1. 设计了 Speaker Chunking 策略，按说话人合并短发言
  2. 引入 BM25 作为补充检索方式
  3. 添加 BGE-Reranker 进行重排序

通过这些优化，Recall 提升到了 86.1%。

三、技术栈类问题

Q7：你熟悉哪些 Agent 框架？它们有什么区别？

推荐回答：

我主要熟悉 LangGraph 和 LangChain：

  • LangGraph：更专注于构建多步骤、有状态的 Agent 工作流，支持 Plan-Execute-Reflect 等模式，状态管理更清晰，适合复杂任务
  • LangChain：功能更全面，包含大量工具和集成，适合快速原型开发

在我的项目中选择了 LangGraph，因为它更适合构建需要长期记忆和多步骤推理的 Agent 系统。

Q8：什么是 RAG？它的核心流程是什么？

推荐回答：

RAG（Retrieval-Augmented Generation）是检索增强生成，核心流程包括：

  1. 文档处理：将文档切分为 chunks，向量化后存储到向量数据库
  2. 检索：根据用户查询，从向量数据库中检索相关文档
  3. 生成：将检索到的文档作为上下文，输入到大语言模型中生成回答

这样可以让模型回答更准确、更具时效性，减少幻觉。

Q9：什么是 Chunking？你用过哪些策略？

推荐回答：

Chunking 是将文档切分为更小片段的过程。我用过以下策略：

  • 固定长度切分：按固定 token 数切分，简单但可能切断语义
  • 段落切分：按段落边界切分，保持语义完整性
  • Speaker Chunking：针对会议场景，按说话人合并短发言

在项目中我设计了 Speaker Chunking 策略，特别适合会议记录这类多说话人场景。

Q10：BM25 和向量检索有什么区别？为什么要结合使用？

推荐回答：

  • BM25：基于词频的传统检索，擅长关键词匹配，对字面相似度敏感
  • 向量检索：基于语义相似度，擅长理解语义，对同义词和语义变化更鲁棒

结合使用可以互补：BM25 保证关键词匹配的召回率，向量检索保证语义理解的准确性，再通过 Reranker 精排，整体效果更好。

Q11：什么是 Function Calling/Tool Calling？

推荐回答：

是让大语言模型根据用户需求，自动选择并调用外部工具（如数据库查询、API 调用等）的能力。在 Agent 系统中非常重要，可以扩展模型的能力边界。

在我的项目中，我实现了会议问答、纪要生成、待办抽取等工具，并让 Agent 根据用户问题自动选择调用。

Q12：为什么选择 FastAPI？它的优势是什么？

推荐回答：

选择 FastAPI 主要因为：

  1. 高性能：基于 Starlette，支持异步，性能接近 Node.js
  2. 类型提示：支持 Python 类型提示，自动生成文档和参数校验
  3. 快速开发：代码简洁，开发效率高
  4. 生态完善：支持依赖注入、中间件等，适合构建生产级服务

Q13：你了解 ReAct 和 Plan-and-Execute 吗？

推荐回答：

  • ReAct：让模型在思考过程中产生"动作"，通过"思考-动作-观察"循环解决问题
  • Plan-and-Execute：先规划执行步骤，再按计划执行，适合复杂任务拆解

在我的项目中，基于 LangGraph 实现了 Plan-Execute-Reflect 的变体，支持任务拆解、工具调用和结果反思。
