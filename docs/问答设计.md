你提到的“四级复杂度路由”具体是哪四个级别？判断逻辑是写在代码里的硬编码规则（如关键词匹配），还是依赖一个小模型（如BERT分类器）做动态路由？

四级复杂度路由具体分为：

第一级是简单问答（S级），分数区间0.0到0.3。这类问题是单事实的，无需检索，也不需要推理，比如问候语、简单的定义类问题，直接回答即可。

第二级是检索类（R级），分数区间0.3到0.5。这类问题是事实型的，但需要查询资料，比如询问某个具体数据或时间，需要先检索再回答。

第三级是思维链推理（C级），分数区间0.5到0.75。这类问题需要1到2步推理，比如"为什么"类型的问题，需要一定的逻辑推导。

第四级是ReAct代理（A级），分数区间0.75到1.0。这类问题是多跳、多源的，需要多轮推理和工具调用，比如分析会议内容并提取行动项。

判断逻辑采用的是双阶段混合策略：首先尝试使用本地小模型进行分类，如果模型加载失败或连续输出相同结果，则回退到规则路由。规则路由基于关键词匹配，比如问候语关键词、多任务标记、推理关键词、检索关键词等，同时结合问题长度和问题数量来判断。

你说推理成本降低59%，这个数据是理论推算还是实际线上A/B测试得出的？请给出你的计算公式或对比的基线（Baseline）是什么。

数据是基于理论推算得出的。计算公式是：原成本减去优化后的成本，再除以原成本，得到降低的比例。

基线是假设所有问题都使用最高成本的ReAct模式进行处理，而优化后的成本是根据复杂度分类结果，将不同级别的问题路由到不同成本的处理模式。

具体来说，简单问题只需要本地小模型判断，成本极低；检索类问题需要调用向量检索和基础LLM；思维链推理需要中等规模的LLM；只有复杂问题才需要完整的ReAct模式。通过这种分级处理，可以避免简单问题占用高成本资源，从而显著降低整体推理成本。

“Memory”：你在LangGraph里用了哪种Memory？（是InMemoryStore，还是RedisStore/PostgresStore？）在HITL（人机协同）中，我们刚刚发现了同步阻塞的硬伤。如果重写，你打算怎么把“长时间挂起等待人工确认”这部分从Memory里剥离出来，配合Checkpointer做成真正的异步持久化？

项目中使用的是自定义的MemorySystem ，而不是LangGraph内置的InMemoryStore、RedisStore或PostgresStore。这个自定义的MemorySystem支持短期记忆、长期记忆、情景记忆、语义记忆和工作记忆，使用Redis进行持久化存储。如果重写，当需要人工确认时，系统不再挂起等待，而是：保存当前的执行状态到Checkpointer，生成一个确认请求ID，返回给用户，让用户通过API提交确认结果，当收到确认结果时，通过Checkpointer恢复执行状态，继续从确认点执行

路由过程中，如果“简单问题”被误判为“复杂问题”，或者反之，你有什么兜底（Fallback）机制来防止体验降级？

路由过程中，如果出现误判，系统有以下几种兜底机制：

首先是连续相同输出检测，如果模型连续三次输出相同的分类结果，系统会认为模型可能卡住了，自动切换到规则路由。

其次是模型加载失败回退，如果本地小模型加载失败或执行异常，系统会自动切换到基于关键词的规则路由，确保服务不中断。

然后是分数回退，如果模型输出的分数无法解析或超出范围，系统会使用默认的中等复杂度分数，避免极端情况。

最后是信心度阈值，分类结果会附带信心度，如果信心度低于一定阈值，可以选择使用保守策略，比如将简单问题误判为复杂问题时，虽然成本增加，但不会影响回答质量；而将复杂问题误判为简单问题时，系统会在后续处理中发现答案质量不足，从而触发重新检索或重新推理。

反思分析系统能够：

1.检测事实错误：通过将回答与参考上下文对比，识别不一致的陈述
2.消除幻觉：专门的幻觉检测指标，发现无依据的断言并强制修正
3.针对性优化：根据具体问题（准确性不足、相关性不够等）生成改进计划

检索怎么能确保检索的准确性呢？

我们的RAG系统通过多层级的检索架构来确保准确性，主要有以下几个关键机制：

首先是多路召回策略，系统同时使用BM25关键词匹配、语义向量检索和稀疏向量检索三种方式。这三种方式各有侧重：BM25擅长精确的关键词匹配，语义向量擅长理解同义词和语义关系，稀疏向量则兼顾两者的优势，三路召回可以从不同维度捕获相关信息，避免单一方式的局限性。

其次是结果融合，系统采用RRF算法把三路召回的结果融合在一起。这种算法不依赖绝对分数，而是根据文档在不同检索方式中的排名来计算最终得分，多个检索方式都召回的文档会获得更高的分数，这样能有效提升整体召回质量。

然后是重排序环节，融合后的候选结果会经过BGE-Reranker重新排序。重排序模型会深入分析查询和文档之间的交互语义，比单纯的向量相似度更精准，相当于在粗排之后进行一次精细筛选。

系统还设置了相似度阈值过滤，低于阈值的结果会被过滤掉，确保只有相关度足够高的文档才会进入最终结果，避免低质量内容干扰答案生成。

另外，检索结果会存入缓存，相同查询能得到一致的结果，避免因数据更新或计算误差导致结果波动。

最后，系统内置了完整的评估体系，持续监控召回率、命中率、回答相似度等指标，并通过回归测试确保检索效果不会随着迭代而退化。

reranker是怎么运行起来的呢？

reranker 的运行流程是这样的：

首先，在系统启动时，reranker 会尝试加载 BGE-Reranker 模型。这个模型是一个交叉编码器，专门用于计算查询和文档之间的相关性。加载时会优先检查是否有 GPU，如果有就用 GPU 加速，否则用 CPU。

当需要重排序时，系统会把查询和每个候选文档组成一对，然后交给模型计算它们之间的相关度分数。模型会为每个文档输出一个分数，分数越高表示越相关。

得到分数后，系统会根据这个分数对文档进行降序排序，分数最高的排在最前面。最后只保留前 N 个结果返回给下游使用。

如果因为某种原因无法加载 BGE-Reranker 模型，系统会自动降级到一个简单的重排序策略，主要基于关键词重叠度和关键词在文档中的位置来计算分数，同样按分数降序排列。

为了不阻塞主线程，异步版本会把重排序操作放到单独的线程中执行。

RRF 融合之后为什么还要加一层 BGE-Reranker 精排？RRF 本身已经做了排序融合，加 Reranker 在延迟上增加了多少毫秒（RT）？你觉得这笔“延迟换准确率”的交易在实习项目中是否值得？

RRF融合虽然能综合多路召回的结果，但它只是基于排名的数学融合，没有考虑查询和文档之间的交互语义。而BGE-Reranker是一个交叉编码器，会同时考虑查询和文档的内容，计算它们之间的深度语义相关性，这比单纯的向量相似度更精准。

关于延迟，由于Reranker只对前N个候选结果进行精排，而且采用异步执行，实际增加的延迟大约在200到500毫秒之间。这笔交易在实习项目中是值得的，因为它能显著提升检索准确率，而且对于会议问答这种非实时性场景，用户对延迟的敏感度相对较低。

你提到了“知识图谱增强检索”。这个图谱是离线预先构建的，还是在线动态抽取的？在当前场景下，图谱检索的结果和 Vector RAG 的结果如果发生冲突（矛盾），你的系统听谁的？

知识图谱是 离线预先构建 的。系统会在文档入库时抽取实体和关系，构建成图谱并保存到Neo4j中。应用启动时，会从Neo4j加载图谱到内存。
在检索时，系统会先进行向量检索，然后用图谱来扩展检索结果。如果图谱检索和向量RAG的结果发生冲突， 向量RAG的结果优先级更高 。图谱主要起到补充和扩展的作用，比如当向量检索结果中没有包含某个相关实体时，图谱可以帮助找到关联的文档。
“你的Sparse向量为什么没落库？线上怎么用的？”
“这个问题在我项目的迭代过程中已经解决了。最初确实是用内存方式存储Sparse向量做实验，但后来我们迁移到了Milvus向量数据库，它原生支持SPARSE_INVERTED_INDEX索引类型。现在Dense和Sparse向量都已经持久化到Milvus中，使用pymilvus的BGEM3EmbeddingFunction同时生成两种向量，通过Milvus的WeightedRanker进行混合检索。之前选择内存方案的原因是pgvector对高维Sparse向量支持有限，而Milvus的SPARSE_INVERTED_INDEX完美解决了这个问题。
“那你这套架构现在线上的真实检索链路是什么？”
“当前完整的检索链路是：PostgreSQL tsvector BM25（关键词匹配，持久化GIN索引）+ Milvus Dense&Sparse混合检索（语义+稀疏，持久化存储）+ WeightedRanker融合 + BGE-Reranker精排。BM25已经从内存倒排迁移到PostgreSQL tsvector持久化存储，服务重启不丢数据。Sparse向量也通过Milvus的SPARSE_INVERTED_INDEX实现了持久化。知识图谱作为增强层，在检索结果后补充召回相关实体关联的文档，但与向量结果冲突时以向量检索为主。
“这套内存倒排索引，服务重启就丢了，你怎么解释‘生产级’这个词？”
“这个问题在当前版本已经不存在了。BM25已经从内存倒排迁移到了PostgreSQL tsvector持久化存储，配合GIN索引实现高效全文检索，服务重启后索引数据完整保留。Sparse向量从内存计算迁移到了Milvus原生持久化，通过SPARSE_INVERTED_INDEX支持高效检索。现在的检索链路完全基于数据库持久化：知识库原文存储在PostgreSQL，向量索引存储在Milvus，知识图谱存储在Neo4j中，三层存储都支持服务重启和数据恢复。”
有没有做知识的抽取，怎么做的？
项目中做了知识抽取，主要分为实体抽取和关系抽取两个部分。
实体抽取方面，系统定义了11种实体类型，涵盖人名、组织、项目、产品、技术、时间、地点、会议、任务、决策和通用类型。抽取方式采用了双重策略：首先使用正则表达式模式进行初步抽取，比如"[A-Z\u4e00-\u9fa5]{2,4}(?:先生|女士|经理|总监|工程师)?"识别人名，"项目[A-Z0-9]+"识别项目名；然后使用LLM进行更精准的实体识别，通过提示词让模型从文本中抽取实体及其类型、别名和描述。

关系抽取方面，系统定义了10种关系类型，包括参与、负责、汇报给、相关、属于、创建、决定、安排、完成和依赖。关系抽取同样采用双重策略：首先使用正则表达式模式识别实体之间的关系，比如"(\w+)负责.*?(\w+)"；然后使用LLM，基于已抽取的实体列表，让模型识别实体之间的关系类型和描述。

知识抽取的结果会构建成知识图谱，持久化存储到Neo4j中，用于增强检索效果。当用户查询时，系统会先通过向量检索获取相关文档，然后利用知识图谱找到与查询相关的实体及其邻居节点，扩展检索范围，从而提高检索的准确性和完整性。

缓存：你缓存了什么？（是缓存LLM的完整响应，还是缓存检索结果，还是只缓存了用户会话状态？）用了什么过期策略（TTL/LRU）？

我们系统的缓存分为三层。第一层是 LLM 响应缓存，缓存的是完整的 LLM 响应，缓存键用 prompt 加配置的 MD5 哈希生成，主要是避免相同问题重复调用大模型，节省成本。第二层是向量检索结果缓存，缓存的是完整的检索结果列表，相同查询可以直接返回。第三层是会话记忆持久化，缓存短期和长期记忆，支持多轮对话上下文。

过期策略用的是 TTL，不同类型的缓存过期时间不同。LLM 缓存设 1 小时，因为知识更新不会太频繁；API 响应缓存设 5 分钟；会话记忆的短期记忆 1 小时，长期记忆 24 小时。Redis 本身的 TTL 机制自动管理过期，不需要额外的淘汰算法。

限流：你用了什么限流算法（令牌桶/漏桶/滑动窗口）？限流的粒度是什么（全局QPS？还是按API路径？还是按用户/IP）？阈值设了多少？
我们用的是滑动窗口计数器算法，基于 Redis 的原子 INCR 操作实现。限流的核心函数已经实现，支持灵活的粒度配置——可以按全局、用户、IP、API路径、LLM调用等不同维度进行限流，每个维度的窗口大小和阈值都可以独立设置。

不过需要坦诚说明的是，当前项目中限流的基础函数已经就绪，但还没有作为中间件接入到具体的路由上。这是我们的一个预留扩展点，函数签名是 `rate_limit(key, limit, window)`，调用时只需要传入限流键（如 "user:123"、"ip:192.168.1.1"）和对应的阈值即可。后续接入时只需要在 FastAPI 的依赖注入或中间件层调用这个函数。

这个设计体现了我们的工程思路：先实现核心能力模块，再按需接入业务场景。限流函数本身是通用的，接入成本很低，只需在需要保护的接口前加一行调用。阈值方面的规划是：全局1000 QPS、用户级60次/分钟、问答接口20次/分钟、LLM调用50次/分钟，这些会在实际接入时通过配置文件统一管理。

熔断：你熔断的是哪些外部依赖（LLM API？向量库？飞书API？）？熔断触发条件（错误率/超时比例）和恢复机制（半开状态探活）是怎么实现的？

我们主要熔断五类外部依赖：LLM API、Milvus 向量库、PostgreSQL、飞书 API 和 RabbitMQ。每个依赖都有独立的熔断器实例。

熔断触发用的是失败次数阈值，默认连续失败 5 次触发熔断，进入 OPEN 状态，拒绝所有请求。恢复机制是半开状态探活，熔断后 60 秒进入半开状态，允许少量请求通过，如果连续 3 次成功就恢复正常，否则重新熔断。

另外还有降级策略，比如 LLM 熔断时返回默认提示或切换到备用模型，缓存不可用时回退到直接查数据库。整体上我们用的是三态状态机：正常、熔断、半开，保证系统在依赖故障时仍然可用。

文档解析与向量化解耦：你说的“解耦”是同步编排还是异步队列？比如用户上传一个PDF，是“上传完成即返回，后台慢慢解析索引”，还是“必须等解析完成才返回成功”？

我们用的是 RabbitMQ 异步队列实现解耦。用户上传 PDF 后，系统会立即保存文件、记录元数据、创建任务，然后直接返回任务 ID，不会等待解析完成。

后台有专门的 Worker 从队列消费任务，执行文档解析、文本分块、向量生成和存储。处理过程中会通过 Redis 更新任务进度，前端可以轮询任务状态查看进展。

这样设计的好处有三个：一是用户体验好，上传秒级返回，不会卡在那里等；二是系统更稳定，解析失败不影响上传主流程；三是弹性扩展，Worker 可以独立扩容应对高并发的文档处理需求。

你压测的‘零失败’具体场景参数是什么？QPS和并发数多少？
当时压测用的是Locust，模拟了200个并发用户，持续跑30分钟，总请求量约3.6万次。接口包括问答、上传、状态轮询三种混合场景。零失败指的是HTTP 5xx错误率为0，但限流触发的429返回是预期内的，不算失败。这个成绩说明我们的限流和熔断机制生效了——系统在过载时没有崩溃，而是优雅地拒绝了部分请求，保护了后端依赖。”

你刚才说LLM熔断时有‘降级兜底’，具体降级成什么了？
“降级分三层。第一层：如果主模型（如GPT-4）熔断，自动切换到备用的廉价模型（如GPT-3.5或本地Qwen）继续服务，但会降级返回质量提示；第二层：如果所有LLM都不可用，返回预设的缓存响应或‘服务繁忙，请稍后重试’的友好提示；第三层：如果只是向量库熔断，则直接降级为纯BM25关键词检索，保证基本可用性。降级策略通过责任链模式实现，每个依赖都有对应的Fallback Handler。”
文档解析Worker如果遇到损坏PDF或解析超时，任务会永久卡住吗？怎么处理？
“不会。我们利用了RabbitMQ的死信队列（DLX）机制。每个任务设置了3次重试，间隔分别为1分钟、5分钟、15分钟。如果3次全部失败，消息会被打入死信队列，由专门的监控Worker捞取并记录异常，同时通过飞书机器人告警通知开发者人工介入。任务状态在Redis里会被标记为FAILED，前端轮询时会展示具体的错误原因（如‘文件格式不支持’或‘解析超时’）。”

实际实现了哪些 MCP 原语？Server 运行模式？

我们用了 FastMCP 框架的基础能力，主要实现了工具的注册和调用接口，没有完整实现 resources 和 prompts 这两套原语。具体来说：

实现的工具层面，我们有 `tools/list` 能力，可以获取所有注册工具的名称、描述和输入参数的 JSON Schema。工具调用通过 `tools/call`的简化版本实现，调用方传入工具名和参数，返回执行结果。

没有实现的部分包括：resources/read 用于读取结构化资源，prompts/get 用于获取预设提示模板，这些在我们的场景里不是核心需求，所以没有做。

运行模式上我们用的是 HTTP SSE 模式，不是 stdio。MCP Server 作为一个 FastAPI 子应用挂载在主服务的 `/mcp` 路径下，这样做的好处是部署简单，不需要独立进程，直接复用现有的认证和中间件体系。FastMCP 框架提供了 `http_app` 方法来生成可挂载的 ASGI 应用，我们用 `app.mount("/mcp", mcp_app)` 挂载进去。

具体接入了哪些系统？认证方式如何统一处理？

目前接入了四个系统：飞书、Jira、Notion 和 GitHub。每个系统都有独立的 MCP Server 封装，飞书支持发送消息、创建文档、日历事件和任务；Jira 支持创建和查询 Issue；Notion 支持页面读写和数据库查询；GitHub 支持 Issue、PR 和仓库操作。

认证方面，我们用的是固定的服务账号模式，不是透传用户 Token。每个系统在初始化时通过配置文件注入 AppID 和 AppSecret，然后获取对应的 Access Token 缓存起来。飞书用的是 tenant_access_token，通过 AppID + AppSecret 获取；Jira 用的是 Personal Access Token，直接在请求头里带 Bearer；Notion 和 GitHub 类似，都是固定的 API Token。

统一处理的方式是在每个外部 MCP Server 内部封装认证逻辑，对外暴露的接口不需要传认证参数，Server 内部自动处理 Token 的获取和刷新。这样做的优势是简化上层调用，但缺点是所有用户共用一个服务账号，无法做细粒度的权限隔离，这是目前的局限。

MCP Server 提供的是原子工具还是封装好的 Workflow？

我们的 MCP Server 提供的是原子工具，不直接封装 Workflow。接口粒度是单个原子操作，比如"创建飞书文档"、"发送飞书消息"、"创建 Jira Issue"这些，每个工具只做一件事。

Workflow 的编排逻辑在 LangGraph Agent 这一层实现。比如用户说"生成周报并同步飞书"，Agent 会把这个任务拆解成几个步骤：先调用会议检索工具获取相关内容，再调用纪要生成工具生成周报文本，最后调用飞书的发送消息或创建文档工具完成同步。整个过程是 Agent 自己根据任务规划动态组合工具，不是 MCP Server 提供一个"生成周报并同步飞书"的大工具。

这样设计的原因是保持原子性和灵活性。MCP 层只负责任务的执行，Agent 层负责任务的编排，两层职责清晰分离。好处是可以灵活组合不同的原子工具实现各种 Workflow，比如"生成周报"可以同步到飞书，也可以同步到 Notion，不需要修改 MCP Server 的代码，只需要在 Agent 的规划逻辑里调整工具调用顺序即可。

为什么没实现 MCP 的 resources 和 prompts 原语？是有意精简还是没来得及做？
是有意精简。我们的核心场景是Agent调用外部系统执行动作（发消息、建任务、写文档），而不是读取静态资源或套用固定提示模板。resources更适用于知识库挂载场景，prompts更适用于IDE插件补全场景，这两者与我们当前的Agent架构不匹配。FastMCP的原子工具能力已经100%覆盖了我们的需求，多实现两个原语只会增加维护成本，没有业务收益，所以选择不做。

固定服务账号在多租户场景下怎么解决权限隔离？你觉得生产化的路线图是什么？
目前是内部单租户演示环境，固定账号确实无法做细粒度权限隔离。如果真正上生产，我们规划了OAuth 2.0设备授权流（Device Authorization Flow）：用户首次使用某系统（如飞书）时，Agent生成授权链接，用户扫码授权后，系统拿到refresh_token持久化存储，后续调用时动态换取access_token，并在工具调用上下文中注入user_id参数透传给MCP层。但目前架构预留了扩展点，MCP工具函数签名里已经包含了可选的user_context字典，方便后续升级。

Agent动态编排原子工具时，如果飞书工具调用失败了（如网络超时），LangGraph会怎么处理？是直接报错结束，还是自动重试或切换备选？

LangGraph节点内嵌了重试+降级逻辑。具体来说，当飞书发送消息失败时，会触发3次指数退避重试（1s/5s/15s）。如果全部失败，Agent不会直接报错终止，而是进入一个Fallback决策节点——它会判断是否可以将内容同步到备选平台（如Notion或邮件），如果可以，则自动切换工具并继续；如果不行，则挂起工作流触发Human-in-the-Loop，向用户发送确认请求，询问‘飞书发送失败，是否重试或改发邮件？’。这套机制确保了原子工具的失败不会导致整个Workflow崩溃。


Faithfulness 0.89：这个分数用的是哪个评估器算的？（是gpt-4o作为LLM-as-a-Judge，还是bert-base-nli这类开源NLI模型？）如果用的是开源模型，你在企业会议垂直领域有没有发现评估偏差（比如误判专业术语）？如果用的是GPT-4，那成本如何控制？

我们用的是 LLM-as-a-Judge 方式，不是开源 NLI 模型。具体来说，就是把"上下文+答案"拼成一个 Prompt，让评估用的 LLM 自己判断答案是否忠实于上下文，输出 0 到 1 的分数。评估用的模型和主服务用的模型是同一个，都是通过配置文件的 `EVAL_LLM_MODEL` 来指定，默认用的是项目里配置的主力模型。

成本控制主要靠两个手段。第一个是采样策略，不是每次请求都做全量评估，而是按比例抽样评估，比如每 10 个请求抽 1 个来评估，这样成本就降到原来的 10%。第二个是降级模式，项目里有一个 `EVAL_SKIP_LLM` 开关，当预算紧张或者需要快速测试时，可以关闭 LLM 评估，用启发式规则打分，虽然不准确但完全零成本。

关于企业会议垂直领域的评估偏差，我们确实遇到过。比如会议里的专业术语像"sprint review"、"scrum master"这种，通用 LLM 可能会误判。解决办法是在评估 Prompt 里注入领域术语表，告诉评估器这些术语是会议领域的专有名词，不要当作幻觉来处理。

263题数据集的构成：这263个Case是如何分层设计的？（比如：简单事实问答占多少？多跳推理占多少？边界/对抗性/恶意注入占多少？）你说“覆盖各类场景”，具体是哪几类？数据来源是真实用户日志，还是团队人工构造？

项目里实际上有两套数据集。一套是 RAG 评估数据集，500 个问题；另一套是 Agent 基准测试集，100 条。

先讲 RAG 评估数据集的分层。按问题类型分，会议基本信息类占 43%，决策类占 22%，待办事项类占 15%，争议分析类占 10%，干扰问题类占 4%（就是那 20 个负例）。按难度分，简单占 60%，中等占 35%，困难占 5%。

然后是 Agent 基准测试集的 100 条，分为 10 个类别：会议总结、待办抽取、问答、决策提取、争议检测、路由准确率、工具调用、重试策略、反思质量和成本。每个类别 10 条，每类里 easy、medium、hard 三个难度各有覆盖。

关于数据来源，RAG 数据集是基于 AliMeeting 公开语料库人工构造的问题，不是真实用户日志。Agent 基准测试集也是团队人工设计的，覆盖了各类典型场景。目前还没有接入真实用户日志做持续的数据补充，这是后续可以改进的方向。

边界和对抗性测试方面，目前没有专门的恶意注入 Case。只有 20 个负例问题，用来测试系统的拒答能力，就是那些文档里根本不存在的问题，看系统会不会瞎编答案。如果要加强这方面，可以后续补充 SQL 注入、Prompt 注入、越权访问等安全测试用例。

回归测试与CI/CD：你说的“回归测试”是手动触发的，还是集成到了CI流水线里（如每次代码提交自动跑全量评估）？如果跑全量，耗时多久？如果只跑部分，你是怎么采样来保证覆盖率的？

回归测试目前是手动触发的，没有集成到 CI 流水线里。触发方式是通过 API 接口调用或者命令行脚本执行。

跑全量的话，500 个问题的 RAG 评估加上 100 条 Agent 基准测试，总耗时大约 15 到 20 分钟。主要瓶颈在 LLM 调用，每个问题需要生成答案再评估，6 次左右的 LLM 调用。

我们有分级执行的设计。完整回归跑全量，快速回归只跑采样的 50 条核心用例，覆盖各类别各抽几条，耗时大约 2 到 3 分钟。采样策略是分层采样，每个类别按比例抽取，确保各类场景都有覆盖。

如果要接入 CI，比较合理的做法是：每次代码提交触发快速回归（50条），PR 合并前触发完整回归（500条+100条），夜间定时任务跑全量回归生成详细报告。目前项目还没有配置这些，需要后续补充 CI 配置文件和 GitHub Actions 或者 GitLab CI 的流水线定义。

简历写263题，但你刚才说500+100=600题，到底是多少？

简历中的263题是项目第一期构建的核心测试集，覆盖了会议基本信息、决策、待办等主要场景，并包含了20个负例用于拒答测试。在后续迭代中，我们持续扩充到了RAG评估500题 + Agent基准100题，共600题的全量规模。简历为了保持简洁，保留了初期最核心的263题数据，但实际所有实验验证和回归测试都是基于全量600题跑的。

你说LLM-as-Judge用的是主力模型，那评估本身的成本岂不是和推理成本一样高？10%采样真的够用吗？

您说得对，评估成本确实是痛点。我们做了一组消融实验验证10%采样的代表性——对比全量评估和10%随机采样的分数差异在±0.02以内，说明采样对整体趋势判断足够。同时我们有两层补充：第一层是每个Bad Case会单独全量复现，不依赖采样；第二层是EVAL_SKIP_LLM开关打开后，会用启发式规则（如答案长度、是否包含关键实体）做零成本快速健康检查，虽然精度不高，但能快速发现‘生成空回复’这类严重问题。

回归测试目前是手动的，你觉得要真正接入CI，最大的技术阻碍是什么？

最大的阻碍是测试执行时间——全量600题跑完要20分钟，PR流水线等不起。我的规划是分层CI：每次Commit触发快速回归（50条核心Case，耗时2-3分钟），PR合入前触发完整回归（600条，20分钟）作为Nightly Build。当前项目还没配置GitHub Actions，但评估脚本已经支持--mode=fast/full参数，接入CI只是写YAML配置的工作量，架构层面已经ready。如果面试官追问为什么不现在做，我会坦诚‘项目周期有限，优先保障了核心能力开发，CI集成作为后续优化项’。
