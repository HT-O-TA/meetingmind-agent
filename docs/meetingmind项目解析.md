# meetingmind项目解析

本文只解释项目核心设计：解决了什么问题、当前怎样实现、各模块怎样连接，以及哪些能力还没有完成。内容以当前代码和已有证据为准，不记录开发过程，也不把计划中的能力写成现有能力。

首发范围为本机部署与验收。采用单机轻量模式，通过本机回环 HTTPS 入口访问。已有证书、代理、鉴权、故障响应、基础告警及多用户压测的本机演练记录，详细条件见第五、六板块。

## 一、认证与鉴权

### 1. 这一部分解决什么问题

会议系统中既有普通用户、只读用户和管理员，也有个人、部门和公开资料。系统不仅要确认“请求是谁发出的”，还要保证用户只能读取和修改自己有权访问的资源。

认证负责确认用户身份，鉴权负责判断用户能做什么。权限检查不能只放在登录页面或API入口，因为会议内容还会经过检索、缓存、异步任务和工具调用。如果后面的环节丢失用户身份，即使接口登录检查正确，也可能发生私有文档泄露或跨用户操作。

### 2. 当前方案

用户使用用户名和密码登录。密码经过加盐哈希后保存在PostgreSQL中，登录成功后由后端签发带过期时间的JWT。业务请求携带JWT，后端解析用户ID后重新查询数据库，确认账号仍然存在且处于启用状态，并使用数据库中的最新角色和部门信息。

项目当前有三种角色：

| 角色 | 能力 |
|---|---|
| `admin` | 在相应业务接口拥有更宽访问范围，仍受限流和工具门禁约束 |
| `user` | 按资源归属和部门范围读写 |
| `readonly` | 只能读取有权资源，不能执行写操作 |

资源权限不只看角色，还会结合会议组织者、文档上传者、所属部门和允许访问的资源范围：

- 同部门用户可以读取共享会议资料，但不能随意修改其他人组织的会议；
- 文档上传者和管理员可以修改文档，普通用户只能读取其权限范围内的资料；
- 发言、待办和音频任务继承所属会议或创建者的权限；
- 异步任务记录创建用户，查询、取消、重发和清理都按当前用户隔离；
- 只读用户不能通过任务或工具调用绕过写权限。

当前非公开文档并不等于“只有上传者可见”，同部门用户仍可能具有读取权限。更细的个人私有、部门共享和全局公开三态模型尚未落地。

### 3. 一次请求怎样经过各层

认证与鉴权主链可以概括为：

> 用户登录 → 后端签发JWT → 请求携带JWT → 回查PostgreSQL用户状态 → 生成访问上下文 → 业务、检索、缓存、任务和工具层分别校验权限

访问上下文包含用户、部门、管理员状态、可访问会议和文档范围等信息。它会继续进入以下环节：

1. **业务接口**：检查用户能否读取或修改目标会议、文档、待办和任务。
2. **检索入口**：BM25、向量检索和文档分块读取缺少访问上下文时默认拒绝，即Fail Closed。
3. **向量回查**：Milvus只返回候选ID和分数，正文、软删除状态和最终权限仍由PostgreSQL确认。
4. **缓存隔离**：检索缓存键包含用户和权限范围，检索缓存保存候选ID和排序信息。命中后仍会回查PostgreSQL，重新检查正文和访问权限。
5. **异步任务**：任务绑定创建用户和业务资源，不同用户不会因为使用相同幂等键而复用同一任务。
6. **工具调用**：外部写操作还要通过权限、风险等级、人工确认、幂等和持久审计门禁。

人工确认也与用户、Agent运行、线程和单次工具调用绑定。恢复执行时会重新检查身份和上下文，避免旧确认被其他用户或新操作复用。

前端只负责保存令牌、附加认证头和改善页面体验。真正的安全判断全部在后端完成，不能依赖隐藏按钮或前端路由。

### 4. 当前亮点

- JWT只提供身份线索，后端还会回查数据库中的最新账号状态；
- 权限贯穿API、检索、缓存、异步任务、HITL和工具调用，不是只检查一次；
- 检索缺少访问上下文时默认拒绝，维护脚本和离线评测也必须显式提供访问上下文，按任务需要选择授权范围；
- Milvus只负责找候选，PostgreSQL是正文、资源状态和ACL的最终事实源；
- 检索缓存不保存正文，并按用户和权限范围隔离；
- 高风险写工具需要权限、人工确认、幂等和审计同时成立；
- 已有跨部门403、私有文档隐藏、缓存隔离和工具确认等测试与演示证据。

### 5. 当前边界

当前方案足以支持本地演示和工程验证，但还不是完整的企业身份与权限系统：

- 禁用账号后，后续请求会被账号状态检查拒绝。前端退出会清理本地令牌，服务端目前没有单令牌、单设备会话撤销或刷新能力；
- 生产配置启动时检查示例签名密钥、调试开关和跨域来源，访问令牌有效期限制为1至60分钟；
- 文档权限仍以公开标记、上传者和部门规则组合判断，没有明确的三态可见性模型；
- 用户扩展权限仍缺少版本化的严格Schema；
- 尚未接入OAuth、OIDC、企业SSO、多因素认证和真正的多租户隔离；
- 尚未使用PostgreSQL行级安全，也没有完整的权限管理后台；
- 前端令牌存储方案仍适合本地演示，不应直接作为公网生产方案。

### 6. 上线前还缺什么

认证鉴权部分后续需要按以下顺序继续完善：

1. 修复并验证PostgreSQL等真实基础设施连接；
2. 建立Alembic迁移基线，避免继续依赖一次性迁移脚本；
3. 将自由JSON权限升级为有版本的严格JSONB Schema；
4. 将文档公开布尔值升级为`private`、`department`、`public`三态可见性；
5. 增加可撤销的JWT会话、刷新令牌和退出全部设备能力；
6. 补充会话吊销、权限迁移和故障恢复验证；
7. 公网上线时再接入HTTPS、密钥托管、更安全的前端会话方案和统一身份服务。

以上生产升级的方向已经确认，但当前实施计划处于暂停状态，尚未执行数据库迁移，也不属于冻结版本的现有能力。

### 文档权限矩阵

文档权限矩阵覆盖管理员、普通用户、只读用户，以及本人文档、同部门文档、公开文档、跨部门私有文档的读写组合，共 24 格。测试调用文档服务，并检查拒绝时返回的 403。

## 二、限流、失败控制与降级

### 1. 这一部分解决什么问题

会议问答、Agent推理、文件处理和外部工具都可能消耗较多CPU、GPU、Token、数据库连接和队列容量。如果没有边界，一个用户的高频请求、模型连续重试或异常任务就可能拖慢整个系统。

这一板块解决三个问题：限制请求进入速度，限制单次任务能消耗的资源，以及在下游失败时及时停止、隔离或降级。它关注的是系统不要被压垮，也不要在错误发生后无限重试。

### 2. 当前方案

#### API入口限流

关键入口使用Redis固定窗口计数。实例连接同一Redis并使用一致的键空间与规则时可以共享额度，实际多实例部署仍需验证：

| 入口 | 默认限制 |
|---|---:|
| 注册 | 每个IP 3次/小时 |
| 登录 | 每个IP和用户名摘要各5次/5分钟 |
| RAG问答 | 每个用户20次/分钟 |
| Agent普通查询 | 每个用户10次/分钟 |
| Agent流式查询 | 每个用户5次/分钟 |
| Agent批量查询 | 每个用户2次/分钟 |
| 文档或音频任务创建 | 每个用户10次/分钟 |
| 文档批量上传 | 每个用户2次/分钟 |
| 失败任务人工重发 | 每个用户5次/分钟 |
| 任务长轮询 | 每个用户5次/分钟 |

超出额度返回429和建议等待时间。Redis无法完成限流检查时，高成本或高风险入口返回503，不会在失去限流能力后继续放行。管理员同样受资源限流约束。

#### Agent运行预算

每次Agent运行都有独立Token账本。模型调用前先估算输入、最大输出和安全余量，再检查模型上下文窗口、单节点预算、整次运行预算和最大调用次数。预算不足时会在请求发给模型之前停止。

规划层默认最多生成8个任务，Token紧张时会主动减少任务数。批量请求一次最多接收20个问题，Agent内部并行任务默认最多3个，每个任务默认最多执行60秒。

#### 重试和队列隔离

云模型只针对供应商429执行有限的指数退避重试，重试本身也计入Token和调用预算。工具调用根据是否幂等决定重试次数，可能产生副作用的非幂等工具不会被反复执行。

RabbitMQ消费者默认只预取1条消息。任务失败后最多额外投递2次，总尝试次数为3次；仍然失败就进入死信队列，等待人工确认后重发。单队列默认最多保存10000条消息，队列已满时拒绝继续发布，避免积压无限增长。

#### 失败率停止和降级

Agent每完成一个并行执行波次，都会计算当前累计失败率。默认达到30%时停止后续波次，把尚未执行的任务标记为跳过，避免沿着已经明显失败的计划继续消耗资源。

局部能力不可用时，系统优先给出诚实的降级结果。例如，RAG生成失败时可以保留检索片段，复杂度模型不可用时回退规则判断，语义分块不可用时回退固定分块，不确定的外部写操作则直接关闭。

### 3. 一次请求怎样经过各层

限流与失败控制主链可以概括为：

> 请求进入 → 身份或IP分桶 → Redis检查额度 → 校验输入规模 → 建立运行预算 → 限制并发和超时 → 有限重试 → 检查累计失败率 → 正常返回、降级或停止

异步任务则采用另一条链路：

> 收到创建请求 → 入口限流 → 创建任务并尝试投递 → RabbitMQ削峰 → 消费超时控制 → 延迟重试 → 重试耗尽进入死信 → 人工重发

这些机制分别限制入口、单次运行和后台积压，不能互相替代。API限流不能阻止一次请求内部无限调用模型，Token预算也不能控制大量用户同时建立长连接，所以项目同时保留了多层边界。

### 4. 当前亮点

- 限流使用Redis原子计数，多实例之间不会各算各的；
- 登录同时限制IP和用户名摘要，可以兼顾单IP撞库与分布式尝试；
- Redis异常时高成本入口默认拒绝，不会悄悄失去限流保护；
- 模型429重试也计入Token账本，不能通过重试绕过成本限制；
- 非幂等工具减少自动重试，并继续受权限、人工确认、幂等和审计约束；
- RabbitMQ具备预取限制、有界重试、发布确认、队列上限和死信恢复；
- Agent失败率达到阈值后会停止后续波次，不再只是记录一个没有生效的配置。

### 5. 当前边界

当前具备限流、预算控制、超时、有限重试、死信、局部降级和进程内 LLM 熔断。

Jira、Milvus、PostgreSQL、Redis 和 RabbitMQ 仍依靠各自的超时、重试或降级。

还需要注意：

- 当前API限流是固定窗口，窗口交界处可能出现短时突发；
- 普通会议、文档和待办CRUD没有统一频率限制；
- 普通Agent和SSE入口共用每个后端进程默认8个在途名额，SSE占用持续到响应结束或断开。跨进程、按用户和GPU任务的在途限制仍待建设；
- 队列重试使用固定延迟，没有根据失败次数指数退避；
- 失败率停止只作用于单次Agent运行，不会影响其他请求；
- 部署入口应配置实际可信代理地址。Compose可用Uvicorn的`FORWARDED_ALLOW_IPS`指定，默认仅信任回环地址。本机模拟可信代理实测同一转发IP第六次登录请求返回429，另一IP仍可进入登录校验。正式部署拓扑仍需复测；
- 限流已通过离线契约测试和本机Redis冒烟。实测覆盖超额429、Retry-After、窗口到期后放行，以及将测试客户端接到不可用端口时返回503、切回真实Redis后恢复放行。本机可信代理的客户端 IP 分桶已通过验证，相关结果见部署板块。

### 6. 上线前还缺什么

1. 在真实Redis环境验证并发计数、窗口重置、故障503和恢复行为；
2. 为任务长轮询、批量上传和Agent请求补充连接数、在途任务数与全局并发限制；
3. 按实际故障模式评估 Jira 和 Milvus 的熔断，并采集 LLM 熔断状态；
4. 记录429率、503率、下游失败率、队列积压量、死信增长率和熔断状态；
5. 为不同接口建立容量基线，再根据真实压测调整默认阈值；
6. 验证多实例部署下的Redis共享计数、RabbitMQ背压与故障恢复；
7. 将告警、降级和人工恢复步骤写入正式运行手册。

### 模型供应商熔断

熔断按进程内的供应商类型和 Base URL 区分。连接失败和 5xx 连续累计 3 次后打开，冷却 30 秒。冷却期间调用快速失败，半开只允许一个探测。探测成功恢复，失败或取消重新进入冷却。429 继续走已有退避逻辑。预算账本沿用原先的失败记录路径。

使用模拟连接故障和 HTTP 503 演练，覆盖冷却期间零外呼、半开并发拦截、恢复及取消。状态各进程独立，暂未实现跨实例共享。

## 三、监控与运维

### 1. 这一部分解决什么问题

系统能够返回结果，不代表它处于可服务状态。后端进程可能仍在运行，但数据库已经断开；一次请求可能失败，却无法从大量日志中找到对应记录；容器长期运行时，日志也可能持续占满磁盘。

这一板块先解决最基础的三个问题：区分“进程还活着”和“关键依赖可用”，为每次HTTP请求提供可追踪的编号，并限制本地容器日志占用。它是上线前的最小运维底座，不等同于完整监控平台。

### 2. 当前方案

项目提供三类健康入口：

| 入口 | 当前含义 |
|---|---|
| `/live` | 只检查FastAPI进程能否响应，不访问任何外部依赖 |
| `/ready` | 并行检查PostgreSQL、Redis和RabbitMQ |
| `/health` | 兼容旧客户端，检查内容与`/ready`相同 |

PostgreSQL和Redis是关键依赖，任一失败都会让`/ready`返回503。部署入口需要根据就绪结果决定是否停止转发。Redis探针只发送PING，缓存关闭时仍可检查连接。后端启动后，RabbitMQ单独故障返回200并标记`degraded`。Compose冷启动仍要求RabbitMQ先健康。三项探测默认单项超时为2秒，通过异步取消实现。依赖检查结果包含名称、状态和耗时，公开响应不包含连接详情。

进入应用的HTTP请求会生成新的服务端`X-Request-ID`。正常响应、业务异常、HTTP异常、参数异常和未处理异常会带回这个ID，访问日志与异常日志也会记录它。合法的客户端ID作为关联信息保存。CORS预检由外层中间件直接处理。

Compose中的Redis、RabbitMQ、Backend、Worker和Frontend统一使用Docker本地日志驱动，默认单文件10 MiB、保留3个文件，避免容器标准输出无限增长。项目还保留开发环境Agent Trace、工具持久审计、任务状态和死信恢复记录，它们分别用于查看节点执行、外部副作用和后台任务，不应混成一套概念。

### 3. 一次请求或故障怎样经过各层

正常HTTP请求的排障链路是：

> 请求进入 → 服务端生成请求ID → 业务处理 → 访问日志记录ID和耗时 → 响应头返回同一ID → 出现异常时用ID关联异常日志

部署平台判断实例状态的链路是：

> 调用`/live`确认进程存活 → 调用`/ready`并行检查依赖 → PostgreSQL或Redis失败返回503 → RabbitMQ失败返回`degraded` → 依赖恢复后下一次检查自动恢复状态

异步任务使用任务ID追踪状态，并把发起任务的服务端请求ID带入RabbitMQ。发布、消费、重试和死信日志可用这两个ID关联，向量子任务沿用原始请求ID。

### 4. 当前亮点

- 存活和就绪语义分开，部署入口接入就绪状态后可以据此暂停发流量；
- 三项依赖并行探测并设置单项超时，真实故障下的响应时间仍需联调测量；
- RabbitMQ故障采用明确的降级状态，不会把仍可读取资料的实例直接全部摘除；
- 公开响应与探针自身的失败日志限制输出字段，RabbitMQ连接模块另有脱敏连接日志；
- 服务端请求ID不信任客户端输入，并通过异步上下文隔离并发请求；
- 正常与异常响应都能用同一请求ID排查，浏览器也可以读取该响应头；
- 五个Compose服务统一设置日志保留上限，减少本地长期运行时磁盘被写满的风险。

### 5. 当前边界

当前方案主要解决“能检查、能关联、不会无限写日志”，还没有形成生产级可观测体系：

- HTTP访问日志可通过`scripts/summarize_http_logs.py`从标准输入离线汇总各路由的请求量、状态码和P95。耗时截至响应头可用，SSE完整连接时长需另行测量。目前没有实时指标平台、集中式日志或自动告警；
- 没有Worker心跳、队列积压趋势、死信增长率和任务处理时延指标；
- 请求ID覆盖HTTP与队列投递、消费日志。外部工具和持久审计的统一请求ID关联尚待补齐；
- 开发Trace保存在进程内，重启后清空，不能作为生产追踪系统；
- 审计记录关注谁执行了什么副作用，不等同于性能监控日志；
- 已完成本机双实例和进程强杀验证，长时间运行、磁盘压力和更多依赖故障组合仍待验收；
- 当前契约测试可以证明代码行为，但不能替代真实基础设施运行证据。
- 本机后端将探针预算设为3秒。三次独立进程冷启动后，通过真实HTTP访问就绪入口均返回200且整体为正常，RabbitMQ耗时约2.05至2.09秒。项目默认配置仍为2秒。
- 本机Redis已改为只发布到IPv4回环地址，新容器复用原数据卷，旧容器处于停止状态并可回滚。
- 四项真实集成测试通过。PostgreSQL检索回查只选择输出需要的字段，避免读取旧库中类型不同的向量列，权限和软删除校验均已复测。
- 本机旧库的向量列是固定1024维。上传和向量Worker按实际列类型写入，维度不匹配时将结果保留在JSON兼容字段，固定维度列留空。
- RAG先做认证和限流，再初始化检索依赖。未启用重排时不加载重排模型，Milvus连接地址留空时跳过Milvus探测。
- 本机HTTP直连业务演示已通过，覆盖文档上传、轻量检索及引用、待办创建、权限拒绝，以及文档任务和向量子任务完成。本次使用离线词频向量，关闭Milvus与重排，临时提高演示进程的登录和注册额度。生产代理拓扑、GPU模型与Milvus组合仍需实测。
- 在项目根目录用后端Conda环境执行 `python scripts/run_local_acceptance.py` 可复跑轻量业务验收。脚本复用本机三项基础服务，启动临时API和Worker，输出JSON结果并关闭子进程。验收会写入本机测试账号、会议、文档、待办和任务记录。
- Compose默认关闭Milvus。启用时连接、集合检查和查询分别传入3秒超时。对本机不可连接端口的实测中，检索探测约2.17秒后选择回退路径。本地模型加载和多次RPC的总耗时需要单独测量，当前Conda缺少可选的Milvus模型模块。
- 仓库Nginx配置可转发业务API和三个健康入口。本机用临时Nginx连接真实后端，就绪返回200；模拟PostgreSQL探针故障后，就绪和兼容入口均转发503并保留请求ID，存活入口仍返回200。正式部署入口仍需验证客户端IP和是否按就绪状态停止转发。

### 6. 上线前还缺什么

1. 为HTTP、Agent、LLM、数据库和队列增加请求量、错误率、P50/P95耗时、Token和成本指标；

6. 进行多实例、并发、长时间运行和依赖故障注入测试，确认摘流与恢复符合预期；

2026-11-25，Windows、16 逻辑 CPU、Python 3.11.16。下表的耗时与吞吐只统计完成的请求。每格依次为 **P95 毫秒 / 每秒成功数**，上传任务一行统计从上传到向量子任务完成的整条链路。

| 场景 | 并发 1 | 并发 4 | 并发 8 | 并发 16 |
|---|---:|---:|---:|---:|
| 轻量检索 HTTP | 417 / 20.30 | 2372 / 6.73 | 631 / 22.28 | 2936 / 5.43 |
| 合成 Agent 普通入口 | 330 / 3.50 | 295 / 13.75 | 327 / 25.05 | 306 / 25.84 |
| 合成 Agent SSE 入口 | 339 / 3.09 | 372 / 11.34 | 430 / 19.93 | 384 / 20.78 |

- **Agent 和 SSE** 在并发 16 时，各完成 8 次，其余各 8 次被在途保护以 HTTP 503 拒绝。恢复到单次请求后两个入口均成功。并发 8 时 SSE 首事件 P95 为 429 毫秒，完整响应 P95 为 430 毫秒。

### 5. 当前边界

这是一份单实例短时基线。每档只有 16 个样本，P95 容易被个别慢请求影响。Agent 测的是入口和保护机制，完整规划和模型耗时需要另测。后台任务峰值来自客户端跟踪，RabbitMQ 只核对了结束时的队列状态，尚无队列深度峰值曲线。vLLM 报告对应单卡推理服务，适用范围是记录中的硬件、模型和上下文设置。

### 6. 上线前还缺什么

用首发配置和实际反向代理做持续并发测试，使用多会议、多用户和不同文件大小。采集真实 RabbitMQ 深度、最老消息年龄、缓存命中率及各阶段耗时。根据 P95、错误率、积压是否持续增长确定首发容量，再据此设置限流阈值。

### 本机四账号复测与基础告警

本机直连轻量配置用四个账号和独立会议，以并发 4、8 各发 48 次每类请求。384 次全部完成，没有意外错误或容量拒绝。并发 8 时，RAG、Agent、SSE、上传到子任务完成的 P95 分别约为 2097、332、406、1060 毫秒。Agent 仍使用固定延时测试服务。

同步从 RabbitMQ 取得 44 个样本。文档主队列采样最大等待数 3、最大未确认数 1，向量主队列分别为 0 和 1。最后一次有任务的样本之后，下一次采样约 1.70 秒后两条主队列均为 0。这是采样间隔内观察到的回落，瞬时峰值和精确回落耗时未测得。本轮未增加死信。复跑用 `scripts/bench_local_business.py --users 4 --requests 48 --concurrency 4 8` 并指定输出报告路径，同时运行 `scripts/sample_local_queues.py`。

`scripts/check_local_alerts.py` 可按日志窗口和队列基线检查 5xx 比例、P95、连续积压和新增死信，并输出触发、恢复状态。样本不足时保留对应的既有告警。使用 `--watch` 可在前台持续采样，`--queue` 可选隔离演练队列。这次用真实应用访问日志和隔离 RabbitMQ 队列验证了四项规则的触发与恢复，测试消息和队列已清理。常驻服务和外部通知尚未接入。


### 本机加量复测

2026-11-25，Windows 16 逻辑 CPU、Python 3.11.16。单 API、单 Worker，通过回环 HTTP 连接本机 PostgreSQL、Redis 和 RabbitMQ。四账号轮流请求。每组先发 8 次预热，再计时 64 次，各并发档各测一轮。轻量检索沿用词频向量，关闭 Milvus、重排与生成。Agent 普通及 SSE 使用固定等待 250 毫秒的测试服务。

| 场景 | 并发 4 成功数 / 成功 P50 / P95（ms） | 并发 8 成功数 / 成功 P50 / P95（ms） |
| --- | ---: | ---: |
| 轻量检索 HTTP | 64/64 · 13.34 · 89.88 | 64/64 · 101.58 · 519.16 |
| 合成 Agent 普通入口 | 64/64 · 279.07 · 293.74 | 64/64 · 292.46 · 317.76 |
| 合成 Agent SSE 完整响应 | 64/64 · 335.84 · 357.20 | 64/64 · 354.15 · 383.78 |
| 上传到向量子任务完成 | 64/64 · 354.41 · 377.48 | 64/64 · 416.58 · 524.19 |

本轮轻量检索 P50 由并发 4 的 13.34 毫秒升到并发 8 的 101.58 毫秒，约为 7.6 倍。当时是单 API 进程，检索缓存没有命中。并发下未命中查询集中执行可能放大等待，实验没有拆分数据库、线程和连接池耗时，仍无法确定涨幅由哪一项造成。计时阶段共 512/512 成功，HTTP 429、预期在途拒绝及意外失败各 0/512。预热与缓存探测另计。频率额度临时提高至 500，在途上限保持 8。该轮用于观察额度内短时负载，HTTPS 耗尽额度的数据保留在第六板块。

**混合缓存探测。** 70 个不同的账号、会议和查询组合逐一发出，再原样重放其中 30 个。100/100 成功，检索缓存共查 100 次，命中 0/100，API 和模型缓存均无读次数。修复前检索会查缓存，但仅在 Milvus 路径写入。这个结果保留为旧配置的基线。

修复后，配置为直接走 PostgreSQL 的检索可以写入非空结果。缓存只保存候选 ID 和分数，命中后回查 PostgreSQL 校验文档权限、软删除和当前正文。键同时区分检索模式、阈值和用户权限范围。复测先等待中文样本完成向量索引，再发 70 个不同请求并重放 30 个。最终成功 100/100，缓存命中 30/100（30%），30 个重放均命中。该数值对应固定重复比例和单进程缓存。加量复测的并发 4/8 检索 P50 分别为 41.40/96.99 毫秒。由于样本和索引前置步骤发生变化，历史 13.34/101.58 毫秒不能用来计算缓存带来的性能提升。

**队列。** 客户端在并发 4 和 8 时分别观察到最多 4 和 8 个已接单、尚未确认完成的任务。最后一次接单后约 271 和 268 毫秒观察到这一档全部完成。同期 RabbitMQ 共 95 批采样，文档主队列最大采样等待数为 4、未确认数为 1，向量主队列分别为 0 和 1。客户端等待时间包含轮询，采样数值可能漏过瞬时峰值，最老消息年龄未测。

复跑时使用本机 Conda 和已有依赖服务，在独立终端同时采样。脚本会创建测试账号、文档和任务，使用测试数据库。

```powershell
python scripts/bench_local_business.py --users 4 --concurrency 4 8 --requests 64 --warmup 8 --mixed-cache --output artifacts/business-load-warm64.json
python scripts/sample_local_queues.py --seconds 95 --interval 1 > artifacts/business-load-warm64-queues.jsonl
```

## 五、网关、部署与扩缩容

### 1. 这一部分解决什么问题

明确系统从哪里接请求，哪些组件需要一起启动，以及请求变多时该增加 API 还是 Worker。这样出了问题，可以先判断是入口、业务服务还是后台任务出了故障。

### 2. 当前方案

本机首发选择单机轻量模式。PostgreSQL 在宿主机运行，Redis 和 RabbitMQ 通过 Docker 提供，后端和 Worker 可从 Conda 启动。Compose 另提供容器部署方式，默认关闭 Milvus。本机演练使用仅绑定回环地址的临时 Nginx HTTPS 入口。证书由测试客户端显式信任，演练结束后清理。启动顺序是先确认 PostgreSQL、Redis、RabbitMQ，再启动 API 和 Worker，最后启动 Nginx 并检查就绪与任务消费。

Nginx 转发业务 API 和三个健康入口。账号、资源权限和 Redis 限流由后端检查。代理地址配置正确且受信时，后端才能按真实客户端 IP 限流。Redis、RabbitMQ 和数据库只需要供后端和 Worker 连接。

### 3. 一次请求怎样经过各层

> 浏览器访问 Nginx → Nginx 转发业务请求 → API 认证、限流并处理请求 → 需要后台执行时通过 RabbitMQ 交给 Worker → 客户端查询结果

启动时先确认三项基础依赖，再检查 API 就绪和 Worker 是否实际消费任务。HTTP 探针正常只能证明 API 的依赖检查通过，Worker 应另外用任务完成记录验证。

### 4. 当前亮点

- 已用真实后端验证 Nginx 转发就绪响应，依赖故障时保留 503 和请求 ID。
- SSE 响应已带有 Nginx 禁用缓冲的响应头。本机通过 Nginx 的 HTTP 演练使用固定延时测试服务，约 112 毫秒收到首个进度事件，约 1415 毫秒收到最终事件。
- Redis 和 RabbitMQ 的本机端口已收紧到回环地址。
- 临时 API 和 Worker 的启动、业务验收及退出已有一键脚本。

### 5. 当前边界

现有证据来自本机单实例。Compose 参考配置中的多个 Uvicorn 进程可以分别接请求，每进程的 Agent 在途上限分别计数。Redis 频率额度只有在共用同一 Redis 和键空间时才共享。进程内指标、文件检查点和本地上传路径也需要在扩实例前逐项核对。

增加 API 进程主要缓解入口处理压力，增加 Worker 才会改变后台消费能力。扩 Worker 之前需要核对 RabbitMQ 预取、任务幂等和数据库、GPU 容量。实际扩缩容和故障摘流目前没有验收记录。

### 6. 上线前还缺什么

本机 HTTPS 演练已验证证书、401/403、CORS 和就绪状态。可信代理限流用两组实际客户端和独立测试桶验证，同一 IP 前两次通过、第三次返回 429，另一 IP 仍通过，伪造的转发头未改变归属。模拟数据库探针失败时，就绪返回 503，存活返回 200，Nginx 仍转发业务请求。复测证明了这一入口策略。固定部署的证书生命周期、HTTPS 下的 SSE 首事件及负载均衡下的动态扩缩容仍待验收。

### 2 API + 2 Worker 本机验收

使用独立 Compose 项目和临时 PostgreSQL、Redis、RabbitMQ，两个 API 提供独立的回环端口。SSE 使用固定等待的合成 Agent 回包，认证、限流、HTTP 和连接管理走正式代码。

| 验收对象 | 实例 A | 实例 B |
| --- | --- | --- |
| API | 第 1 个检索请求 200，第 3 个 429。SSE 接纳 8 条，第 9 条 503 | 第 2 个检索请求 200。SSE 接纳 8 条，第 9 条 503 |
| Worker | 收到 1 个文档任务 | 收到 5 个文档任务 |

检索请求由同一账号按 A → B → A 发出，每窗口额度为 2。6 个任务 ID 各出现一次，6/6 均完成。两个实例同时持有 16 条 SSE，16/16 收到结束标记。实际并发上限还取决于流量如何分给实例。

### 复跑与留存

先依次启动临时的 PostgreSQL、Redis、RabbitMQ，再启动 API A 初始化数据库，随后启动 API B 和两个 Worker。先用当前源码构建共享验收镜像，再用本机 Conda 运行两个验收脚本。输出目录为 artifacts。

# 等 API A 的 /ready 返回 200

### 本机 HTTPS 复测

四账号、并发 4 和 8、每档连续发流约 20 秒。八档共 5,184 次请求，成功 4,000/5,184（77.16%），轻量检索触发限流 1,184/5,184（22.84%），意外失败 0/5,184。延迟仅从成功响应计算。RAG 两档共享同一分钟的额度，后一档成功吞吐受限流影响。并发 8 时，Agent、SSE 和上传到向量子任务完成的成功耗时 P95 分别约 319、417、670 毫秒。

RabbitMQ 同步采样 109 批。文档主队列的采样最大等待数为 2 条，最后繁忙样本后约 1.70 秒的下一次采样两条主队列均清空，死信数量未增加。独立 5 秒档缓存窗口中，轻量检索缓存记录 208 次未命中、0 次命中，API 和模型缓存均没有产生计数。以上数据对应测试配置，每档分钟级运行和首发常态命中率仍需另测。

## 七、入口：解析、转写与路由

入口先弄清三件事：用户想做什么，哪些资料有权使用，哪些内容只能当证据。文件上传、音频任务和 Agent 问题是不同入口，共用身份和资源边界。

| 入口 | 处理方式 | 交给下一步的内容 |
|---|---|---|
| 文档 | 核对大小、扩展名、MIME 和实际结构，解析支持的文本、PDF、Word 和表格 | 文档正文、解析来源和索引所需的片段 |
| WAV 音频 | 验证 WAV 后入队，Worker 执行本地转写，整理时间戳、说话人标记和安全状态 | 版本化转写与发言记录，供复核和检索 |
| Agent 问题 | 整理身份、任务、预算和来源，抽取核心目标与约束，再判断走问答、纪要、待办还是规划执行 | `InputEnvelope`、`TaskAnchor` 和路由决定 |

`InputEnvelope` 是项目自己的 `input.v1` 请求结构，把身份、资源范围、附件、来源、风险和预算放到同一处。`TaskAnchor` 单独保留当前目标、关键约束与任务标识。检索结果、历史对话和工具输出仍按各自来源标记，工具报错走失败状态。可疑证据会标记或隔离，下游按状态使用。

Agent 普通、流式和批量入口先认证并检查 Redis 额度，再初始化模型和向量服务。无身份和超额请求分别走 401 和 429，不占用后续依赖。

路由冻结集 v4 在同一批 100 条盲写样本上比较纯规则、规则加语义相似度、规则加本地 BGE-M3 意图头。准确率分别为 46%、74%、93%，P95 分别约 0.4、55.7、82.7 毫秒。去除近重复后保留 84 条，意图头方案准确率仍约 93%。这是路由选对的比例。

**早期本地分类器对照。** 另一组 60 条留出样本中，本地分类器和规则的任务准确率分别为 60.0% 和 56.7%，P95 约为 1.37 秒和 0.1 毫秒。小幅准确率收益伴随明显时延，因此默认采用规则。该组结果与上面的 BGE-M3 路由 v4 分开看。

ASR 有两项单条验证。公开 WAV 的 GPU 冒烟记录了 CER 为 0。本机队列验证确认转写任务完成并写入 1 条发言，保留时间戳和说话人标签，纪要仍为待复核草稿。两项分别验证转写和落库链路。

## 八、上下文与记忆

系统需要同时回答三个问题：这轮以什么为准、追问时从哪里取历史、任务暂停后从哪一步恢复。

- **上下文组装**：按当前任务选择问题、证据和历史，为每项记录来源、长度、优先级及截断情况。上下文清单留下引用和哈希，方便检查哪些材料进过模型。
- **会话和任务空间**：`thread_id` 定位会话线程，`run_id` 标记单次运行，`task_id` 表达业务任务，`task_namespace` 隔开同一会话里不同任务的历史和事实。
- **短期状态与恢复**：最近几轮对话用于追问；Checkpoint 保存可恢复的工作流状态；人工确认另有快照，用于核对同一用户、运行和待执行动作。
- **长期事实**：显式写入 PostgreSQL，保留来源与范围。新事实能替代同一范围的旧版本，也能把不确定的冲突分开记录。事实和索引事件同事务写入，后者由 outbox 衔接异步投影。当前运行口径以 PostgreSQL 为事实源，独立索引投影保持关闭。

长会话实验使用 8 场真实会议改写的 12 段会话，每段 10–13 轮。比较全量拼接、组装 v1 和组装 v2。相同预算下，v2 让历史条目按与当前问题的词面相关度竞争位置，并减少重复标签。输入 Token 估算中位数为全量 645、v1 726、v2 584，关键事实保留由 34/41 到 36/41。这测的是**组装结果和事实是否还在**，计数采用固定估算方法。

离线贯穿测试让同一会话切换两个任务，再回到第一个任务追问。测试检查最终组装文本，确认新任务保留预算数字和禁止项，第一个任务的历史只在回到其任务空间时读到。

## 九、召回

> 确定用户和会议范围 → BM25 找关键词，Dense 找语义相近片段 → 加权合并，需要时重排 → 回查 PostgreSQL 过滤权限和软删除 → 给生成环节返回片段及引用位置

Milvus 查候选时，PostgreSQL 仍负责最终正文和权限。检索缓存按查询条件与 ACL 隔离，缓存命中后也重新回查。轻量部署可使用本地替代向量和关键词检索。详细权限边界见第一板块。

上传后如果正文已保存但索引未建成，文档显示“索引失败”，正文仍可读取。可通过已有文档任务入口重新处理。Worker 发现有正文却没有分块时会重建，并在重建仍失败时记录任务失败。

| 实验 | 数据和对照 | 可以说明什么 |
|---|---|---|
| 会议内排序基线 | 40 条 QA、20 场目标会议。已知会议 ID，规范化去重后比较 BM25、Dense、Hybrid 和 Hybrid + Reranker | 在该发言级口径下 Hybrid 的 Recall@5 最高，BM25 的 MRR 最高。按会议聚类做 Bootstrap，置信区间反映同一会议下问题相关 |
| 分块及等字数对照 | 同 40 条 QA，比较单发言和约 300 字块，均取 Top-5。再给发言级对照相同字符额度 | 300 字块 Hybrid 的 MRR 约 0.856。等字数时，块的证据召回约 0.293，发言对照约 0.265。独立记录了 Top-5 理论覆盖上限 |
| 全库离线检索 | 34 场会议、1626 块同池，查询不给会议 ID。20 条具体议题题与 20 条依赖“这场会议”指代的摘要题分开 | 具体议题题的 Top-5 会议命中为 Hybrid 19/20、加重排 20/20，证据召回约 0.333、0.379。用相同融合策略离线跑，未走线上 API |
| 检索策略发布门禁 | 40 条 QA 按会议隔离开发与验证，开发集筛权重，验证集复验 | 纯 Dense 使开发集 nDCG@5 从 0.6428 升到 0.6745。在隔离的 11 条验证题中，nDCG@5 从基线 0.7204 降到 0.5875，7 条退化。门禁拒绝，保留原有 0.3/0.7 融合权重。正式结果见 policy_optimization_real_v1.json |

会议命中、证据覆盖量和首条相关结果的排名分别计量。发言级实验中 Hybrid 的 Recall@5 最高，BM25 的 MRR 最高，重排后的 Recall@5 在四种方法中最低。发言级会议内对比中，BM25、Dense、Hybrid 和 Hybrid + Reranker 的 Recall@5 分别为 0.0563、0.0622、0.0732、0.0521，MRR 分别为 0.4326、0.3919、0.3958、0.3706。按会议聚类重采样 2000 次，Hybrid 的 Recall@5 估计区间约为 0.043–0.100。该区间用于描述同一评测口径下的不确定性。

## 十、生成

问答拿到有权限的片段后才组织回答和引用。轻量模式可只返回证据；模型生成不可用时，系统仍可以把已找到的片段交给用户。Agent 的纪要、待办和约束走各自的结构化输出路径，下游按 Schema 检查并按需要修复或返回失败。证据引用要对应模型本轮实际看到的片段。

RAG 响应保留本轮检索证据列表，同时单独返回答案实际展示的引用。生成答案只能引用上下文清单中实际纳入的片段。出现越界编号或引用被截掉的片段时，返回真实检索摘录并标明降级。合法编号只能证明证据出现在本轮上下文，内容是否支持论断另由忠实度评测核对。

- **冻结候选规范化**：28 场会议、100 条单人复核任务，其中 QA 40、待办和约束各 30。Qwen 基线和 Opus 5.5 + Prompt v2 均完成 100 条、JSON 有效率 100%。QA 引用 Precision 从 97.5% 到 100%。在人工作为正例保留的候选中，约束和待办 F1 分别从 0.158 到 0.737、0.139 到 0.498。模型和提示词同时变更，因此记录的是组合效果。是否需要保留候选与如何填字段属于规范化评测，和从全文发现候选分别看。
- **提示词与模型选择**：Opus 的提示词开发、开发留出报告比较 v1、v2、v3，v2 随冻结配置进入 100 条运行。Sonnet 5 另有同规模评分报告，可与效果和时延一起对照。
- **引用和忠实度**：引用评分匹配人工复核的证据 ID。另用两个评判模型对 40 条 QA 做论断级盲评，两位评判给出的“全部论断有依据”比例分别为 65%→85%、85%→92.5%，注入无关句的探针均被识别。引用匹配和论断盲评衡量不同内容。
- **四种召回的生成链路验证**：每种方法复用 10 条 QA，共 40 次生成请求。同模型、同提示词、每题只给 Top-5，引用限定在这 5 段。该组用于验证从排序到引用的链路。

提示词开发留出集的约束部分有 25 条应保留、25 条应拒绝。v1、v2、v3 在这两组上的 F1 分别为 0.34/0.96、0.84/0.88、0.88/0.76，最终冻结 v2。Sonnet 5 的 100 条对照同样全部完成，JSON 有效率为 100%，P95 约 4.70 秒。

**四路生成冒烟。** BM25、Dense、Hybrid 和 Hybrid + Reranker 各用同一批 10 个问题运行一次，共 40 次请求。40 次均返回合法 JSON，其中 29 次回答「无法从会议片段确定」。这组小样本确认了检索结果可以接入生成。问答质量排序需要更完整的样本和答案复核。

生成侧的忠实度需要结合可见证据一起读。第十四板块列出证据缺口与人工盲审的逐题交叉结果，以及探针与自然错误的区别。

## 十一、工具执行

模型提出行动，后端负责决定能不能执行。注册表限定可用工具和参数，执行前检查权限、风险、用户授权和依赖；高风险写操作保存确认快照后暂停。恢复时校验确认人、Agent 运行和待行动作，再使用幂等记录约束重复写入，并把执行结果写进审计。工具失败按失败结果传回编排层。

本机演示验证了确认门禁，PostgreSQL 集成测试验证了审计持久化及幂等。Jira 的工具适配和真实 Jira 站点的操作验收是两个范围，现有演示覆盖本地受控执行。

工具获准后、恢复前如果用户失去写权限，后端会拒绝领取确认点，也不会创建执行节点。拒绝原因和确认 ID 记录在服务日志中。

工具规划冻结留出集共 40 条，包括 16 条写请求。Opus 5.5 的主工具选择准确率 1.00、参数准确率约 0.84，写操作确认召回 16/16，未经确认的写入 0/40；复跑仍确认 16/16。参数正确率以主工具命中的样本为分母。Sonnet 5 也在同一留出集跑过，比较时同时看工具覆盖、确认召回和延迟。该报告记录的是规划与确认行为。同组 Sonnet 5 确认了 16 条写请求中的 6 条，规划 P95 约 15.90 秒。同组 40 条 Opus 规划样本的首跑 P95 为 70.57 秒，复跑为 17.69 秒。差异原因尚未隔离，模型选择同时参考门禁和两轮时延。

## 十二、编排与异步

| 通道 | 负责什么 | 如何处理失败 |
|---|---|---|
| LangGraph 单次运行 | 输入与路由后选择简单问答、纪要、待办或规划执行。规划记录步骤、依赖和约束，校验节点决定结束、拒绝或修复 | 预算和步骤有上限。按依赖分波次执行，失败率达到阈值后停止后续波次。事实、工具错误和待执行计划有各自状态 |
| RabbitMQ 后台任务 | 文件和音频耗时工作由 API 接单，Worker 拉取，调用方再按任务 ID 查状态。文档任务可派生向量子任务 | 发布确认、预取与队列上限约束积压；按策略延迟重试，耗尽进死信，授权后可重发 |
| HITL 暂停与恢复 | 保存待确认动作、运行和身份范围，等待用户批准或拒绝 | 恢复前复核上下文与预算，再从待执行位置继续 |

入口 Redis 限流、Agent 在途限制、单次运行预算和 Worker 预取分别管不同层。RAG 生成失败可保留证据，Model API 的有限重试仍受预算约束，外部非幂等写操作按工具策略处理。完整阈值见第二板块。

SSE 客户端断开时，响应生成器取消后台任务，并在有限清理窗口内等待退出。连接结束后在途名额可供下一条请求使用。本机以真实 HTTP 和合成 Agent 验证了在途上限为 1 时，并发请求收到 503，断开后下一条流可进入。

证据包括真实 RabbitMQ 毒消息重试到死信、Redis 幂等与任务领取、HTTP 创建任务到 Worker 完成的本机闭环。第四板块的 44 批 RabbitMQ 采样对应压测期间的真实 Broker 状态。

### 进程强杀验证

历史强杀测试中，RabbitMQ 已重投，但旧 Redis 领取锁默认保留 3,660 秒。重投消耗完两次业务失败重试，任务进入死信。

现在使用默认 30 秒的可续期领取锁。Worker 工作期间每 10 秒尝试续期，只有持有当前令牌的 Worker 可以续期或释放。重投遇到有效领取锁时，在 RabbitMQ 延迟队列等下一次投递，保留业务失败重试次数。领取锁失效时，原 Worker 会尝试取消还在进行的处理。

复测在原 Worker 发出向量子任务之后、父任务写入完成之前强杀，Broker 有 1 条未确认的父任务消息。另一 Worker 观察到 7 次投递，其中等锁期间的尝试未实际领取。父任务记录共 2 次领取，强杀后 32.41 秒自动完成，并复用已经发出的同一个向量子任务。该结果覆盖本机单 Worker 进程退出和这一个处理断点。

API A 有 SSE 在途时强杀，旧流断开，API B 仍通过就绪查询。A 启动后在途数为 0，新连接能完成。重启验证覆盖名额重新可用，旧流不会自动续传。

## 十三、可观测与成本

排障时，入口用请求 ID 和响应状态找对应日志；Agent 节点 Trace 用于看路由、检索和执行分别耗了多久；任务状态与 RabbitMQ 用于看发布、重试和死信。开发 Trace 有界且按进程保留。工具审计单独记录有副作用的动作。探针、日志汇总和队列告警的运行证据见第三至第六板块。

**一次模型调用怎样记账。** 调用前对输入、输出预留和安全余量估算，检查模型上下文、节点和运行预算。调用后用供应商实际 usage 回写；拿不到 usage 时保留预留口径。重试消耗也记账，确认恢复沿用原运行预算。响应中的 `budget_ledger` 是运行级预算快照，`context_manifest` 记录证据装配，不附带原文。

**已量到的成本与时延。** 100 条候选规范化运行，Qwen 报告总 Token 37,171、P95 3.88 秒，Opus + Prompt v2 总 Token 857,911、P95 7.80 秒。应连同供应商、提示词和统计来源一起读。40 条 Opus 工具规划首跑与复跑延迟见工具执行板块。独立 vLLM 的首 Token、总延迟和吞吐见第四板块。这里记录 Token 和耗时，货币成本须另按实际计费核算。

**工具规划延迟诊断。** 同一批 8 条开发样本上，Opus 并发 1 和 4 的单请求 P95 分别为 21.81 秒和 21.96 秒，Sonnet 串行为 15.01 秒。另选 7 条尾部样本让 Opus 串行复测，P95 为 17.47 秒。尾部组按历史耗时筛选，这个 P95 只描述这 7 条。

| --- | --- | --- |

#### 忠实度判定与归属断言

- 给定片段可以核实更正时，该断言计为有依据。额外音频核实应登记证据来源，供单独分析。

- 答案明确写成「转写为 A，疑为 B」时，分别核对转写事实和纠错假设。A 能在片段中核实，B 作为显式假设单列，不计为已证实的断言。若答案随后把 B 当成已确认事实，按静默采用未经核实的更正处理。
