# 双轮完整审查与真实演示

> **历史证据记录**：本文证明的是 2026-08-26 本机 Compose、测试和固定 Demo 的运行情况，不等于真实长会议效果、真实 LLM 质量或真实 Jira 外部写入已经验收。当前证据边界以[证据与限制（大白话）](../证据与限制_大白话.md)为准。

> 审查日期：2026-08-26。目标是把“代码看起来可用”推进到“核心能力可重复演示”，同时保留证据边界，不承诺形式化意义上的零缺陷。

## 1. 审查范围与方法

两轮审查使用不同侧重点，避免只重复跑同一组测试：

1. 第一轮以静态边界和契约为主：逐项检查公开 Router、认证授权、缓存隔离、Agent 状态、输入校验、异常输出、RAG 检索、Worker 调用契约和前端权限入口，并补单元/API/契约测试。
2. 第二轮以真实运行和竞态为主：重建 Compose，通过真实 HTTP 依次执行注册、会议、文档、RAG、待办、RabbitMQ 父子任务和跨部门越权；再并发执行两条业务链路，配合 PostgreSQL、Redis、RabbitMQ 集成测试、日志和队列状态定位动态问题。

## 2. 第一轮发现与修复

| 类别 | 发现 | 处理 |
|---|---|---|
| 业务对象权限 | 会议、文档、待办的部分读接口缺少用户边界，存在 IDOR 风险 | 统一为管理员、所有者/负责人、同部门或公开对象的明确规则；写操作限制为管理员或对象管理者；只读角色禁止写入 |
| 缓存隔离 | 会议与待办缓存键未完整包含用户作用域 | 缓存键加入用户作用域，并在变更后失效相关缓存 |
| 管理接口 | Feedback、Bad Case、Trace 的读写权限过宽 | Feedback 提交保留给认证用户，其余治理与 Trace 接口限制为管理员；修复动态路由冲突 |
| Agent 隔离 | 全局 AgentService 会被请求级依赖覆盖，会话记忆未完整包含用户 ID | AgentService 改为请求级；仅共享有界 LRU 会话存储；thread ID 使用 `user:session:conversation` |
| 推理信息 | API/SSE 可能返回内部 thought/reflection | 对外只返回安全进度字段和业务结果；异常统一为通用消息 |
| 前端凭证 | 登录页调试日志输出了访问令牌前缀 | 删除令牌与 localStorage 调试输出，避免浏览器日志泄漏凭证片段 |
| 配置与校验 | 无 LLM Key 时连检索模式也无法构造服务；bcrypt 超长 UTF-8 密码可能被静默截断 | LLM 客户端改为真实生成时才要求 Key；密码按 UTF-8 72 字节边界拒绝；补生产 CORS、ID 和批量边界 |
| RAG 主链 | BM25 引用了不存在的 `async_session`，配置探测失败会使事务中止；全文索引与查询表达式不一致 | 使用 `AsyncSessionLocal`；安全探测 `pg_ts_config`；按块正文构造 `tsvector`；初始化固定 `simple` GIN 表达式索引 |
| Worker 契约 | VectorWorker 调用了不存在的 `EmbeddingService.embed_chunk()` | 实现按 chunk 读取、向量生成、持久化及真实 fallback 模型标识，并补回归测试 |

## 3. 第二轮发现与修复

### 3.1 Worker 未初始化 Redis

真实文档任务首次进入 Worker 后一直停留在 `pending`。根因是 Web 进程初始化了 Redis，独立 Worker 进程没有初始化；Worker 读取任务状态时实际对 `None` 调用 `get`。

处理：

- Worker 启动前强制初始化 Redis，失败则直接退出，不以“已启动但无法工作”的状态降级；
- 退出时关闭 RabbitMQ 和 Redis；
- TaskQueueService 在未初始化 Redis 时给出明确异常；
- 状态回写回调异常不再破坏已经完成的 RabbitMQ ACK/重试确认流程。

### 3.2 新上传文档默认公开

上传接口没有公开性参数，但模型默认 `is_public=True`。因此，挂在私有会议上的新文档可能被其他部门读取。

处理：新文档默认私有；上传者仍可通过元数据更新显式设为公开。真实演示验证跨部门详情为 403，列表中也不存在该私有文档。

### 3.3 快速消费者覆盖竞态

在统一 Demo 和并发业务流中，向量任务已经被 Worker 执行并 ACK，但 Redis 状态偶发停留在 `pending`。时序如下：

```text
publisher 保存 pending → publish → consumer 完成并写 completed
                                 → publisher confirm 返回后又用旧对象写 pending
```

处理：创建和重新发布任务都在 publish 前保存发布意图；confirm 成功后只读取 Redis 最新状态，不再回写旧对象。补两个确定性测试，让模拟消费者在 confirm 返回前完成；随后两条并发 HTTP 业务流均通过，父任务和向量子任务都为 `completed`。

### 3.4 演示契约收敛

- 文档任务接口不再接受客户端提供的服务器 `file_path`，只使用数据库中的受管路径；
- 新增 `scripts/demo_http_business_flow.py`；
- `scripts/run_fixed_demos.py` 统一运行 HTTP 主链、队列恢复、公开 WAV ASR、LoRA 抽取四项 Demo。

## 5. 仍然必须诚实保留的边界

当前证据足以说明本机核心链路能真实运行，但“没有任何 bug”无法通过有限测试证明。以下部分仍不能写成已完成：

- Compose 轻量镜像没有 pgvector、Milvus、本地 Embedding/Reranker，RAG 真实使用 PostgreSQL 轻量检索与明确标记的 fallback；
- 未配置真实 LLM API Key，因此本轮没有验证外部模型生成质量与计费链路；
- 未提供真实 Jira/飞书账号，外部写工具只验证了策略、HITL、幂等、审计和客户端契约；
- ASR 是公开单句，不代表多人会议 CER/DER；
- LoRA 演示输入与评测数据是项目自编合成样例，不外推真实业务指标；
- 生产 TLS、Secret Manager、备份恢复、多节点高可用、真实容量和镜像 SBOM 仍需目标部署环境。

因此当前结论是：除真实账号、真实业务数据和生产环境验收外，本仓库内可执行的核心工程任务已经完成双轮审查、修复和可重复演示；后续重点应转向用户亲自复现、读懂关键代码并练习讲解，而不是继续无边界扩功能。
