# 阶段 7：深度瘦身与 AI 应用岗位聚焦

日期：2026-08-26

## 1. 为什么这次不是“再关几个开关”

阶段 0-6 已经建立了 RAG、Agent、RabbitMQ、ASR、LoRA/QLoRA、部署和 CI 证据，但仓库仍保留大量可选框架。它们带来三个问题：

1. 代码阅读时无法判断哪条链真正运行；
2. 测试数量很大，但不少测试只验证替身或已经退出主链的模块；
3. README、面试稿和简历继续引用 Sparse/RRF、KG、MCP、长期记忆、Prometheus 及不可复现数字。

本阶段采用更严格的判断：一个模块必须直接服务当前 AI 应用主链，或拥有真实数据/外部系统证据；否则直接删除，不保留“默认关闭”的实现。

## 2. 保留边界

```text
身份与文档 ACL
→ 会议 / 文档 / 待办事实数据
→ 文档或 WAV 音频入库
→ RabbitMQ 可靠任务
→ 说话人感知分块
→ BM25 + Dense + 加权融合 + Reranker
→ RAG 引用与降级
→ LangGraph 业务路由 / Tool Agent
→ Schema / ToolPolicy / HITL / ToolExecutor / 审计
→ Bad Case / 离线评估 / 真实节点 Trace
```

ASR 和 LoRA/QLoRA 仍是独立重型环境，不进入 Web 镜像。

## 3. 删除清单与判断依据

| 删除组 | 代表内容 | 删除原因 |
|---|---|---|
| KG | KnowledgeGraph、Neo4j、Graph API/页面、迁移脚本 | 不进入正式检索，缺真实收益评测 |
| MCP | Client/Server/Discovery、飞书/GitHub/Notion/Jira MCP 示例 | 没有真实 MCP 闭环；正式 Jira 已是 REST v3 工具 |
| 通用 Agent 框架 | Multi-Agent、通信总线、Prompt 市场、动态工具发现、ReAct/CoT 节点 | 主链不注册，增加路由和讲解复杂度 |
| 查询实验 | HyDE、Multi-Query、Step-back、Sparse、RRF、策略 B/M | 没有冻结数据证明收益 |
| 多模态骨架 | 图片、视频、远程 Vision/Whisper 网关 | 只有接口没有真实业务证据；保留已跑通 FunASR |
| 多层记忆 | PG/Redis/向量长期记忆、统一门面、反思记忆、迁移 | 三套数据源和缓存难以说明一致性；普通回答不应自动沉淀为事实 |
| 重复评估 | RAGAS、DSPy、Agent Benchmark、RAG Regression、多套 API | 统一离线命令已经覆盖当前指标；旧实现存在伪精度风险 |
| 通用后台 | 动态配置、用户后台、模板/成本/性能/测试 API | 非 AI 应用岗位核心，也没有前端真实使用 |
| 重复观测 | AgentMonitor、Observability、Performance、Prometheus/Grafana | 三套状态口径不一致，前端还调用已不存在接口 |
| 通用工程展示 | Fault Tolerance 框架、Locust 页面和脚本 | 与当前主链重复或没有真实容量基线绑定 |
| 孤立数据与脚本 | 434 份旧会议语料副本、RRF 结果、固定 0.8 基线、Windows 硬编码导入脚本 | 当前测试/评估均不引用，旧结果不可由正式链路复现 |
| 通用文本功能 | 文本计数/格式化 Agent 工具、独立 `text-process` API | 不是 AI 应用主链；底层清洗仅作为文档/ASR 入库内部能力保留 |
| 停用异步 Agent | 默认关闭的 Agent Worker、队列和开关 | 无 API 创建入口，与同步 Agent 主链重复 |

同时删除所有对应测试、配置项、依赖、Compose 服务和前端入口，避免留下“幽灵能力”。

## 4. 关键收敛结果

### 4.1 Agent

Agent 图固定为：

```text
route
→ injection/rejection/risk/confirmation
→ retrieve 或确定性业务节点
→ complex plan → tool risk → execute → replan
→ validate → repair（有上限）
```

`create_agent_graph()` 只有一个编译入口，不再通过大量 Feature Flag 组合图结构。复杂度 C/A 只决定是否进入计划执行，不再注册独立 ReAct/CoT 循环。

### 4.2 记忆

原记忆代码覆盖进程内、Redis、PostgreSQL、Milvus、反思样本和迁移。现在只保留每个 session 最近 10 轮的固定窗口：

- 只用于连续追问；
- 不持久化、不跨用户画像；
- 超限丢弃最早轮次；
- 服务重启即清空；
- 不把普通模型回答写成长期事实。

会议事实长期保存仍由 Meeting、Document、Todo 等业务表承担，而不是名为 Memory 的第二事实库。

### 4.3 RAG

正式检索只有策略 A：

```text
PostgreSQL 关键词召回 + Dense 召回
→ 按 chunk_id 去重
→ 0.3 / 0.7 归一化加权
→ BGE Reranker
→ PostgreSQL 正文与 ACL 回查
```

融合服务从支持多种未验证策略的大文件，收敛为只实现加权融合与统一精排的单一模块。非 A 策略会直接报错，而不是静默执行另一条路径。

### 4.4 Trace

删除三套重复观测后，只保留一套有界进程内 Agent 节点 Trace：

- 节点名和类型；
- 真实耗时和成功/失败；
- 重试次数；
- 截断后的输出或错误；
- Token/成本只有真实采集时才写入，默认不伪造。

它适合本地调试和演示，不冒充分布式持久化观测平台。

## 5. 规模变化

| 指标 | 瘦身前 | 瘦身后 | 变化 |
|---|---:|---:|---:|
| 代码文件 | 240 | 147 | -93（-38.8%） |

减少行数不是独立目标。真正的验收是：正式主链更短，配置没有死开关，前端不再调用已删除接口，测试只覆盖仍存在的行为。

零外部依赖契约：

```bash
cd backend
python -m unittest \
  tests.contracts.test_stage0_boundaries \
  tests.contracts.test_rag_mainline_contract -v
```

结果：`12 tests, OK`。

前端：

```bash
cd frontend
npm test -- --run
npm run build
```

结果：新版 SSE 分片、多事件和尾帧测试 `3 passed`，生产构建通过。

受当前执行沙箱禁止创建线程影响，FunASR 异步包装和 FastAPI `TestClient` 不能在该沙箱中完整运行；契约、Agent、分块与全部单元测试为 `184 passed, 1 deselected`，其中单元测试 `49 passed`，FunASR 同步真模型冒烟通过。完整套件交给 GitHub Actions 在正常线程环境复核。

文档口径也已二次复核：README、API、路线总表和本文表达当前状态；阶段 0-6 文档保留当时问题与运行数据，并显式标注历史快照/证据边界。已删除的 KG、MCP、Prometheus/Grafana、旧检索分支和管理 API 只能出现在“删除决策”或“历史快照”语境，不再作为当前配置与启动指南。

仓库中保留的 `.docx` 属于用户原始材料，没有作为当前能力和指标的权威说明；以 README、本记录、可执行测试和本地忽略的脱敏简历 Markdown 为准。简历和面试准备文档按 `.gitignore` 继续不推送，避免个人材料意外公开。

## 7. 技术掌握检查题

完成本阶段后，应该能脱离代码回答：

1. 为什么业务事实表比“万能长期记忆表”更容易保证一致性？
2. 为什么没有离线数据时，HyDE/Multi-Query 不能仅凭理论优势进入默认链路？
3. 加权融合为什么要先在各召回源内归一化？相同 chunk 命中两路时如何合并？
4. Reranker 的候选池为什么必须大于最终 `top_k`？
5. LangGraph 静态业务图与通用 ReAct 循环分别适合什么任务？
6. 为什么高风险写工具必须经过 Schema、Policy、HITL、Executor 和持久审计？
7. RabbitMQ 的 publisher confirm、manual ACK、重试队列、DLQ、幂等键分别解决什么失败？
8. 进程内 Trace 能证明什么，不能证明什么？
9. 合成 LoRA 指标为什么不能写成真实会议效果？
10. 如果未来恢复 MCP 或 KG，最小业务问题、数据和验收门槛分别是什么？
