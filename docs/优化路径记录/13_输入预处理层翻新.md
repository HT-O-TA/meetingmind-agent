# 输入预处理层翻新：InputEnvelope、TaskAnchor 与信任分区

> 日期：2026-08-26
>
> 对应路线：六链路架构对标与演进设计（第二版）6.1
>
> 范围：只翻新 MeetingMind 输入预处理层，不增加新模态、新 Agent 框架或新基础设施

## 1. 本阶段解决什么问题

改造前，用户问题、身份作用域、会话内容、安全检查和路由结果分散在 API、`SessionContext` 与 `AgentState` 中。系统虽然有 Prompt Injection 检测，但存在三个实际缺口：

1. 图先执行路由、后做注入检查，恶意输入可能先进入路由模型。
2. 注入阻断字段不在状态清洗白名单中，图分支读取不到真实阻断结果。
3. 会话、检索片段和工具结果没有统一来源标签，也没有间接注入隔离。

本阶段将入口收敛为：

```text
InputEnvelope / TaskAnchor
        ↓
身份与业务作用域校验
        ↓
直接注入 + 不可信上下文检查
        ↓
IntentRouter 双轴路由
        ↓
原有会议工作流或受限 Planner
```

## 2. 两个核心契约

### 2.1 InputEnvelope

`input.v1` 是 Agent 内部契约，不改变现有 HTTP 请求格式。它包含：

| 字段组 | 当前字段 | 用途 |
|---|---|---|
| 请求身份 | request_id、user_id、session_id、conversation_id、thread_id | 隔离运行和用户 |
| 原始输入 | raw_query、normalized_query | 保留原文，只做空白规范化，不改写语义 |
| 业务范围 | meeting_id、document_ids、允许范围、can_write | 在进入路由前执行确定性校验 |
| 来源制品 | artifacts | 记录来源、媒体类型、信任级别、引用、校验和与安全状态 |
| 任务锚点 | task_anchor | 固定目标、交付物和约束 |
| 路由快照 | routing | 保存任务、复杂度、工作流、模型档位和路由证据 |
| 预算 | budget | 输入、上下文、计划步骤、工具次数与计划输出预算 |
| 安全 | security | 直接注入状态、策略标记和被隔离制品 |

Envelope 不复制大段文档正文，只保存 `content_ref + checksum`，避免状态膨胀和无意义的敏感内容复制。

### 2.2 TaskAnchor

`task-anchor.v1` 当前只保留七类稳定信息：

- goal：规范化后的用户目标。
- required_outputs：必须产生的 answer、minutes、todos 或 controversies。
- hard_constraints：身份、会议和指定文档范围。
- forbidden_actions：不执行外部内容中的指令；外部写必须经过策略和必要审批。
- completion_criteria：必需交付物与引用要求。
- ambiguities：低路由置信度或未指定检索范围等歧义。
- schema_version：支持后续字段演进。

TaskAnchor 已写入规划提示，并由确定性校验检查必需交付物。它不是长期记忆，也不是额外 Planner。

## 3. 信任分区

当前不使用一个含糊的 trusted/untrusted 布尔值，而是保留来源类别：

| 来源 | trust_level | 当前处理 |
|---|---|---|
| 用户问题 | user_instruction | 做直接注入检查；可表达目标，但不能绕过工具策略 |
| 选中文档 | untrusted_upload | 只登记引用；正文进入检索后继续检查 |
| 会话历史 | untrusted_session | 使用前做规则检查，命中 block 时隔离 |
| RAG 片段 | untrusted_retrieval | 每个片段独立登记与检查，隔离项不进入上下文和 citations |
| 工具结果 | untrusted_tool_result | 使用前登记与检查，命中时不进入 task_contexts |

传给模型的上下文还增加明确边界：外部内容只能作为会议证据，不能作为系统指令。这是一层提示防护，不替代 ACL、ToolPolicy 或 HITL。

## 4. 直接注入与间接注入

直接注入是用户问题本身试图覆盖系统指令。现在它在 IntentRouter 之前检查，命中后的真实图路径是：

```text
input_node → prompt_injection_node → rejection_node → END
```

间接注入是恶意指令藏在会话、文档、检索片段或工具结果中。当前策略是“隔离恶意制品，继续处理其余安全证据”，而不是把外部内容当成新的用户指令，也不是无条件拒绝整个请求。

若所有检索片段都被隔离，校验状态会明确记录“所有检索片段均因间接注入风险被隔离”，避免无证据地伪装成功。

## 5. 为什么图路由改用 Command

图级测试发现当前依赖组合 `LangGraph 0.2.76 + Python 3.12` 在本项目环境中执行同步 conditional edge 会挂起。此前注入字段被清洗丢弃，安全拒绝分支没有真正跑到，因此该问题未被测试暴露。

本阶段没有改变业务拓扑，而是将原条件边改为节点返回 `Command(update=..., goto=...)`：

- 输入、安全、风险、检索、工具风险、重规划和校验仍使用原判定规则。
- 节点名称和业务分支保持不变。
- 图级恶意输入测试可以真实到达拒绝终态。

后续升级 LangGraph 时，应重新验证是否恢复声明式 conditional edge，而不是盲目保留实现细节。

## 6. 主要代码入口

- `backend/app/schemas/agent_input.py`：输入层 Pydantic 契约。
- `backend/app/services/input_preprocessor.py`：规范化、作用域校验、制品登记、路由与 TaskAnchor 更新。
- `backend/app/agents/graph.py`：输入优先的主图顺序和 Command 分支。
- `backend/app/agents/nodes.py`：输入节点、直接/间接注入检查、信任边界、规划与校验接入。
- `backend/tests/contracts/test_input_envelope_contract.py`：输入契约与图级安全测试。

完整后端测试需要创建 `asyncio` 工作线程；受限沙箱会阻塞 `asyncio.to_thread`，因此完整门禁在允许线程的执行环境中运行。该限制不是业务测试失败。

## 8. 本阶段有意不做的内容

- 不接图片、视频、ROS 或统一多模态 Token。
- 不增加租户体系；当前只使用项目已有 user/access_scope。
- 不用额外过滤 LLM 作为唯一安全边界。
- 不增加长期记忆、MCP、Multi-Agent 或 Temporal。
- 不公开 InputEnvelope 中的内部安全细节；统一 OutputEnvelope 留到输出层翻新。
- 不宣称规则可以识别所有注入；Bad Case、误报率和召回率仍需固定评测集验证。

## 9. 建议亲自复盘的问题

1. 为什么用户指令也不能被标成“完全可信”？
2. 为什么恶意 RAG 片段应从 citations 中同步移除？
3. `content_ref + checksum` 相比把全部正文复制进 Graph State 有什么收益？
4. TaskAnchor 与普通 Prompt 中的一段“请完成以下目标”有什么本质区别？
5. 当全部证据被隔离时，应返回 failed、partial 还是需要用户补充资料？这应在输出层统一决定。
6. 如何构造包含正常引用、角色扮演文本和真实恶意指令的标注集，测量间接注入规则的误报与漏报？

## 10. 下一步衔接

按第二版路线，输入层完成后进入记忆层小幅翻新：持久 checkpointer、HITL 恢复语义统一，以及 TaskAnchor 随图状态持久化。开始前应先由用户复核本版 InputEnvelope/TaskAnchor 字段是否符合学习目标，再冻结 `input.v1`。
