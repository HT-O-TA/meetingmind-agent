# 输入预处理层翻新：InputEnvelope、TaskAnchor 与信任分区

> 日期：2026-08-26
>
> 音频证据生命周期续改：2026-08-27
>
> 对应路线：六链路架构对标与演进设计（第二版）6.1
>
> 范围：只翻新 MeetingMind 输入预处理层，不增加新模态、新 Agent 框架或新基础设施

## 1. 本阶段解决什么问题

改造前，用户问题、身份作用域、会话内容、安全检查和路由结果分散在 API、`SessionContext` 与 `AgentState` 中。系统虽然有 Prompt Injection 检测，但存在三个实际缺口：

1. 图先执行路由、后做注入检查，恶意输入可能先进入路由模型。
2. 注入阻断字段不在状态清洗白名单中，图分支读取不到真实阻断结果。
3. 会话、检索片段和工具结果没有统一来源标签，也没有间接注入隔离。

本阶段将入口收敛为：

```text
InputEnvelope / TaskAnchor
        ↓
身份与业务作用域校验
        ↓
直接注入 + 不可信上下文检查
        ↓
IntentRouter 双轴路由
        ↓
原有会议工作流或受限 Planner
```

## 2. 两个核心契约

### 2.1 InputEnvelope

`input.v1` 是 Agent 内部契约，不改变现有 HTTP 请求格式。它包含：

| 字段组 | 当前字段 | 用途 |
|---|---|---|
| 请求身份 | request_id、user_id、session_id、conversation_id、thread_id | 隔离运行和用户 |
| 原始输入 | raw_query、normalized_query | 保留原文，只做空白规范化，不改写语义 |
| 业务范围 | meeting_id、document_ids、允许范围、can_write | 在进入路由前执行确定性校验 |
| 来源制品 | artifacts | 记录来源、媒体类型、信任级别、引用、校验和与安全状态 |
| 任务锚点 | task_anchor | 固定目标、交付物和约束 |
| 路由快照 | routing | 保存任务、复杂度、工作流、模型档位和路由证据 |
| 预算 | budget | 输入、上下文、计划步骤、工具次数与计划输出预算 |
| 安全 | security | 直接注入状态、策略标记和被隔离制品 |

Envelope 不复制大段文档正文，只保存 `content_ref + checksum`，避免状态膨胀和无意义的敏感内容复制。

### 2.2 TaskAnchor

`task-anchor.v1` 当前只保留七类稳定信息：

- goal：规范化后的用户目标。
- required_outputs：必须产生的 answer、minutes、todos 或 controversies。
- hard_constraints：身份、会议和指定文档范围。
- forbidden_actions：不执行外部内容中的指令；外部写必须经过策略和必要审批。
- completion_criteria：必需交付物与引用要求。
- ambiguities：低路由置信度或未指定检索范围等歧义。
- schema_version：支持后续字段演进。

TaskAnchor 已写入规划提示，并由确定性校验检查必需交付物。它不是长期记忆，也不是额外 Planner。

## 3. 信任分区

当前不使用一个含糊的 trusted/untrusted 布尔值，而是保留来源类别：

| 来源 | trust_level | 当前处理 |
|---|---|---|
| 用户问题 | user_instruction | 做直接注入检查；可表达目标，但不能绕过工具策略 |
| 选中文档 | untrusted_upload | 只登记引用；正文进入检索后继续检查 |
| 会话历史 | untrusted_session | 使用前做规则检查，命中 block 时隔离 |
| RAG 片段 | untrusted_retrieval | 每个片段独立登记与检查，隔离项不进入上下文和 citations |
| 工具结果 | untrusted_tool_result | 使用前登记与检查，命中时不进入 task_contexts |

传给模型的上下文还增加明确边界：外部内容只能作为会议证据，不能作为系统指令。这是一层提示防护，不替代 ACL、ToolPolicy 或 HITL。

## 4. 直接注入与间接注入

直接注入是用户问题本身试图覆盖系统指令。现在它在 IntentRouter 之前检查，命中后的真实图路径是：

```text
input_node → prompt_injection_node → rejection_node → END
```

间接注入是恶意指令藏在会话、文档、检索片段或工具结果中。当前策略是“隔离恶意制品，继续处理其余安全证据”，而不是把外部内容当成新的用户指令，也不是无条件拒绝整个请求。

若所有检索片段都被隔离，校验状态会明确记录“所有检索片段均因间接注入风险被隔离”，避免无证据地伪装成功。

## 5. 为什么图路由改用 Command

图级测试发现当前依赖组合 `LangGraph 0.2.76 + Python 3.12` 在本项目环境中执行同步 conditional edge 会挂起。此前注入字段被清洗丢弃，安全拒绝分支没有真正跑到，因此该问题未被测试暴露。

本阶段没有改变业务拓扑，而是将原条件边改为节点返回 `Command(update=..., goto=...)`：

- 输入、安全、风险、检索、工具风险、重规划和校验仍使用原判定规则。
- 节点名称和业务分支保持不变。
- 图级恶意输入测试可以真实到达拒绝终态。

后续升级 LangGraph 时，应重新验证是否恢复声明式 conditional edge，而不是盲目保留实现细节。

## 7. 输入介质与 ASR 证据生命周期收口

在统一 Agent 输入契约之后，本阶段继续把 HTTP 文件入口与音频证据入口纳入同一条可信边界。系统仍然只保留文本、可解析文档和 WAV，不增加图片、视频、传感器或通用多模态框架。

| 收口项 | 实现 | 失败语义 |
|---|---|---|
| 文件准入 | 文档/WAV 联合校验扩展名、MIME、大小和实际结构；移除无法可靠解析的旧版 `.doc` | 415 类型不支持、413 超限、422 内容无效；不进入解析或消息队列 |
| 音频溯源 | ASR Evidence v2 保存音频哈希、源文件元数据、模型/包/设备、时间戳、说话人、不确定性和处理时延 | 原始模型全文仅作受控审计，Agent/RAG 只消费筛查后的当前版本 |
| 任务状态 | `transcript_status` 独立记录 pending/processing/completed/failed，`ingestion` 记录各阶段时间与错误类别 | 不再用会议业务 `status` 代替音频任务状态 |
| 间接注入 | FunASR 句级片段逐项执行规则筛查，SpeechRecord 保存安全状态、原因与内容哈希 | quarantined 片段保留供人工核验，但不进入正文、纪要草稿、RAG 与 citations |
| 修订与重建 | 人工编辑/删除片段或修订全文时递增证据版本，记录上一版哈希；旧 PG 向量块与缓存先失效再重建 | 空文本为 not_created；未产出新块为 rebuild_required，不继续伪用旧块 |
| 引用式状态 | 检索材料只把引用、校验和及白名单溯源字段登记到 InputArtifact | 原始音频、完整文档和完整转写不复制进 InputEnvelope |

音频证据状态流转为：

```text
WAV 严格准入
  → pending（任务已发布）
  → processing（Worker 已领取）
  → FunASR 原始证据
  → 逐片段筛查
  ├─ 有安全文本 → 私有 asr_evidence 文档 + VectorChunk → completed
  ├─ 空/全隔离 → 不创建索引 → completed + index.not_created
  └─ 发布/处理异常 → failed
```

人工修订不会覆盖证据历史：`asr_original_transcript` 保留首次模型全文，`raw_transcript` 是当前允许进入业务链路的文本，`transcript_revision/evidence_version` 标识当前版本，最近二十版哈希和复核状态保存在元数据中。完整文本修订会使旧句级对齐失效，因此旧片段标为 `asr_superseded` 并从默认发言列表移除。

数据库新增字段由 `backend/app/db/migrations/0009_harden_asr_evidence_lifecycle.py` 升级；新库仍由 SQLAlchemy metadata 创建完整结构。当前权威索引是 PostgreSQL 中的 VectorChunk/pgvector 或轻量向量列；可选 Milvus 的同步属于独立索引运维边界，本阶段不声称双库强一致。

主要实现入口：

- `backend/app/services/input_admission.py`：文档/WAV 严格准入。
- `backend/app/services/asr_evidence_service.py`：片段筛查、证据元数据、版本与索引文本。
- `backend/app/api/v1/endpoints/tasks.py`：WAV 接收与 pending/publish_failed 落库。
- `backend/app/workers/audio_worker.py`：processing/completed/failed、证据分区和索引创建。
- `backend/app/services/meeting_service.py`：人工修订、旧索引失效与新版本重建。
- `backend/app/services/document_service.py`：私有 ASR 证据文档和 VectorChunk 生命周期。

### 7.1 上下文预算优化第 1 步：TokenBudgetLedger

原有 `InputBudget` 只声明字符数、计划步骤、工具次数和规划输出上限，不能证明每次模型请求在发出前都受控。本次把预算从“状态中的配置说明”升级为统一模型入口的运行时硬门禁：

```text
messages + selected_model + requested_max_output
  → 匹配 tokenizer 或保守 UTF-8 上界计数
  → 预留最大输出 + 模型窗口安全余量
  → 校验模型窗口 / 节点累计 / Agent Run 累计 / 调用次数
  ├─ 超限：记录 rejected 决策，不调用供应商
  └─ 通过：预留最坏情况预算 → 模型响应 → 用 provider usage 校准
```

当前预算契约如下：

| 边界 | 默认值 | 语义 |
|---|---:|---|
| 未知模型上下文窗口 | 32768 | 具体模型通过 JSON 映射显式覆盖，不能靠模型名猜测 |
| 单节点累计 | 32768 | 限制重试、多任务或并发工具在一个节点内持续放大 |
| 单次 Agent Run 累计 | 65536 | 汇总图内所有模型请求；调用完成后用真实 usage 释放过量预留 |
| 模型调用次数 | 16 | 即使单次请求很短，也限制循环和重规划次数 |
| 安全余量 | 模型窗口的 15% | 抵御兼容接口消息模板和保守计数误差，不计作真实供应商消费 |

实现边界：

- `LLMService.chat` 是所有真实模型请求的统一入口，门禁在创建网络请求前执行；被拒绝时供应商 client 不会收到调用。
- 图节点通过运行上下文写入 node 标签；并发任务继承并共享同一个 Agent Run 账本，预留动作在进入 `await` 前完成。
- 返回 usage 时保存真实 prompt/completion Token；供应商未返回 usage 时保留“估算输入 + 最大输出”，不能写成真实成本。
- 预算快照只包含模型、节点、计数方法、估算/实际数量和拒绝原因，不保存消息正文。
- HITL 快照保存同一本账，确认恢复继续使用原累计值；缺少或损坏快照时拒绝恢复，防止预算重置。
- 当前 Qwen 环境没有供应商匹配 tokenizer。UTF-8 字节数是有意偏大的调用前上界，`count_method` 会如实标记；它不能用于宣称精确计费。

- `backend/app/agents/graph.py`
- `backend/app/agents/agent_service.py`

### 7.2 上下文预算第 2—5 步：低复杂度收口

本次目标是有效减少 Token 超限、噪声放大、旧信息污染和无效成本，同时控制实现与学习复杂度。因此没有增加摘要 LLM、Embedding 去重、Redis 差量缓存或流式状态机，而是新增一个确定性 `ContextAssembler`：

```text
TaskAnchor 紧凑约束 + 证据型工具结果 + 当前检索块 + 最近会话轮次
  → 来源优先级排序
  → 规范化内容 SHA-256 精确去重
  → 同文档最多 3 块 + 总条数最多 8 条
  → 单条最多 1600 字符，超限只保留前缀并显式标记
  → 5000 字符总预算内组装
  → 生成不含正文的 context-manifest.v1
  → TokenBudgetLedger 执行最终模型调用硬门禁
```

选择与取舍：

| 问题 | 本次实现 | 为什么省时 | 明确边界 |
|---|---|---|---|
| 证据与历史竞争 | 固定优先级：证据工具 > 检索 > 最近会话 | 无训练、无额外模型请求 | 优先级是工程初值，需真实长会议校准 |
| 重复噪声 | 去除来源标签和空白后做精确哈希去重 | O(n) 且完全可复现 | 不识别语义相同但措辞不同的近重复 |
| 单一文档垄断 | 同一 document_id 最多 3 个检索块 | 一个计数器即可实现 | 不是 MMR，不保证最佳语义多样性 |
| 旧会话污染 | 最近三轮拆成独立项并按最近优先 | 不摘要、不建缓存 | 仍是进程内短期记忆 |
| 工具结果膨胀 | 只接收三个只读证据工具，并投影 content/chunk_text/text 等白名单字段 | 避免递归复制任意 JSON | 生成型与写工具结果不自动进入全局上下文 |
| 长内容挤占 | 单条/总条数/总字符三重上限，只保留前缀 | 规则简单且不会保留陈旧尾部 | 可能丢失长文末尾信息，清单会如实记录 |
| 不可解释丢弃 | ContextManifest 记录 ref、hash、长度、优先级及 duplicate/diversity/budget 等原因 | 不建新的可观测平台 | 不保存正文，需结合原始 content_ref 复核 |

ContextAssembler 已接入：

- Agent Planner 的 2000 字符上下文配额，移除后续 `[:2000]` 二次静默截断。
- 简单 QA、纪要、待办、争议、复杂任务输入和文档兜底生成。
- Planner 生成的显式工具 context、前序任务输出和证据工具结果，不能绕过统一预算。
- 独立 RAG `generate_answer`，替换原有按列表顺序贪心拼接。
- 普通 Agent、SSE 最终事件和批量响应返回 `context_manifest`；正文不会进入清单。

## 9. 本阶段有意不做的内容

- 不接图片、视频、ROS 或统一多模态 Token。
- 不增加租户体系；当前只使用项目已有 user/access_scope。
- 不用额外过滤 LLM 作为唯一安全边界。
- 不增加长期记忆、MCP、Multi-Agent 或 Temporal。
- 不公开 InputEnvelope 中的内部安全细节；统一 OutputEnvelope 留到输出层翻新。
- 不宣称规则可以识别所有注入；Bad Case、误报率和召回率仍需固定评测集验证。

## 10. 建议亲自复盘的问题

1. 为什么用户指令也不能被标成“完全可信”？
2. 为什么恶意 RAG 片段应从 citations 中同步移除？
3. `content_ref + checksum` 相比把全部正文复制进 Graph State 有什么收益？
4. TaskAnchor 与普通 Prompt 中的一段“请完成以下目标”有什么本质区别？
5. 当全部证据被隔离时，应返回 failed、partial 还是需要用户补充资料？这应在输出层统一决定。
6. 如何构造包含正常引用、角色扮演文本和真实恶意指令的标注集，测量间接注入规则的误报与漏报？
7. 为什么 ASR 任务 completed、证据通过安全筛查和人工确认准确是三个不同状态？
8. 为什么要保留原始转写哈希，却只让当前安全版本进入 RAG？
9. 修订时为什么必须先让旧向量块失效，再建立新版本？如果新索引失败应该返回什么状态？
10. 扩展到 MP3、图片或视频前，分别还缺哪些可复现的解码、内容安全、资源预算和评测证据？
