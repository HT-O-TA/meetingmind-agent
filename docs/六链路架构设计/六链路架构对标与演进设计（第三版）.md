## 0. 第三版结论

未来简历项目确定为：

1. **Agent 项目：MeetingMind 企业会议知识 Agent**，即当前项目。
2. **微调对齐项目：独立的小模型后训练与评测项目**，以 Python、PyTorch、Transformers、PEFT、TRL 为主。
3. **C++ 项目：房间制实时多人游戏服务器**，以 C++20、Linux 异步网络、状态同步与性能验证为主。

第三版对第二版只做一项重大路线替换：

**不再把“Java 企业 Agent”作为第二个必做项目。**

第二版对 MeetingMind 的六链路判断继续有效：保留 Python、RAG-first、workflow-first、单 Agent 和受控工具闭环，按输入、记忆、规划、工具、校验、输出逐层定向翻新，不推倒重写，不增加 Multi-Agent、MCP、Temporal 或长期演化记忆。

新的总路线为：

```text
MeetingMind 六链路翻新与真实演示
→ 独立微调对齐项目
→ C++ 游戏服务器项目
→ 按目标岗位调整三项目排序和篇幅
```

## 1. 对三个项目组合的看法

### 1.1 总体判断

这个组合是合理的，且比“Python Agent + Java Agent”更有区分度。

| 项目 | 主要证明什么 | 面向 AI 应用开发岗的作用 |
|---|---|---|
| MeetingMind | RAG、Agent 编排、工具治理、异步任务、业务闭环 | 主项目，证明能把模型能力变成可运行应用 |
| 微调对齐 | 数据构建、SFT、偏好对齐、实验设计、评测与失败分析 | 第二核心项目，证明理解模型行为如何被数据与训练改变 |
| C++ 游戏服务器 | 网络、并发、状态机、内存与性能工程 | 工程深度补充，证明不只会调用模型和拼装框架 |

三者分别回答三个不同问题：

- 能否构建可靠的 AI 应用？
- 能否理解并验证模型后训练？
- 能否处理底层并发、网络和性能问题？

这比三个项目都做成 Web CRUD，或两个项目都做成 RAG Agent，更容易形成稳定的个人技术画像。

### 1.2 对 AI 应用开发岗的实际优先级

默认排序应为：

1. MeetingMind；
2. 微调对齐；
3. C++ 游戏服务器。

C++ 项目不是 AI 应用岗简历的主角。它的价值是提供系统能力和差异化，不应挤占前两个项目的篇幅。如果简历只有一页，可采用以下篇幅：

| 项目 | 建议篇幅 |
|---|---:|
| MeetingMind | 45%—55% |
| 微调对齐 | 25%—35% |
| C++ 游戏服务器 | 15%—25% |

若投递 C++ 后端或游戏服务器岗位，才将 C++ 项目放到第一位；项目事实不变，只调整叙事顺序。

### 1.3 为什么当前不再新建 Java Agent

Java 第二 Agent 本身仍是可行方案，但不适合现在作为第四条主线：

- 它会重复工具调用、审批、审计、工作流和 Agent 评测等 MeetingMind 已覆盖的主题。
- 同时维护 Python Agent、Java Agent、微调和 C++ 服务器，会导致每个项目都缺少真实数据、指标和深入复盘。
- 技术栈差异不等于项目价值差异。面试区分度更应来自问题、约束和可复现实验。
- C++ 项目已经承担“非 Python 工程能力”的证明，不需要再用 Java 为语言数量加一。

因此第三版把第二版 Java Agent 降为**将来明确投递 Java AI/企业应用岗位时的备选方案**，当前不创建仓库、不加入排期。

## 2. 三个项目必须保持的边界

### 2.1 能力归属

| 能力 | MeetingMind | 微调对齐项目 | C++ 游戏服务器 |
|---|---|---|---|
| 业务核心 | 会议知识处理与安全业务动作 | 模型后训练与行为评测 | 实时多人会话与权威状态 |
| 主语言 | Python | Python | C++20 |
| 核心框架 | FastAPI、LangGraph | PyTorch、Transformers、PEFT、TRL | Linux、Boost.Asio、CMake |
| 数据重点 | 文档、音频证据、RAG 真值、工具轨迹 | 指令样本、偏好对、数据许可与切分 | 协议消息、房间状态、压测轨迹 |
| 算法/模型重点 | Embedding、Reranker、路由、结构化生成 | SFT、LoRA/QLoRA、DPO、消融 | 网络 I/O、tick、状态同步、背压 |
| 可靠性重点 | ACL、HITL、幂等、审计、恢复 | 可复现训练、检查点、评测防泄漏 | 断线重连、超时、限流、并发正确性 |
| 主要指标 | 检索、生成、工具、延迟、任务完成 | 任务质量、偏好胜率、安全、显存和延迟 | 连接数、吞吐、P95/P99、tick lag、错误率 |

### 2.2 允许重复与禁止重复

三个项目可以共同具备：

- 测试、CI、配置管理和可复现命令；
- 明确的输入输出契约；
- 指标、报告和失败样本；
- 安全边界与真实性声明。

不应重复建设：

- 不在微调项目里再做完整 RAG/Agent 平台。
- 不在 MeetingMind 里扩建通用训练平台。
- 不给 C++ 游戏服务器强行加入 LLM、向量库或“AI NPC”来迎合 AI 标签。
- 不把同一份 MeetingMind 合成数据同时包装成两个完整项目成果。

## 3. MeetingMind 的最终项目定位

### 3.1 保持 Python 是否正确

正确。MeetingMind 的核心是文档/音频处理、Embedding、Reranker、LangGraph、结构化生成、ASR 和评测，这些能力与 Python 生态直接匹配。改成 Java 只会重写已经验证的主链，不会改善会议业务，也不会自动提高简历质量。

本项目的差异化不依赖“语言更多”，而依赖以下完整证据链：

```text
会议文档或 WAV
→ 解析/ASR 与说话人证据
→ PostgreSQL 关键词 + Milvus Dense + BGE Reranker
→ 带 ACL 和引用的 RAG
→ LangGraph 确定性工作流或受限 Planner
→ Schema + ToolPolicy + HITL + Executor + 审计
→ 结构化结果、失败边界、评测和固定 Demo
```

### 3.2 本项目应该强调的能力

- 有业务语义的 RAG，而不是单纯调用向量库。
- workflow-first 的 Agent 取舍，而不是无限 ReAct 或 Multi-Agent。
- 输入信任分区、文档 ACL、工具权限、HITL 和审计组成的纵深防护。
- RabbitMQ 长任务、ASR 证据与业务状态的真实连接。
- 可复现评测、Bad Case 和不夸大合成/烟测指标的工程纪律。

### 3.3 本项目不再承担的能力

- 不升级为 Java/Python 混合微服务项目。
- 不增加第二套 Agent 框架。
- 不恢复 MCP 动态工具、Multi-Agent、KG 或通用多模态骨架。
- 不把轻量 LangGraph 检查点扩展为跨天企业流程平台。
- 不把现有 LoRA/QLoRA 教学实验扩成通用对齐平台；第二项目单独完成这件事。

## 4. 对第二版 MeetingMind 改进方法的确认

### 4.1 总体确认

第二版第 6、7、9 节对 MeetingMind 的改进方向继续采用：

- 只翻新影响正确性、恢复、可测试性和输出语义的部分。
- 每层先建立最小契约，再接入现有图，不扩业务范围。
- 确定性工作流优先，复杂请求才进入受限规划。
- 安全与副作用控制由应用执行，不交给模型自行保证。
- 所有新能力必须有图级、契约或集成测试，并能映射到真实 Demo。

第三版不改变六链路目标，只根据当前进度和三项目组合更新执行状态。

### 4.2 六链路确认表

| 链路 | 第二版结论 | 第三版确认后的最小改造 | 当前状态/验收门槛 |
|---|---|---|---|
| 输入预处理层 | 需要翻新 | InputEnvelope、TaskAnchor、信任分区、直接/间接注入防护，安全检查先于路由 | **已完成第一轮**；已有图级与回归测试，后续用标注 Bad Case 测误报/漏报 |
| 记忆层 | 小幅调整 | 持久 checkpointer、thread/run/task_id 语义、HITL 恢复、TaskAnchor 随状态持久化、长期事实 PG 主库和 outbox | 本地代码闭环已完成；真实 PostgreSQL/RabbitMQ/Milvus/Neo4j 重启、并发和最终一致性仍待验收 |
| 规划推理层 | 需要翻新 | PlanStep 增加产物、完成条件、证据、风险、预算和失败策略；收敛内部决策记录 | 待实施；简单任务绕过 Planner，复杂任务计划可校验、有界停止 |
| 工具执行层 | 可靠性收口 | 落实 timeout、FailureCategory、ToolResult、并发上限和必要熔断；保留现有治理主链 | 待实施；超时与不确定写入不可误报成功，幂等与审计继续 fail closed |
| 反思校验层 | 需要翻新 | ValidationDecision、FailureReport；结构/业务/证据/轨迹优先，LLM Judge 只评难编码维度 | 待实施；能稳定选择 pass/repair/replan/human_review/stop，并输出机读原因 |
| 输出层 | 需要翻新 | 统一 OutputEnvelope 和 complete/partial/pending_approval/failed/rejected 语义 | 待实施；普通、SSE、批量接口语义一致，不把部分失败当成功 |

输入层第一轮的实现与测试记录见[输入预处理层翻新](../优化路径记录/13_输入预处理层翻新.md)。

### 4.3 第二版 M0—M4 与当前执行顺序的关系

第二版使用 M0 正确性、M1 契约、M2 恢复、M3 评测输出、M4 真实演示来组织任务；这个分法仍然正确，但实现时按六链路顺序学习更直观。

两种划分的映射如下：

| 第二版阶段 | 六链路中的落点 |
|---|---|
| M0 正确性 | 输入层的注入状态、工具层的超时、输出层的成功语义 |
| M1 契约 | InputEnvelope、TaskAnchor、PlanStep、ValidationDecision、FailureReport、OutputEnvelope |
| M2 恢复 | 记忆层 checkpointer、HITL 恢复、工具幂等 |
| M3 评测和输出 | 校验层、输出层、固定数据集与 API 一致性 |
| M4 真实演示 | 六层完成后的重大缺陷收口与真实数据/账号验收 |

结合当前决定，后续顺序确认为：

```text
输入层（已完成第一轮）
→ 记忆层
→ 规划层
→ 工具层
→ 校验层
→ 输出层
→ 全链重大缺陷收口
→ 真实数据、真实模型、真实 Jira 演示
```

若某层发现权限绕过、重复外部写、数据损坏或测试无法终止等严重问题，应在该层立即修复；“最后统一收口”不表示推迟已发现的安全/数据正确性缺陷。

### 4.4 每一层的学习要求

每次翻新不只提交代码，还要留下：

1. 改造前的问题和可复现用例；
2. 核心 Schema 与字段取舍；
3. 正常、失败和降级路径；
4. 至少一个图级或跨组件测试；
5. 有意不做的内容；
6. 可供本人复盘的面试问题。

项目目标仍然是本人掌握技术，代码完成只是学习证据。

## 5. 第二项目：微调对齐

### 5.1 推荐定位

暂定项目名可写为：

**小模型指令微调与偏好对齐实验平台**

目标不是“跑通一个训练脚本”，而是回答：

- 什么数据改变了什么行为？
- SFT 与偏好对齐分别解决什么问题？
- 质量提升是否来自数据泄漏、模板记忆或评测偏差？
- LoRA、QLoRA 和训练配置在质量、显存、时间上如何权衡？
- 训练后的模型是否更会拒答，同时出现过度拒答或能力退化？

### 5.2 建议技术范围

| 层 | 建议 |
|---|---|
| 基座 | 选择许可清晰、硬件可承受的 0.5B—3B 开放模型；先单模型，不做模型动物园 |
| 训练 | PyTorch + Transformers + PEFT；SFT 采用 LoRA，显存确有约束时比较 QLoRA |
| 对齐 | 先做离线偏好对齐 DPO；只有任务存在可靠、可验证 reward 时再研究 GRPO |
| 数据 | 公开/自建数据分开标识；许可、去重、污染检查、切分、数据卡和版本哈希齐全 |
| 评测 | 基座、Prompt/Few-shot、SFT、DPO 同协议；任务指标、安全指标、人工盲评和资源指标并列 |
| 推理 | 最小推理 API 或批量评测入口；不重复建设 MeetingMind 的业务平台 |
| 追踪 | 配置、随机种子、环境、checkpoint、预测和报告可复现；按实际需要选择实验追踪工具 |

建议默认路线是 **SFT → DPO**，不是把 SFT、DPO、PPO、GRPO、KTO、ORPO 全部跑一遍。方法数量不能替代数据质量和实验解释。

### 5.3 与 MeetingMind 现有微调实验的关系

MeetingMind 已有 Qwen3-0.6B、76 条项目自编合成数据、LoRA/QLoRA 和统一结构化抽取评测。这是很好的**前置教学实验**，但不是独立对齐项目，原因是：

- 数据量小且全部为项目自编合成数据；
- 任务主要是固定结构化抽取，没有偏好数据与对齐实验；
- 测试集只有 16 条，结果不能外推真实会议；
- 训练能力仍依附 MeetingMind 业务叙事。

第二项目可以复用其中的数据切分、Schema 评测和失败分析经验，但应建立独立仓库、独立任务定义和独立数据。MeetingMind 中的现有实验保留用于复盘，不伪装为新项目成果。

### 5.4 推荐业务题目与验收

默认建议选择：**中文指令遵循与安全拒答的小模型对齐**。

数据至少包含：

- 正常任务完成；
- 格式/约束遵循；
- 信息不足时的澄清或保守回答；
- 明确风险请求的拒答；
- 容易误拒的正常请求，用于测过度拒答。

必须同时报告：

- 任务完成或结构正确率；
- 偏好胜率及评审方法；
- 合理拒答率与过度拒答率；
- 领域外能力退化；
- 训练时间、峰值显存、推理延迟和 adapter 大小；
- 主要 Bad Case 与数据修订记录。

如果没有可靠人工偏好标注，应明确写“模型辅助生成 + 人工抽检/复核”，不能把同一模型生成并评判的数据称为人类偏好真值。

### 5.5 建议阶段

| 阶段 | 产出 |
|---|---|
| A0 任务与基线 | 任务定义、数据许可、固定测试集、基座与 Prompt/Few-shot 基线 |
| A1 SFT | 数据清洗、LoRA/QLoRA 对照、训练/推理资源报告、Bad Case |
| A2 偏好数据 | chosen/rejected 规则、标注指南、一致性检查、数据卡 |
| A3 DPO | 与基座/SFT 同协议比较，分析任务收益、拒答和退化 |
| A4 交付 | 批量评测、最小推理 Demo、实验报告、模型卡和简历证据索引 |

## 6. 第三项目：C++ 游戏服务器

### 6.1 推荐定位

推荐做：

**基于 C++20 与 Linux 异步 I/O 的房间制实时多人游戏服务器**

房间制业务比“通用分布式游戏引擎”更容易形成可验证闭环：登录/会话、匹配或建房、进入房间、固定 tick、玩家输入、权威状态更新、广播、断线重连和结算。

### 6.2 最小技术架构

```text
Load Client / Game Client
          ↓
Connection & Session（TCP 起步）
          ↓
Protocol Codec（长度帧 + Protobuf）
          ↓
Gateway / Command Dispatch
          ↓
Room Actor / Single-writer State
          ↓
Fixed Tick + Authoritative Simulation
          ↓
Snapshot / Delta Broadcast
          ↓
Persistence（出现真实需求后再加）
```

建议技术栈：

| 层 | 建议 |
|---|---|
| 语言/平台 | C++20、Linux |
| 网络 | Boost.Asio；先 TCP，确有实时性与丢包实验需求后再增加 UDP |
| 协议 | 长度前缀帧、消息 ID、版本字段、Protobuf |
| 并发 | I/O 线程 + 房间单写者/strand；先证明正确性，再比较线程池或 actor 方案 |
| 构建 | CMake + CMakePresets |
| 测试 | GoogleTest、协议模糊/边界测试、集成客户端、TSAN/ASAN |
| 性能 | 自建负载客户端 + Google Benchmark；记录环境、预热、重复次数和分位延迟 |
| 数据 | 初版内存状态即可；账户/战绩出现持久化需求后再加入 PostgreSQL/Redis |

### 6.3 不要一开始加入的内容

- 不先做微服务拆分、服务网格或 Kubernetes。
- 不同时实现 TCP、UDP、QUIC、WebSocket 四套协议。
- 不在没有压测证据时声称“百万连接”或“高并发”。
- 不为技术栈数量提前加入 Redis、Kafka、MySQL 和分布式一致性组件。
- 不先做复杂战斗逻辑；服务器工程能力由会话、状态、并发正确性和性能指标证明。

### 6.4 核心验收指标

- 最大稳定连接数及测试机器配置；
- 每秒消息数和有效业务吞吐；
- 端到端 P50/P95/P99 延迟；
- 房间 tick 延迟、漂移和超时次数；
- 断线重连、重复消息、乱序/非法包和慢客户端处理；
- CPU、内存、连接与房间数量的关系；
- ASAN/TSAN、单元、集成和压力测试结果。

每个性能数字都必须绑定 commit、编译参数、机器、客户端模型、消息大小、持续时间和报告文件。

### 6.5 建议阶段

| 阶段 | 产出 |
|---|---|
| G0 协议与会话 | 分帧、编解码、登录会话、心跳、非法包测试 |
| G1 房间闭环 | 建房/加入、单写状态、固定 tick、广播和结算 |
| G2 可靠性 | 断线重连、背压、超时、限流、优雅停机、状态恢复边界 |
| G3 性能 | 负载客户端、分位延迟、火焰图/Profiler、优化前后对比 |
| G4 项目化 | CI、Sanitizer、架构/协议文档、固定演示和简历证据索引 |

## 7. 三项目实施顺序

不建议三个仓库同时全面开发。推荐顺序：

### P0：先完成 MeetingMind

- 完成剩余五条链路翻新；
- 做一次全链重大缺陷收口；
- 用真实或合法脱敏会议材料建立评测；
- 在具备凭据后完成 Jira 审批、写入和回查；
- 录制固定 Demo，并能独立解释每层取舍。

### P1：建立微调对齐独立项目

- 先冻结任务、数据许可和测试集；
- 再完成 SFT 与 DPO，不先追逐方法数量；
- 将 MeetingMind 的微调实验作为先导经验，而不是直接复制成新项目。

### P2：建立 C++ 游戏服务器

- 先完成单机房间闭环和测试客户端；
- 再用压测暴露真实瓶颈；
- 最后按证据决定是否需要 UDP、Redis 或服务拆分。

如果需要保持 C++ 手感，可以在 P0/P1 期间做短时语言练习，但不把练习代码提前包装成第三个项目。

## 8. MeetingMind 在简历上的初版写法

以下版本只使用当前仓库已经实现、测试或明确标注边界的事实。它适合作为初稿，不代表真实数据和 Jira 账号验收已经完成。

### 8.1 项目标题与技术栈

**MeetingMind｜企业会议知识 Agent**

`Python / FastAPI / LangGraph / PostgreSQL / Milvus / Redis / RabbitMQ / BGE / FunASR / Vue 3`

面向会议文档与 WAV 音频，构建从证据入库、混合检索、结构化会议处理到受控外部工具执行的 AI 应用，并以权限、审批、幂等、审计和回归评测约束 Agent 行为。

### 8.2 当前可用项目要点

- 设计会议知识 RAG 主链：说话人感知分块，PostgreSQL 关键词与 Milvus Dense 双路召回，经归一化加权和 BGE Reranker 精排；在召回前下推文档 ACL，回答返回 chunk、说话人、时间戳与来源引用。
- 基于 LangGraph 实现 workflow-first 的单 Agent 编排，简单任务进入确定性会议节点，复杂请求进入受限 Planner；以 InputEnvelope、TaskAnchor 和来源信任分区统一输入，在路由前阻断直接注入并隔离检索/会话/工具结果中的可疑间接指令。
- 建立 `Schema → ToolPolicy → HITL → ToolExecutor → PostgreSQL 审计` 的副作用控制链，支持 Jira Cloud REST v3 适配、幂等回放和不确定写入保护；当前已完成契约与数据库集成验证，真实 Jira 站点写入待账号验收。
- 使用 RabbitMQ 实现文档/音频任务的 publisher confirm、manual ACK、有界重试、DLQ、prefetch 和任务幂等，并通过独立 FunASR Worker 保存句级时间戳、匿名说话人和模型版本，形成 WAV 到会议证据的可演示链路。
- 将模型重型环境与 Web/Worker 解耦，以后端契约/集成测试、前端测试与构建、Docker Compose、部署前检查和 GitHub Actions 固化交付门禁；所有 RAG、ASR 和训练效果数字均按真实/公开/合成数据来源单独标记。

### 8.3 暂不写进主项目要点的内容

MeetingMind 现有 LoRA/QLoRA 实验可以放在技能或面试补充中，但第三版建议不再占用 MeetingMind 的核心简历 bullet。未来独立微调对齐项目完成后，由第二项目专门讲数据、训练和对齐，项目边界会更清楚。

以下说法现在不能使用：

- “生产级”“已上线”或“支撑真实业务并发”；
- “显著提升 RAG 准确率”，因为尚无冻结真实会议 RAG 真值；
- “完成真实 Jira 写入”，因为尚缺站点凭据与回查证据；
- 用公开单句 ASR 烟测代表多人会议 CER/DER；
- 用 76 条合成数据上的 LoRA 指标代表真实会议抽取质量；
- 把当前规则注入检测描述为可以识别所有 Prompt Injection。

### 8.4 六链路完成后再升级的简历信息

完成并实测后，可补充但不得预写：

- 进程重启后的 Agent/HITL 恢复率与重复副作用结果；
- 复杂计划完成率、平均重规划次数和预算命中情况；
- 工具超时、失败分类和外部写幂等指标；
- 引用证据覆盖率、partial/failed 语义一致性；
- 冻结真实或脱敏数据上的 RAG、路由、抽取与端到端指标；
- 真实 Jira 审批、Issue Key、回查和审计证据。

## 9. 简历和面试叙事建议

### 9.1 一条统一主线

三个项目看似分散，实际可以用同一条工程主线串联：

> 我不仅调用模型，还会定义数据与契约、控制失败边界、建立可复现实验，并从应用编排、模型后训练和底层服务器三个层次验证系统行为。

### 9.2 面试时不要平均用力

- AI 应用岗先讲 MeetingMind 的业务闭环和六链路取舍。
- 被追问模型能力时，再讲微调对齐的数据与对照实验。
- 被追问系统基础时，用 C++ 服务器解释异步 I/O、并发模型、背压和性能测量。
- 不要在一个回答中罗列三个项目的所有框架；先回答问题，再给证据。

### 9.3 项目完成标准

每个项目在进入简历前至少具备：

1. 一个无需阅读源码即可运行的固定 Demo；
2. 一组冻结输入、命令、环境和原始报告；
3. 正常、失败和降级路径；
4. 至少一个真实或合法公开数据证据；
5. 明确写出的未完成项与适用边界；
6. 本人能从原理、实现、测试、指标和取舍五个角度解释。

## 10. 尚待后续亲自确认的细节

这些问题不阻塞第三版路线，但在创建对应项目仓库前必须确认：

### 微调对齐项目

1. 最终基座模型、显卡预算和训练时长上限；
2. 中文指令遵循/安全拒答是否作为最终业务题目；
3. 偏好数据来自人工标注、公开数据还是模型生成后人工复核；
4. 哪些指标作为主门禁，如何控制评审模型偏差；
5. 是否需要最小推理服务，还是以离线评测与实验报告为主。

### C++ 游戏服务器

1. 具体玩法与 tick 频率；
2. 首版连接协议是否确定为 TCP；
3. 房间并发模型选 strand/单写者还是显式 actor；
4. 哪类状态必须持久化；
5. 目标硬件与压测客户端模型。

这些细节应由本人逐项确认，以保证项目服务学习目标，而不是直接接受一份无法解释的完整实现。

## 12. 第三版最终决策

| 决策 | 结论 |
|---|---|
| 简历项目数量 | 三个 |
| Agent 项目 | MeetingMind，即当前项目 |
| MeetingMind 主语言 | Python，不改 Java |
| MeetingMind 改进方式 | 确认第二版的六链路部分翻新，不推倒重写 |
| 输入层状态 | 第一轮翻新已完成，后续补真实 Bad Case 评测 |
| 第二项目 | 独立微调对齐项目，Python/PyTorch/Transformers/PEFT/TRL |

| Java 第二 Agent | 从必做路线移除，仅作为特定岗位备选 |
| 当前优先级 | 先完成 MeetingMind 剩余五层、重大缺陷收口和真实演示 |
| 简历默认排序 | MeetingMind → 微调对齐 → C++ 游戏服务器 |
| 核心原则 | 少堆框架，多做真实数据、可复现指标、失败分析和本人可解释的取舍 |
