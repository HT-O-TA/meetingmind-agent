# 规划推理层

> 这份文档用大白话说明：Agent 如何把用户目标拆成可执行步骤、如何避免乱调用工具、如何在失败时停下来，以及当前还没有解决什么。
> 2026-09-04 已完成本轮四项 P0 加固：计划结构/工具门禁、重复失败熔断、否定与阈值约束复核、不确定性传递。长任务全局价值、复杂复盘和真实长会议效果仍需后续验收。

## 这一层负责什么

规划推理层负责把输入层整理好的目标变成一份“能执行的清单”：

- 需要做哪些任务；
- 任务之间谁先谁后；
- 要不要调用工具、调用哪个工具；
- 哪些步骤可以并行；
- 信息不确定或工具失败时，什么时候暂停、重规划或结束。

它不负责重新解释用户身份和权限，也不把文档或工具返回的文字当成新的系统指令。

## 核心问题与改进安排

### 1. 步骤幻觉与链路断裂（P0）

当前方案：

- `PlanBudgetGuard` 校验任务数组、任务 ID、执行顺序、依赖关系、依赖循环、并行分组和工具调用结构。
- 计划中的工具名必须来自当前 `ToolManager` 注册且支持执行的工具集合。
- 工具参数必须是对象；真正执行前还会按工具自己的参数 Schema 再校验一次。
- 计划门禁失败时直接进入校验出口，不再使用默认工具计划“兜底”。

大白话总结：模型写出的计划先过一套清单检查，任务、依赖和工具都对不上就停下，不会拿一份猜出来的计划继续调用工具。

改进方案：

- 为每个工具补齐更严格的 JSON Schema 和参数示例。
- 增加“计划依赖图 → 执行器”的端到端测试，覆盖并行、跳过和失败恢复。
- 后续可引入小型确定性规划模板，减少简单任务对 LLM 自由发挥的依赖。

### 2. 无限循环与死锁（P0）

当前方案：

- 规划状态记录 `planner_iterations` 和计划指纹，相同计划重复出现或规划次数超过上限时熔断。
- 同一工具、同一参数和同一错误连续失败达到阈值后停止继续重试。
- 依赖环在进入执行器前就被拒绝。
- 现有 `max_repair_attempts` 和质量门禁继续限制修复次数。

大白话总结：同一份计划反复出现，或同一个动作连续失败，系统会自动刹车，不会一直重试到 Token 和时间耗尽。

改进方案：

- 记录每次停止的原因和最后一个可复现的失败指纹，方便排查。
- 对“用户改口”“外部状态变化”和“工具不可用”分别设计不同的退出提示。
- 真实环境验证网络超时、幂等重放和并行任务互等场景。

### 3. 过度规划（P1）

当前方案：

- `PlanBudgetGuard.evaluate()` 根据输入长度和复杂度动态限制任务数。
- Token 紧张时提示模型只输出核心步骤，避免生成几十步冗余计划。
- `TokenBudgetLedger` 在模型调用前检查节点、运行和调用次数预算。

大白话总结：上下文越长，允许生成的步骤越少；预算不够就先做最重要的事，不让计划无限膨胀。

改进方案：

- 用真实长会议测量任务数、首 Token 延迟和完成率，确认限制值是否合适。
- 对可合并的连续只读步骤做确定性合并。
- 用户打断后只重算受影响的后续步骤，不从头生成整份计划。

### 4. 复盘能力薄弱（P1）

当前方案：

- `replan_agent` 使用质量门禁检查结构化输出、缺失交付物和执行结果。
- 失败后生成结构化 `repair_plan`，把缺失输出和建议传给下一轮规划。
- 修复节点只做有限的结构修复，不把错误结果伪装成成功。

大白话总结：执行结束后会检查“结果是否真的交付”，需要重做时带着问题清单回到规划，而不是只盲目换一个参数。

改进方案：

- 把失败分成输入错误、工具错误、权限错误、外部状态变化和规划错误。
- 每类失败记录证据，避免复盘只依赖模型猜原因。
- 对高风险操作要求人工确认根因和替代路径。

### 5. 推理与执行的因果泄漏（P1）

当前方案：

- 工具观察结果、工具错误、计划和反思分别放在不同状态字段。
- 工具结果经过来源标签和间接注入检查，不把内部推测直接写成业务事实。
- Checkpoint 不保存完整 CoT 和原始工具日志，只保留恢复所需的受限状态。

大白话总结：模型的“猜测”和工具真正返回的“事实”分开存，失败时写的是失败，不会因为模型说了一句“可能成功”就变成成功记录。

改进方案：

- 为观察结果增加 `observed_at`、`source`、`confidence` 和 `error_category`。
- 执行器只接受公开的结构化 Action，不接受隐藏思维文本里的动作。
- 增加失败后重规划的因果追踪测试。

### 6. 长程任务视野坍缩（P1）

当前方案：

- `TaskAnchor` 在规划前提供总目标、硬约束和必需输出。
- 每个任务保留依赖、输入来源和输出键，执行后统一进入质量门禁。
- 预算和任务空间信息会随状态保留，避免完全依赖当前一步的局部上下文。

大白话总结：规划不是只盯着眼前一步，任务清单和总目标会一直放在状态里，最后还会检查整件事有没有完成。

改进方案：

- 为复杂任务增加阶段目标和全局预算/价值检查点。
- 外部状态变化时回到最近的阶段边界重算，而不是硬补当前步骤。
- 真实长链路验证“前面完成、后面改价/改口”时能否正确回溯。

### 7. 否定约束与隐性成本被忽略（P0）

当前方案：

- 输入层把“不要、不能、低于、不超过、除了、只看”等表达保存为 `TaskConstraint`。
- 规划生成后和工具执行前都会重新检查这些约束。
- 对预算、费用、金额、耗时等带数字的计划参数做确定性阈值校验。
- 工具策略、用户写权限和人工确认仍是最后一道门禁。

大白话总结：用户说的“不要做什么”和“最多花多少”不会只留在 Prompt 里，计划和真正执行工具前都会再对一遍。

改进方案：

- 补充例外、除外对象、单位换算和多条件组合规则。
- 把约束来源位置和检查结果展示到调试信息中。
- 增加“否定词在上下文末尾”“阈值藏在长句中”的回归样例。

### 8. 沉没成本锚定（P1）

当前方案：

- 计划有预算上限、重规划上限和重复计划熔断，不允许无止境打补丁。
- 工具失败会留下结构化错误，质量门禁可以要求重新规划。

大白话总结：前面已经花了很多 Token，也不能成为继续走错路的理由；达到失败边界就停下来重新判断。

改进方案：

- 为重规划增加“继续修补”和“推倒重来”的成本比较。
- 保留最短失败摘要，不把前面所有推理重新塞回上下文。
- 统计每次重规划带来的收益和额外 Token。

### 9. 概率世界中的确定性妄想（P0）

当前方案：

- 任务和工具调用支持 `confidence` 字段，规划层统一归一到 0～1。
- 低置信度会写入 `uncertainty_flags`，并随状态和 Checkpoint 传递。
- 低于门槛的外部副作用工具调用会被阻止，不能把可能结果直接当成确定事实。
- 工具结果仍由执行结果和结构化校验决定成功与否。

大白话总结：不确定就标出来；如果把握不够，尤其是外部写操作，系统会先停下，不让“可能是这样”直接驱动真实动作。

改进方案：

- 让 OCR、检索、分类和工具都返回统一的置信度与错误类别。
- 为不同工具设置不同置信度门槛，不能所有工具用同一个数字。
- 低置信度时优先请求补充材料或人工确认。

### 10. 反思递归和元认知膨胀（P2）

当前方案：

- 计划、反思和 CoT 不自动写入长期事实记忆。
- 质量门禁只保留结构化问题、建议和修复计划，不保存“反思的反思”。
- Checkpoint 对运行时状态有白名单和大小限制。

大白话总结：反思报告只用来修正当前任务，不会一层层把“我对上次反思的反思”继续塞进记忆里。

改进方案：

- 为反思设置最大层级和最大字符数。
- 反思必须引用原始执行证据，不能单独升级成事实。
- 只有被明确确认的总结才允许进入长期记忆。

## 本层完整工作流

`InputEnvelope/TaskAnchor` → 预算评估 → LLM 或确定性模板生成计划 → 计划结构/依赖/工具白名单/约束/置信度门禁 → 风险和人工确认 → 工具参数 Schema 校验 → 执行与错误隔离 → 重复失败/循环熔断 → 质量门禁与有限重规划 → 最终输出校验。

## 与输入层的接口

当前方案：

- 输入层提供 `TaskAnchor`、`InputEnvelope.budget`、`scope`、来源权限和可选 `task_id`。
- 规划层只使用这些字段，不重新解释用户身份，不允许文档或工具结果覆盖用户硬约束。
- 用户目标变化或约束变化时，输入层的复核结果会阻止旧计划继续执行。

大白话总结：输入层先把“目标、限制、权限和预算”写清楚，规划层拿这份清单做计划，并在执行前再核对一次。

改进方案：

- 用户改口时传递事件版本，让规划层明确知道哪条意图覆盖了哪条旧意图。
- 将约束来源位置和计划中的对应任务建立可追踪映射。

## 与记忆层的接口

当前方案：

- 规划状态带有 `thread_id`、`task_id`、`task_namespace`，不会跨任务随意取记忆。
- 计划、反思和工具原始日志不自动写入长期事实；只有显式确认的事实才进入记忆层。
- 记忆层召回的事实仍要带来源、时间和置信度，规划层不能把旧事实当成永远有效。

大白话总结：规划可以用记忆里的资料，但不会把自己的计划和猜测当成长期事实；旧事实是否仍有效要看时间和任务空间。

改进方案：

- 冲突记忆召回时明确标记当前版本、历史版本和待确认版本。
- 让规划门禁把记忆置信度纳入外部工具的动作门槛。

## 当前版本的边界

当前规划层只承诺：

1. 计划进入执行前会检查任务、依赖、工具和参数结构。
2. 重复计划、依赖循环和连续相同失败有停止边界。
3. 否定、排除、范围和常见数字阈值会在计划/执行前复核。
4. 低置信度外部动作不会直接执行，并且不确定性会留在状态里。
5. 计划、工具观察、错误和反思有不同字段和不同持久化边界。

当前不承诺：

1. 自动找到所有复杂任务的全局最优计划。
2. 自动识别所有隐含因果关系和所有单位换算。
3. 已经完成真实长会议、真实外部 API 和多副作用并发验收。
4. 已经完成长程价值函数、复杂根因归因和多模态规划。

## 本轮已完成（P0）

1. 计划任务 ID 唯一、执行顺序完整、依赖存在且无循环。
2. 工具名白名单、工具调用对象和参数对象结构门禁。
3. 计划生成后的约束复核，包含禁止动作和常见数字阈值。
4. 重复计划、规划次数和同一失败调用的熔断。
5. 任务/工具调用置信度字段、低置信度标记和外部动作门禁。
6. 规划失败不再偷偷改用默认工具计划，统一进入校验出口。
7. P0 回归测试覆盖未知工具、参数结构、依赖循环、重复 ID、预算超限和阈值违规。

## 本层明确不做

1. 不把 LLM 输出的自然语言思维链当作可执行指令。
2. 不允许规划层绕过工具注册、权限策略或人工确认。
3. 不把工具错误、猜测和计划写入长期事实记忆。
4. 不用无限重试掩盖工具不可用、权限不足或输入不完整。
5. 不在本轮提前引入复杂的全局优化器、多智能体协商或多模态融合。

## 本层亮点总结

1. **计划先验收再执行**：任务、依赖、工具和参数不符合规则就停，不会直接调用。
2. **失败有刹车**：重复计划、依赖死循环和同一错误连续重试都会触发熔断。
3. **限制条件不靠模型记忆**：否定词、阈值和禁止动作会在计划后、执行前再检查。
4. **不确定性不被抹平**：置信度会跟着任务和工具调用走，低把握的外部动作会被拦住。
5. **内部猜测与外部事实分开**：计划、工具结果、错误和反思各有边界，不互相冒充。
6. **和上下两层对得上**：输入层提供目标与权限，记忆层提供带范围的事实，规划层只负责把它们变成受控动作。

## 本层验收重点

1. 用真实长会议验证计划步骤数、首 Token 延迟、完成率和重规划次数。
2. 用模拟工具故障验证连续失败、超时、幂等重放和并行互等不会死循环。
3. 用“不要/除非/预算上限/用户改口”样例验证计划和执行前门禁都能拦截。
4. 用低置信度 OCR、检索和外部写工具验证不确定性不会被强行当成确定事实。
5. 验证计划失败后的 API 返回能保留错误原因，并且不会误报为成功。
