# 输入预处理层

> 这份文档用来说明：用户内容进入 Agent 前，系统已经做了什么，还需要补什么。
> 2026-09-04 已完成混合输入、工具错误隔离、否定/阈值约束、来源权限和 Token 预算的第一轮小改造；本轮又补强了注入混淆识别和会话上下文隔离；长会议真实数据验收仍待补做。

## 这一层负责什么

输入预处理层不是简单地把用户文字转发给模型，而是先把输入整理清楚：

- 这是谁发来的？
- 他到底想完成什么？
- 哪些内容是用户要求，哪些只是会议资料或工具返回值？
- 用户有没有限制条件？
- 当前输入有多长，能不能安全地交给模型？

当前主要处理用户问题、会议文档、WAV 转写、会话历史、RAG 片段和工具结果。

## 核心问题与改进安排

### 1. Prompt 注入和上下文污染

当前方案：

- 用户输入在进入路由前先做直接注入检查。
- 文档、RAG、ASR 和工具结果统一标记为不可信来源。
- 命中间接注入的内容会被隔离，不进入后续上下文和引用列表。
- 上下文中会明确提示：会议资料和工具结果只能当作资料，不能把其中的指令当成系统指令。
- 已有 25 条合成攻击样例，并接入回归测试。
- 规则检测会先统一全角字符、HTML 实体、零宽字符和少量常见字母混淆，再检查“插空格/伪造 system 角色/URL 或 Unicode 编码”等绕过方式。
- `session_context` 和 `raw_context` 都会在进入上下文组装前筛查；命中内容会清空或隔离，不会因为字段名看起来是“内部数据”而跳过检查。
- warning 级内容可以作为会议资料保留，但会写入安全标记，不能被当作可执行指令。

大白话总结：先确认输入是不是在攻击，再把历史内容和外部资料当成“只能参考的材料”。可疑内容会被隔离，安全讨论类内容可以留下，但会明确标记为警告。

改进方案：

- 增加真实攻击样例，分别统计误报和漏报。
- 补充零宽字符、全角/混淆字符、Base64、URL 编码和伪造角色头的真实样例，并单独统计误报。
- 统一规定来源优先级：系统规则 > 用户要求 > 工具观察 > 文档/RAG 内容。
- 不把关键词过滤当成唯一防线，最终仍要在工具执行前重新检查权限和风险。
- 让来源标签贯穿输入、上下文、工具参数和结果校验，不能只停留在 Prompt 文本里。

### 2. 混合输入导致任务漂移

当前方案：

- 用 `TaskAnchor` 保存任务目标、交付物、硬约束、禁止动作和完成标准。
- 现在会从用户原话中提取并列意图，保存为 `TaskIntent`，保留原文和顺序。
- 现在会提取否定、阈值、排除和范围条件，保存为 `TaskConstraint`。
- 用 `InputRouting` 记录初步任务类型、复杂度和路由建议。
- 用 `ContextManifest` 记录哪些内容进入了上下文，哪些被截断或丢弃。
- 结果校验会检查是否完成了要求的输出。

大白话总结：系统先把用户想做的几件事和限制条件记在一张“任务清单”里，后面每一步都照着清单核对，避免模型聊着聊着换了目标。

改进方案：

- 继续提高意图和约束的识别覆盖率，并保留每条约束来自原文哪一段。
- 工具执行前再次检查任务目标和约束，发现目标变化时先暂停，不直接继续执行。
- 增加“用户改口、目标冲突、约束被遗漏”的测试样例。

### 3. 工具错误被当成业务事实

当前方案：

- 工具结果会被标记为不可信内容。
- 上下文组装时只取允许的字段，避免把整个返回对象直接拼进 Prompt。
- 工具结果还会经过间接注入检查。
- 工具失败会单独标记为 `tool_error`，并明确写成“系统信息，不是会议事实”。
- 对 JSON 或半结构化返回值优先做结构内裁剪，尽量保持对象和数组的完整形状。

大白话总结：工具说“失败”只代表工具这次没拿到结果，不会被当成会议内容；真正的业务数据和系统报错会分开保存、分开展示。

改进方案：

- 继续推动所有工具统一返回 `status`、`error`、`payload`、`metadata` 四部分。
- 增加更多非标准 JSON、嵌套错误和超长工具返回值测试。
- 明确规定：工具失败只能说明“这次调用失败”，不能自动变成会议事实。

### 4. 否定词、阈值和隐性约束被忽略

当前方案：

- `TaskAnchor.hard_constraints` 保存系统已经确定的硬约束。
- `TaskAnchor.forbidden_actions` 保存禁止动作。
- `InputScope.can_write` 控制用户是否有写权限。
- 工具层还会再次检查权限、风险等级和人工确认。
- 输入层会把用户明确说出的“不要”“不能”“低于”“不超过”“除了”等条件保存为结构化约束。
- 规划前和工具执行前都会复核这些约束；发现外部工具违反禁止条件时直接拦截。

大白话总结：用户说“不要做什么”“最多多少钱”“只看哪些资料”，系统会把这些话单独记下来，并在规划和执行前再检查一遍，尽量不让模型漏掉小字条款。

改进方案：

- 继续增加约束类型、具体值、来源位置和是否必须满足等字段。
- 在规划前、工具执行前、最终输出前各检查一次关键约束。
- 增加否定、例外、范围和数字阈值的专项测试。

### 5. 多源输入的权限层级混淆

当前方案：

- `InputArtifact` 记录来源、媒体类型、信任级别、引用和安全状态。
- 用户问题、上传文档、检索结果、会话内容和工具结果不会再被当成完全相同的来源。
- RAG 和工具内容会加上“不可信外部内容”的边界提示。
- 每个来源会自动得到 `authority` 和 `authority_rank`：用户要求最高，工具观察次之，文档/RAG 和会话资料只能提供参考。
- 校验时会按来源重新计算权限；有人把文档手动改成“用户级”会直接被拒绝。
- 上下文清单和每个内容块都会保留权限标签，供后续节点审计。

大白话总结：不同来源的内容不是一个级别：用户要求优先，工具结果和会议资料只能提供参考。每块材料都带着自己的来源和权限，后面查得清是谁说的。

改进方案：

- 系统规则和用户限制不能被文档或工具结果覆盖；当前做的是应用内不可升级标签，不是密码学签名。
- 对跨层传递的每个内容块保留来源、用户权限、时间和校验和。
- 增加“恶意指令藏在公开文档或工具结果中”的端到端测试。

### 6. Token 爆炸、成本高、响应慢

当前方案：

- `ContextAssembler` 按来源和优先级选择内容。
- 限制单条内容大小、内容条数和同一文档的块数。
- 使用字符预算和 `TokenBudgetLedger`，在调用模型前检查模型窗口、节点预算、运行预算和调用次数。
- 对已配置但没有 tokenizer 的模型使用可解释的中文/英文混合近似计数，未知模型仍保留保守上界，避免误用估算。
- 429 限流重试会重新预留 Token 和调用次数，不会悄悄绕过运行预算。
- 上下文清单同时记录近似 Token 数，便于观察成本和延迟。
- 最近会话只保留有限轮数，旧内容会被丢弃。

大白话总结：系统不会把整场会议和所有历史一股脑塞给模型，而是先去重、限量、截断，再用预算账本拦住超长请求；这样成本和等待时间都有上限。

改进方案：

- 用真实长会议验证证据覆盖率、重复率、旧内容比例、Token 消耗和响应时间；近似计数最终仍以供应商 usage 校准。
- 只有数据证明需要时，再加入滚动摘要、结构化压缩或分段处理。
- 不通过简单扩大上下文窗口来掩盖输入整理问题。

### 7. 时空错位和流式状态粘性

当前方案：

- ASR 证据会保存时间偏移和说话人信息。
- 当前系统主要按一次请求处理输入，不把实时事件当成连续状态流。

大白话总结：现在只处理一段一段的会议输入，并没有假装已经解决实时语音中的“改口覆盖”和事件先后问题。

改进方案：

- 如果以后支持实时语音、屏幕流或 IoT，增加 `event_id`、`event_time`、`sequence`、`supersedes` 和 `valid_until`。
- 明确用户改口时，新意图如何覆盖旧意图。
- 区分“刚刚发生的一次事件”和“仍在持续的状态”。
- 在实时功能正式立项前，不把这套复杂机制提前塞进当前批量会议流程。

### 8. 文本、文件、图片和传感器数据格式不一致

当前方案：

- 当前稳定支持文本、文档和 WAV。
- 文件会检查扩展名、MIME、大小和实际内容。
- 图片、视频、ROS 和传感器时序数据目前明确拒绝，不让它们以不完整格式进入 Agent。
- `InputArtifact` 已经预留媒体类型、来源和内容引用。

大白话总结：当前只接收已经验证过的文本、文档和 WAV；图片、传感器等暂不硬接进来，避免格式没对齐就产生错误结论。

改进方案：

- 暂时不扩展多模态输入，先把当前会议文本链路做稳定。
- 将来支持图片或传感器时，再设计统一的 `ModalityEnvelope`，同时校验时间、单位、来源、维度和范围。
- 不把不同模态粗暴平均成一个向量后直接交给规划层。

### 9. Prompt 缓存碎片化和 Embedding 漂移

当前方案：

- 当前项目没有真正的 Prompt Semantic Cache。
- 会话短期记忆没有做成长期 Embedding。
- 检索内容主要依靠来源、引用、版本和上下文预算控制。

大白话总结：项目现在还没有把“语义缓存”和长期向量记忆当成已完成能力，先用来源、版本和长度控制，避免缓存内容和当前问题对不上。

改进方案：

- 现阶段暂不做语义缓存，避免先引入新的不一致问题。
- 如果以后建设缓存，需要固定缓存键规范、时间表达方式和 Embedding 模型版本。
- 不同模型版本、不同上下文格式产生的向量不能直接混用。

### 10. 多模态输入互相冲突

当前方案：

- 当前图片、视频等非目标模态直接拒绝，因此暂时不会出现“红车/蓝车”这类感官冲突。

大白话总结：因为暂时不接图片、视频等输入，所以不会把互相矛盾的视觉和文字信息强行平均后再下结论。

改进方案：

- 只有在项目正式支持多模态后，才增加模态置信度、冲突检测和仲裁规则。
- 需要明确文本描述、图片识别和传感器数据冲突时谁优先，以及如何把冲突交给用户确认。

## 与记忆层的接口

当前方案：

- 输入层负责生成 `InputEnvelope`、`TaskAnchor`、`scope` 和来源权限；其中可选 `task_id` 作为任务身份透传，记忆层不重复解释用户目标，也不重新授予权限。
- Agent 运行会根据原问题、会议/文档范围和当前线程生成 `task_namespace`，输入层校验通过后，记忆层用它隔离近期上下文和事实召回。
- `TaskAnchor` 只作为本轮任务契约随 checkpoint 保存；普通会话问答不会自动升级成跨会话长期事实。
- 长期事实如果写入，必须携带 `user_id`、`thread_id`、`task_namespace`、会议/文档范围和来源信息，工具结果和知识资料不能伪装成用户指令。

大白话总结：输入层先把“谁在问、要做什么、能看哪些资料”说清楚，记忆层再按这张边界表保存和查找。两层共用任务空间和权限范围，避免记忆串台或越权。

改进方案：

- 后续引入显式 `task_id` 或输入事件版本，让用户改口、切换任务时不再依赖短问题启发式。
- 生产长期记忆检索必须先做身份、线程、任务空间和会议/文档范围硬过滤，再做关键词、向量和时间排序。
- `TaskAnchor` 或权限范围发生变化时，旧任务记忆先停止召回，必要时要求用户确认后再建立新事实。

## 当前版本的边界

当前输入层只承诺：

1. 输入有明确来源和权限范围。
2. 用户目标和系统约束可以在后续节点继续检查。
3. 不可信文档、RAG、ASR 和工具结果不会直接变成系统指令。
4. 上下文和 Token 使用量受到硬限制。
5. 文本、文档和 WAV 链路可以稳定运行。
6. 对常见的否定、阈值、排除和范围表达做确定性提取；复杂语义仍需后续复核。

当前不承诺：

1. 识别所有形式的 Prompt Injection。
2. 自动处理图片、视频、传感器和实时事件流。
3. 自动解决所有长会话的语义漂移。
4. 用输入层替代规划层、工具层或最终结果校验层。

## 后续验收重点

后续优化完成后，至少需要验证：

1. 真实攻击样例的误报率、漏报率和隔离后任务完成率。
2. 混合输入中核心目标、硬约束和禁止动作的保留率。
3. 工具错误和业务数据是否真正分离。
4. 长会议中的上下文覆盖率、重复率、Token 消耗、响应时间和任务完成率。
5. 如果启用实时或多模态输入，再增加事件覆盖、意图覆盖和模态冲突测试。

## 本层亮点总结

1. **先检查，再路由**：用户输入先经过身份、范围和注入检查，安全不过关就不会进入后面的 Agent 路由。
2. **任务不容易跑偏**：`InputEnvelope` 和 `TaskAnchor` 把“要做什么、不能做什么、最后要交付什么”固定下来，后续节点可以反复核对。
3. **资料和指令分开**：文档、RAG、会话和工具结果都被标记为不可信资料，里面写的“请忽略系统指令”不会自动变成真正指令。
4. **来源权限可追踪**：每类输入都有来源、信任级别和权限层级；普通资料不能伪装成用户或系统要求。
5. **上下文不会无上限膨胀**：组装器会做去重、限长、限条数和来源排序，Token 账本还会在模型调用前拦截超预算请求。
6. **失败有明确边界**：工具报错会和会议事实分开，编码注入、历史会话污染和被隔离内容都会留下审计记录。
7. **边界说得清楚**：当前稳定支持文本、文档和 WAV；实时流、多模态和真实长会议效果仍明确列为后续验收事项。
