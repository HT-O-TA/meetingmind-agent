### 2. 历史和决策记录

- `优化路径记录/01`～`13`：记录每个阶段为什么这样改，里面的“下一步”和旧数字不代表当前状态。
- `六链路架构设计/第一版`、`第二版`：设计演进记录，不覆盖第三版之后的当前状态。
- `六链路架构设计/第三版`：保留总架构和取舍，但当前完成度以本清单上方的当前文档为准。
- `JD对标与项目收敛路线.md`：岗位对标和历史收敛路线，不能替代当前代码状态。

### 3. 非主线或旧格式材料

- `AI_Agent系统架构详细文档.docx`：旧架构参考，不作为实现说明。
- `面试.docx`：求职材料，不作为技术状态说明。
- `架构解析/*.html`：Markdown 的旧预览产物，不是编辑源；内容落后时以同名 Markdown 为准。
- `项目规划/第二项目_PatchAlign-Cpp立项与实施路线.md`：独立项目，不计入 MeetingMind 完成度。

## 本次已发现并修正的口径冲突

1. 项目总览原来写“下一步进入记忆层翻新”，但记忆层本地闭环已经完成；现改为先做文档收口和真实证据。
2. 输入层确认文档原来把记忆层翻新列为下一步；现改为真实/脱敏长会议验证。
3. 六链路第三版原来把规划层写成“待实施”；现改为规划层 P0 已完成第一轮，真实长任务效果待验收。
4. 六链路第三版原来直接排“完成剩余五层”；现改为文档治理 → 真实证据 → 固定演示 → 按证据翻新剩余三层。
5. 第一版、第二版六链路文档已明确标为历史版本，避免旧结论与当前实现混用。

## 后续治理规则

- 新功能先更新对应的当前层文档，再补优化路径记录；不在多个主文档复制同一段说明。
- 状态只用四种词：`已实现`、`有自动化证据`、`部分验证`、`未验证`。
- 每个“已完成”必须能指向代码、测试或真实演示；只有设计没有实现时写“设计完成”。
- 每个数字注明数据来源和日期；合成数据不能写成真实业务效果。
- 任何文档如果出现“下一步”，必须链接到[当前状态与下一步](./当前状态与下一步_大白话.md)，避免各写一套路线。
- 真实证据产生后，先更新[证据与限制](./证据与限制_大白话.md)，再更新项目总览和对应层文档。

## 清理边界

本轮不直接删除历史 Markdown、DOCX 或 HTML，原因是它们仍包含设计取舍和审计线索。等真实证据补齐后，再根据访问频率决定是否把旧格式材料移到单独的归档目录。
