感知输入层
架构：感知输入层接收三类来源的附件：文档库上传、会议附件、Agent 附件。所有来源统一经过接入治理模块做格式校验和安全检查，然后进入媒体类型路由，按文件类型分发到对应的本地感知模型管线。
图片路径：直接交给 Qwen3-VL 进行结构化提取，输出包括摘要、OCR 文字、视觉事实、决策项、待办项和不确定项。
音频路径：先经过 soundfile/soxr 做格式标准化，再进入 FunASR 管线，依次完成 ASR 转写、VAD 长音频切分、标点恢复、句级时间戳标注，最后通过 CAM++ 声纹嵌入做说话人聚类与发言对齐。
视频路径：先由 ffprobe 校验媒体信息，然后拆成两条并行链路——画面侧由 Qwen3-VL 提取摘要、OCR 和时间线，音轨侧由 FFmpeg 抽取音频后交给 FunASR 完成转写和说话人分离。两条链路的结果在证据文档层做音画融合，合并为统一的结构化输出。
三条路径的产出格式一致：带来源的非可信 Markdown 证据，明确标注来源文件、模型后端、时间戳、说话人、可核验事实、决策与待办、不确定项和降级信息。
这些结构化证据随后进入统一的下游管线：Document 入库 → 文本分块 → 向量索引与关键词索引双写。最终服务于四个消费场景——会议总结、决策提取、待办抽取、RAG 检索与 Agent 问答。

亮点：视频双路处理；输出结构化、可追溯。

面：我设计的不是给系统加一个图片上传按钮，而是一套本地多模态证据入口。图片由 Qwen3-VL 结构化提取，语音由 FunASR 生成说话人和时间戳，视频拆成画面理解和音轨转写两条链路做音画证据融合，最终统一转成带来源的非可信证据，进入文档分块、RAG 检索、会议总结和待办抽取闭环。同时对模型缺失、无音轨、解码失败和 Prompt Injection 做了明确降级与隔离。

意图理解层
架构：用户查询进入后，首先经过一条规则短路通道——如果匹配到问候语等简单模式，直接走 simple_qa_node，不进入后续分类流程。
通过短路的请求进入双轴分类。第一个轴是任务类型分类，将请求归入五个类别：QA（问答）、TODO（待办提取）、MINUTES（会议纪要）、CONTROVERSY（争议观点）、MULTI（多任务混合）。第二个轴是复杂度分类，将请求归入四个等级：S（Simple，简单直答）、R（Retrieval，需要检索）、C（CoT，需要链式推理）、A（Agent，需要多步工具调用）。两个轴的分类结果组合后，进入仲裁优先级链。
仲裁不是 5×4=20 种组合的穷举映射，而是一条瀑布式判断链，命中即停。最高优先级是多任务命中（MULTI），直接进入 COMPLEX 工作流由 plan_node 做 Plan-Execute 拆解；其次是单任务命中且复杂度为 C 或 A，同样进入 COMPLEX 但走该任务的深度推理版；再次是单任务命中且复杂度为 S 或 R，直接映射到对应的确定性节点（todos_node、minutes_node、controversy_node、simple_qa_node）；再往下是无任务命中但复杂度为 C 或 A，由复杂度接管走 cot_node 或 react_node；最低优先级是无任务命中且复杂度为 S 或 R，兜底走 simple_qa_node。
仲裁结果确定后，进入模型路由。复杂度同时驱动两个路由决策：策略路由（去哪个执行节点）和模型路由（用哪档模型）。任务类型决定模型能力的下限——确定性任务（TODO/MINUTES/CONTROVERSY）锁死在 plus 档位，只有 QA 类在 S 复杂度下有 turbo 空间；复杂度决定模型能力的上限——C 和 A 级别无论什么任务类型都用 max 档位。两条原则：任务类型管"能不能省"，复杂度管"省多少"。
最后是一道横切熔断规则：如果仲裁结果为 COMPLEX 但通道置信度低于 0.65，强制降级到 simple_qa_node。宁可大材小用，也不让低置信度的复杂流程产出不可靠结果。

亮点：任务类型优先，复杂度兜底，业务语义驱动路由，而非技术复杂度驱动路由。

面：意图理解层是系统的总指挥，做三件事：分类、仲裁、路由。双轴分类——任务类型决定走哪条业务管线，复杂度决定推理深度。仲裁是一条 6 级优先级的瀑布链，多任务最高、兜底最低，命中即停。分类结果同时驱动策略路由和模型路由——去哪个节点、用哪档模型，一次判断两个决策。最后加了一道置信度熔断，低置信度的复杂请求强制降级，宁可大材小用也不出不可靠的结果。

检索记忆层
架构：检索记忆层同时管理两类知识来源：文档证据和跨会话长期记忆。用户查询进入检索节点后，系统首先从服务端 JWT 构造访问上下文，将用户、部门、项目、会议和文档归属条件下推到召回阶段，先过滤权限再计算相关性，避免召回后过滤造成信息泄漏。
文档检索路径：查询可先经过 Multi-Query、HyDE 等查询改写，随后并行进入 BM25 关键词召回和 BGE-M3 稠密向量召回。多路结果通过加权融合或 RRF 合并，并根据配置选择是否使用 BGE-Reranker 精排。如果明确指定文档摘要，则直接读取该文档的完整分块，不混入长期记忆。
长期记忆路径：所有写入统一经过 UnifiedMemoryService。PostgreSQL 保存唯一主记录并生成统一的 memory_id，Redis 和进程内 LRU 只保存可重建的热索引，Milvus 作为派生向量索引，与文档共用集合并通过 resource_type/resource_id 区分资源。记忆向量在写入时预计算，查询时只编码用户问题；Milvus 不可用时回退到 PostgreSQL 中保存的预计算向量和结构化查询，不重新编码全部记忆。
跨源融合与输出：文档候选和记忆候选不会各自取完 Top-K 后直接拼接，而是转换成统一候选结构。系统先在各自来源内部归一化分数，再综合语义相关性、原始排名、记忆置信度、重要性和当前会议匹配度进行跨来源融合，必要时使用同一个精排模型重新排序，最后全局截取 Top-K。输出同时保留 document_id/chunk_id 或 memory_id，用于生成可追溯引用。

长期记忆写入的两道门：第一道是事实准入——用户明确提交的内容必须带请求来源，系统自动提取的事实必须带会议、文档或记忆引用，并达到置信度阈值；普通 Agent 回答不会直接沉淀，只有纪要、决策、待办和争议等结构化产物才会尝试写入。第二道是写入决策——新事实先与已有记忆比较，再执行 ADD、UPDATE、DELETE 或 NOOP。重复内容跳过，更新内容在同一事务中写入新记录并将旧记录标记为 superseded，保留事实变化轨迹而不是直接删除历史。

整个检索记忆链路使用冻结数据集做独立回归，固定检查 Recall、MRR、nDCG、跨权限泄漏率、事实准入、冲突处理、索引覆盖率和检索延迟，避免只用一次正常问答证明系统有效。
