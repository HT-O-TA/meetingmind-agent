一
设计基于 LangGraph 的 Agent Runtime，构建 S/R/C/A 四级复杂度路由与 Plan-Execute-Reflect 工作流，集成短期上下文记忆、长期知识记忆、Tool Calling及模型路由机制，基于模型路由策略，相比固定最高成本模型调用推理成本降低 **59%**。
1.你提到的“四级复杂度路由”具体是哪四个级别？
四级复杂度路由具体分为：

第一级是简单问答（S级），分数区间0.0到0.3。这类问题是单事实的，无需检索，也不需要推理，比如问候语、简单的定义类问题，直接回答即可。
第二级是检索类（R级），分数区间0.3到0.5。这类问题是事实型的，但需要查询资料，比如询问某个具体数据或时间，需要先检索再回答。
第三级是思维链推理（C级），分数区间0.5到0.75。这类问题需要1到2步推理，比如"为什么"类型的问题，需要一定的逻辑推导。
第四级是ReAct代理（A级），分数区间0.75到1.0。这类问题是多跳、多源的，需要多轮推理和工具调用，比如分析会议内容并提取行动项。

判断逻辑采用的是双阶段混合策略：首先尝试使用本地小模型进行分类，如果模型加载失败或连续输出相同结果，则回退到规则路由。规则路由基于关键词匹配，比如问候语关键词、多任务标记、推理关键词、检索关键词等，同时结合问题长度和问题数量来判断。

追：你提到“0.3/0.5/0.75”这些分界点，但未说明如何确定。是凭经验？还是通过A/B测试找到成本-效果最优解？
是比较合理的人工阈值，后期可以通过采 1000 条真实问题，人工标注正确级别，然后用这批数据对分界点做 ROC分析，找到误判代价最低的切割点。


2.这个 59% 是怎么算出来的？你的 Baseline是什么？
数据是基于理论推算得出的。
计算公式是：原成本减去优化后的成本，再除以原成本，得到降低的比例。测试集使用100条人工测试用例，覆盖多种类别和难度，以确保评估的准确性

基线是假设所有问题都使用最高成本的ReAct模式进行处理，而优化后的成本是根据复杂度分类结果，将不同级别的问题路由到不同成本的处理模式。

具体来说，简单问题只需要本地小模型判断，成本极低；
检索类问题需要调用向量检索和基础LLM；
思维链推理需要中等规模的LLM；
只有复杂问题才需要完整的ReAct模式。
通过这种分级处理，可以避免简单问题占用高成本资源，从而显著降低整体推理成本。


3.路由过程中，如果“简单问题”被误判为“复杂问题”，或者反之，你有哪些兜底机制来防止体验降级？

路由误判是 Agent 系统的核心风险，我们从 误判方向 分别兜底：

简单问题误判为复杂问题 ——这类误判浪费成本但不影响体验，主要通过 置信度熔断 兜底：当 COMPLEX 路由的综合置信度低于 0.65 阈值时，自动降级为 SIMPLE_QA，避免低置信度问题走高代价路径。同时有 双轨交叉验证 ——复杂度分类和任务类型检测两条独立轨道，通过冲突仲裁纠正单轨误判。

复杂问题误判为简单问题 ——这类误判直接影响体验，更危险。我们通过三层兜底：第一层是 兜底分类器 ，通过推理关键词和问题结构特征识别复杂度；第二层是 Reflect 阶段的质量回检 ，如果 Plan-Execute-Reflect 检测到回答不完整，会动态生成补丁子任务重新执行；第三层是 容错系统 ，通过重试 + 熔断 + 降级策略保证服务可用性。

总结来说就是： 路由前双轨交叉验证、路由中置信度熔断、路由后 Reflect 质量回检 + 容错降级 ，形成完整的防误判兜底链路。

4.你的Memory是怎么实现的，当出现长上下文时有什么处理方法

我们的记忆系统采用 三层存储架构 ：

短期记忆 ：存储在内存 + Redis 缓存，按会话隔离，最多保留 100 条。当对话轮次超过 10 轮时，旧轮次会被标记为待压缩。

长期记忆 ：存储在 PostgreSQL 并通过 Redis 热点缓存加速查询。支持关键词搜索、按会话/会议过滤、重要性排序。跨会话持久化。

实体关系 ：追踪用户在对话中提到的实体（人、项目、决策）和关系，用于个性化和知识图谱增强。

长上下文处理 ：采用 多级压缩策略 ——

1. 先用 tokenizer 精确计数，未超限直接通过
2. 超限时用 LLM 做语义压缩（提取相关信息、删除冗余、合并相似内容）
3. LLM 不可用时降级为按比例截断或按 token 限制截断
会话隔离通过四层 ID 体系保证（user → session → conversation → meeting），避免数据串会话。




二
构建企业级 Hybrid RAG 检索系统，基于 BM25 + BGE-M3 Dense/Sparse Hybrid Retrieval，结合 RRF 融合、BGE-Reranker 精排，引入知识图谱增强实体关系检索，实现知识检索 Recall 提升至 **86.1%**。
1.你的 Query Rewrite 具体用了什么策略？在实际跑的时候，Rewrite 带来的延迟增加你是怎么解决的？

我们的 Query Rewrite 采用了 HyDE（假设性文档嵌入） + Multi-Query（多查询分解） + Step-back （退一步推理）三策略融合：
HyDE ：让 LLM 生成 3 个假设性答案，用假设文档做向量检索，绕过 query-document 的语义鸿沟。
Multi-Query ：将复杂问题分解为多个子问题并行检索，覆盖多维度信息。
Step-back ：退一步识别核心概念和扩展背景，发现隐含相关信息。

延迟优化 采用了四层方案：
1. 分级启用 ：根据查询复杂度选择启用哪些策略，简单查询直接跳过
2. 快速降级 ：任何策略失败立即回退到原始查询，不阻塞
3. 并发执行 ：多路查询生成后并发检索，而非串行
4. 结果限制 ：最多扩展 5 个查询，避免膨胀

2.你提到了“知识图谱增强检索”。这个图谱是离线预先构建的，还是在线动态抽取的？有没有做知识的抽取，怎么做的？

我们的知识图谱采用 离线预构建 + 可选 Neo4j 持久化 的方案：

构建时机 ：文档入库时异步触发图谱构建，不会阻塞主流程。先通过正则规则快速抽取实体和关系，再用 LLM 补充语义层面的抽取，确保召回率。

持久化 ：默认使用内存索引（速度快），也支持可选的 Neo4j 持久化（通过 ENABLE_NEO4J_PERSISTENCE 开关），应用启动时从 Neo4j 加载到内存。

抽取策略 ：实体和关系抽取都采用"规则 + LLM"双轨并行——规则匹配保证速度和确定性，LLM 抽取补充语义理解能力，两者结果合并去重。

增强检索 ：向量检索 + 图谱增强的融合方案——先用向量检索召回候选，再从 Query 中抽取实体做 2-hop 图谱扩展，最后按 0.7 × 向量分 + 0.3 × 图谱权重 融合重排序，同时补充图谱命中但向量未命中的"漏网之鱼"。

3.这个 86.1% 的 Recall 是怎么评估出来的？你有自己标注测试集吗？Ground Truth（标准答案）是怎么来的？

我们的评估基于 AliMeeting 会议语料库 （217 个会议转录文档），自动生成了 500 个测试问题，覆盖事实型、推理型、列表型三类问题。
Ground Truth 构建 ：对每个文档生成模板化问题，并标注该文档 ID 为唯一正确答案。同时截取文档原文前 50 字作为 expected_answer 。
评估方法 ：由于模板问题本身没有语义信息，实际检索时用 expected_answer 的前 50 字作为语义查询，通过 BM25 + BGE-M3 混合检索 + RRF 融合获取 Top-10 结果，检查是否命中目标文档。
结果 ：全量 500 题的 Recall@10 为 93.6%，其中 medium 难度（会议决策+计划方案）的 Recall@10 为 86.1%。
当然这个评估有局限性——Ground Truth 是自动生成的单标签，且查询用的是答案片段而非真实用户提问。后续如果要更严谨，需要引入人工标注的多标签测试集。



三
搭建基于 FastAPI、Redis、RabbitMQ 的异步 AI 服务架构，实现 Agent 执行、文档解析及向量化流程解耦，并通过缓存与异步任务机制提升系统稳定性。
1.为什么选择 RabbitMQ 而不是 Redis 的 Pub/Sub 或者 Kafka？在 Agent 这种长耗时任务里，RabbitMQ 在你的架构中具体承担了哪一块的解耦（是文档解析、向量化，还是 LLM 推理）？
RabbitMQ可以做到持久化，Redis 的 Pub/Sub不行，当前项目不需要用到Kafka这种高吞吐，会带来不必要的运维成本，承担解耦包括文档解析、向量化、实体抽取、KG构建、长耗时任务
2.压测下的“零失败”，在工程上通常意味着你做了很好的容错。当 RabbitMQ 的消费者处理超时，或者下游 LLM API 触发限流（Rate Limit）时，你的代码是怎么处理的？有重试机制吗？

我们的容错体系是 四层防御 ：

第一层 RabbitMQ 连接 ：实现自动心跳检测和断线重连，连接建立本身也有 3 次重试 + 5 秒间隔。队列配置了消息 TTL 和最大长度，防止积压。

第二层消费者 ：消息处理成功自动 ACK，异常自动 NACK 回队列重新投递。对于批量向量化任务，单个 chunk 失败不阻塞整批，部分成功也能完成。

第三层 LLM 限流 ：专门针对 429 RateLimitError 做了处理——优先解析 Retry-After 响应头，没有则用指数退避（5s → 10s → 20s），最多重试 3 次。非限流异常直接抛出，不浪费重试预算。

第四层容错系统 ：通用的熔断器 + 降级框架。当 LLM API 连续失败 5 次，熔断器 OPEN，后续请求直接走降级策略（返回缓存或默认回复），60 秒后进入 HALF_OPEN 试探恢复。

这套机制保证了在 RabbitMQ 消费超时或 LLM 限流时，系统不会雪崩，而是优雅降级。


四
基于 FastMCP 构建标准化 Tool Calling 与企业 Workflow，实现 Agent 与企业办公系统的统一接入，支持会议纪要生成、任务同步及知识沉淀等自动化流程。

1.你为什么要引入 MCP (Model Context Protocol)？直接用 LangChain 的 Tool 装饰器或者自己写一个 Function Calling 的封装不行吗？MCP 解决了什么核心痛点？

我们引入 MCP 主要解决了 三个核心痛点 ：

第一，异构系统的统一接入 ：项目需要集成飞书、GitHub、Jira、Notion 等外部系统，每个系统的认证、API 风格、数据格式都不同。用 LangChain Tool 装饰器的话，每个工具都要手写 Schema、异常处理、认证逻辑。MCP 提供了标准化协议，我们只需要实现 MCP Server 封装各系统的 API，Client 端通过协议自动发现工具、生成 Schema。

第二，工具的动态扩展 ：业务场景变化时需要快速新增工具。如果用 LangChain，每加一个工具都要改代码、重启应用。MCP 支持运行时注册新的 MCP Server，热加载工具列表，不需要重启。

第三，统一的调用抽象 ：内部工具（如向量检索、摘要生成）和外部工具（如发送飞书消息、创建 Jira Issue）对 LLM 来说完全透明——统一的 call_tool(tool_id, params) 接口，自动路由到正确的服务。这样 Agent 可以灵活组合内部能力和外部办公系统。

实际效果是：新增一个外部系统的工具集成，从 原来的 2-3 天 缩短到 半天 ，且可以随时热更新。

2.在 Agent 调用工具时，你是如何处理参数校验和错误恢复的？比如，用户说“帮我约李四开会”，但系统里有两个“李四”，或者李四的时间冲突了，你的 Agent 会怎么做？

我们的参数校验和错误恢复是 五层防御体系 ：

第一层 Schema 校验 ：每个工具都有 ToolMetadata 定义参数的类型、必填、枚举值、范围限制。执行前自动校验，不通过直接返回错误，不会把脏参数传给下游。

第二层参数归一化 ： _prepare_tool_arguments 会自动从用户问题、会话历史、实体解析中补全缺失参数。比如用户说"约李四开会"，系统会自动解析"李四"为 user_id，补全默认时间。

第三层双重重试 ：Agent 层做 2 次快速重试，Executor 层再做 3 次指数退避重试（1s→2s→4s）。对于临时性故障（网络抖动、瞬时限流）能自动恢复。

第四层 Reflect 自愈 ：如果重试仍然失败，反思节点会做确定性错误检查和 LLM 深度评估，生成 _build_repair_plan 补丁子任务，动态插入到 DAG 中。比如检测到"时间冲突"，会自动生成"查询可用时间"的补丁任务。

第五层 Human-in-the-Loop ：对于歧义问题（两个"李四"）或需要用户确认的操作，通过 request_confirmation 暂停执行，等待用户选择后继续。

以"帮我约李四开会"为例：系统先做实体解析发现两个"李四"→触发人机协作让用户选择→确认后查询时间槽→发现冲突后推荐替代时间→用户确认后创建日历事件。整个过程对用户是自然的多轮对话体验。

3.你说实现了“统一接入”，如果我现在要接入一个没有 MCP Server 的老旧系统（比如一个只有 SOAP 接口的内部 HR 系统），你的架构怎么兼容？

我们的架构采用了 适配器模式 + 双通道接入 来兼容老旧系统：

适配器层 负责协议转换：SOAP/COM/数据库等协议细节封装在适配器中，统一转换为标准 JSON 接口。比如 HR SOAP 系统，我们创建 HRSOAPAdapter ，内部用 zeep 调用 SOAP WebService，将 SOAP 对象转换为 {"success": True, "data": {...}} 标准格式。

接入层有两个通道 ：

- 通道 A（快速接入） ：通过 ToolRegistry.register() 直接注册为内部工具，适合简单场景，新增工具只需写适配器 + 注册两步
- 通道 B（标准协议） ：封装为 MCP Server，适合复杂场景或多 Agent 共享，通过 MCP 协议动态发现
以接入 SOAP HR 系统为例，开发步骤是：

1. 创建 HRSOAPAdapter 封装 SOAP 调用逻辑
2. 定义 ToolMetadata 描述工具的参数、类型、风险等级
3. 通过 ToolRegistry.register(tool, executor) 注册
4. Agent 即可通过统一的 call_tool(tool_id, params) 调用
这种方式的好处是： 协议隔离、统一接口、易于测试、易于替换 。未来如果 HR 系统从 SOAP 升级为 REST，只需修改适配器内部实现，Agent 层面完全无感。


五
建立覆盖 Prompt 管理、Bad Case、Benchmark、回归测试及 RAGAS 的 AI Evaluation Pipeline，结合 Agent 执行轨迹分析与 Reflection 机制，对检索、Agent、Tool 等核心能力持续评估。
1.RAGAS 的 Faithfulness（忠实度） 指标，它的底层原理是什么？如果 RAGAS 打分很低，你通常怎么排查是检索（Recall）的问题，还是生成（Generation）的问题？

原理是将 LLM 生成的答案拆解为多个"原子陈述"，然后逐一验证每个陈述是否能在检索到的上下文中找到支撑。

排查步骤：
1. 先用 RAGAS 指标组合定位大方向 ：看 Context Recall 指标——如果 Recall 低，说明检索层有问题，文档没找到；如果 Recall 高但 Faithfulness 低，说明是生成层的问题，LLM 在胡说。
2. 检索层深挖 ：如果是检索问题，我会检查——数据分块粒度是否匹配查询模式、Embedding 模型是否适配领域、Top-K 和相似度阈值是否合理、是否缺少 BM25 关键词检索的补充。
3. 生成层深挖 ：如果是生成问题，我会检查——Prompt 是否有明确的"忠实约束"、注入的上下文是否完整无歧义、LLM 的 Temperature 是否过高、是否需要增加答案验证步骤。
4. 最后通过 Bad Case 库做精准迭代 ，对失败案例分类，针对性地调优检索策略或 Prompt。
