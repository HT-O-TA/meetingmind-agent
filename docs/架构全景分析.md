# MeetingMind Agent 架构全景分析

> 本文档基于对项目代码的全面分析，记录 10 层核心架构 + 7 层横向支撑体系的实现现状、优点与缺点。

---

## 第一部分：10 层核心架构

---

### 第1层：感知输入层

  实现：
  - API 端点（[agents.py](file:///f:/project/meetingmind-agent/backend/app/api/v1/endpoints/agents.py)）接收 question、meeting_id、session_id、conversation_id、document_ids 等参数。
  - [SessionContext](file:///f:/project/meetingmind-agent/backend/app/agents/session_context.py) 统一管理四层 ID 体系：user_id → session_id → conversation_id → meeting_id，自动生成 thread_id = f"{session_id}:{conversation_id}"。
  - [MultimodalGateway](file:///f:/project/meetingmind-agent/backend/app/services/multimodal_gateway.py) 提供多模态输入管道：格式校验 → 大小限制 → 安全检测 → 内容提取 → 统一文本转换。
  - [ContentSafetyService](file:///f:/project/meetingmind-agent/backend/app/services/content_safety.py) 对上传文件做安全检测。
  - `/query-multimodal` 端点支持文件上传（图片/音频/文档），处理结果合并到 question 中。

  优点：
  - 四层 ID 体系消除了 session_id/thread_id/meeting_id 的语义重叠，会话隔离严格。
  - 多模态管道支持图片、音频、文档三类输入，安全检测前置。
  - API 入口结构化，支持普通/流式/批量/多模态四种请求模式。
  - [SessionContext](file:///f:/project/meetingmind-agent/backend/app/agents/session_context.py) 的 `get_config()` 直接生成 LangGraph 所需的 `thread_id` 和 `configurable`，与图执行层无缝对接。
  - `conversation_id` 自动生成（基于 `session_id` + 时间戳），前端无需关心 ID 生成逻辑。

  缺点：
  - 多模态管道的 ASR（语音转文字）依赖外部服务，断网时无降级方案。
  - 大文件上传缺乏分片处理机制，50MB 上限可能阻塞事件循环。
  - SessionContext 未持久化到数据库，服务重启后 conversation_id 丢失。

  ### 第2层：安全护栏层（输入）

  实现：
  - [risk_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 双轨风险评估：
    - 第一轨：[RiskRuleService](file:///f:/project/meetingmind-agent/backend/app/services/risk_rule_service.py) 可配置规则检测（数据库规则 + 硬编码兜底 + Redis 缓存 + 热加载）。
    - 第二轨：[SemanticRiskService](file:///f:/project/meetingmind-agent/backend/app/services/semantic_risk_service.py) LLM 语义风险判断（仅规则未命中时触发，带缓存）。
  - [prompt_injection_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 双轨注入检测：
    - 规则检测：正则 + 关键词，覆盖 5 种注入类型（指令覆盖、角色劫持、数据外泄、权限提升、链式注入）。
    - LLM 深度检测（可选，受 INJECTION_GUARD_DEPTH 控制）。
  - [graph.py](file:///f:/project/meetingmind-agent/backend/app/agents/graph.py) 路由：route → injection_check → (block/reject, pass → risk)。
  - 高风险操作（HIGH/CRITICAL）触发 confirmation_node 人工确认。

  优点：
  - 规则检测 + 语义检测双轨并行，兼顾速度和深度。
  - 风险规则可配置、可热加载，业务方无需改代码即可调整策略。
  - Prompt Injection 防护前置在意图路由之前，避免恶意指令污染后续流程。
  - 注入检测覆盖 5 种类型（指令覆盖/角色劫持/数据外泄/权限提升/链式注入），规则表 + LLM 双轨互补。
  - [RiskRuleService](file:///f:/project/meetingmind-agent/backend/app/services/risk_rule_service.py) 实现了"数据库规则 + 硬编码兜底 + Redis 缓存 + 热加载"的四层保障。

  缺点：
  - 语义风险检测的 LLM 调用受网络延迟影响（~1-3s），无异步非阻塞降级。
  - 注入检测规则表硬编码在代码中，不可配置扩展。
  - 输入护栏与输出护栏不对称：输入层有注入检测，但输出层缺乏对 LLM 生成内容的注入后效应检测。

  ### 第3层：意图理解层

  实现：
  - [IntentRouter](file:///f:/project/meetingmind-agent/backend/app/services/intent_router.py) 统一路由入口，5 步决策链：
    - Step 1: 问候语检测（最高优先级 → SIMPLE_QA）
    - Step 2: 复杂度分类（[ComplexityClassifier](file:///f:/project/meetingmind-agent/backend/app/services/complexity_classifier.py)，S/R/C/A 四级）
    - Step 3: 任务类型检测（关键词 + [SemanticMultiTaskDetector](file:///f:/project/meetingmind-agent/backend/app/services/semantic_multi_task_detector.py) 语义多任务）
    - Step 4: 冲突仲裁（解决复杂度分类与任务检测的矛盾）
    - Step 5: 输出 [RouteDecision](file:///f:/project/meetingmind-agent/backend/app/agents/state.py)（含 confidence/candidates/decision_trace）
  - [route_agent](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 优先使用 IntentRouter，异常时降级到原 ComplexityClassifier 逻辑。
  - API 响应携带 route_decision、route_confidence、route_candidates、route_decision_trace。

  优点：
  - 统一入口消除了 complexity_classifier 与 _detect_task_type 的逻辑相互覆盖问题。
  - 语义多任务检测双轨融合：关键词命中直接判定（<1ms），未命中走 LLM 语义检测。
  - RouteDecision 结构化输出，前端/日志可获取完整决策链路和候选项。

  缺点：
  - SemanticMultiTaskDetector 的 LLM 调用增加 ~1-2s 延迟，无快速跳过机制（简单问题也会触发语义检测）。
  - 冲突仲裁规则硬编码在 IntentRouter._arbitrate 中，不可配置。
  - 路由决策缓存缺失，相同问题重复路由浪费 LLM 调用。

  ### 第4层：记忆层

  实现：
  - [retrieve_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 多路召回：
    - 语义检索（Embedding + 向量数据库）
    - BM25 关键词检索
    - 稀疏向量检索
    - [知识图谱](file:///f:/project/meetingmind-agent/backend/app/services/knowledge_graph.py)增强检索（Neo4j，深度 2 跳）
  - [Reranker](file:///f:/project/meetingmind-agent/backend/app/services/reranker.py) 重排序，支持多路召回结果融合。
  - [long_term_memory](file:///f:/project/meetingmind-agent/backend/app/services/long_term_memory.py) 长期记忆：会话摘要存储 + 上下文注入。
  - route_agent 阶段预注入历史会话记忆到 session_context。
  - [Checkpointer](file:///f:/project/meetingmind-agent/backend/app/agents/checkpointer.py) 基于 Redis 的短期记忆持久化，支持会话恢复。

  优点：
  - 多路召回 + 重排序 + 知识图谱三层检索体系，召回率高。
  - **五层记忆架构**（[Memory](file:///f:/project/meetingmind-agent/backend/app/models/memory.py) 模型）：
    - `working`：工作记忆（当前对话上下文）
    - `short_term`：短期记忆（会话级，PostgreSQL + Redis）
    - `long_term`：长期记忆（用户/会议级持久化）
    - `episodic`：情景记忆（历史决策、反思结果）
    - `semantic`：语义记忆（知识图谱、实体关系）
    - 每条记忆含 `importance_score`（重要性）、`relevance_score`（相关性）、`confidence_score`（置信度）三维评分。
  - 长期记忆在路由阶段预注入，所有路径（包括 simple_qa）都能感知历史。
  - [RedisCheckpointer](file:///f:/project/meetingmind-agent/backend/app/agents/checkpointer.py) 支持会话恢复，thread_id 精确隔离，支持断点续传。
  - [MemoryStore](file:///f:/project/meetingmind-agent/backend/app/services/memory_store.py) 采用 PostgreSQL 主存储 + Redis 缓存的双存储架构，热点数据自动升级。

  缺点：
  - 长期记忆的遗忘机制缺失：历史摘要无限累积，上下文会越来越长。
  - 检索结果缺乏来源可信度标注，低质量文档可能稀释答案质量。
  - 知识图谱依赖 Neo4j，部署复杂度高，且图谱更新与文档变更不同步。

  ### 第5层：规划层

  实现：
  - [plan_agent](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) LLM 驱动的任务规划：
    - 输出 Plan 结构：analysis + tasks + execution_order + parallel_groups + tool_calls。
    - 支持 replan（基于 reflection 的 repair_plan 重新规划）。
  - [PlanBudgetGuard](file:///f:/project/meetingmind-agent/backend/app/services/plan_budget_guard.py) Token 预算保护：
    - 生成前：评估可用 token，动态限制任务数（8→4→2→1）。
    - 生成后：校验 JSON 完整性、tasks/execution_order/parallel_groups 对应关系。
    - 极端复杂场景：渐进式两阶段规划（骨架 → 子任务细化）。
  - [template_planner](file:///f:/project/meetingmind-agent/backend/app/agents/tools/template_planner.py) 模板匹配规划，常见问题类型快速匹配模板。
  - [plan_validator](file:///f:/project/meetingmind-agent/backend/app/agents/tools/plan_validator.py) 计划验证：语法检查 + 逻辑检查 + 质量评估。
  - [repair_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) JSON 修复，解析失败时尝试修复。

  优点：
  - Token 预算保护从源头防止 JSON 截断，计划截断率显著下降。
  - 模板匹配 + LLM 规划双轨：常见问题走模板（快速），复杂问题走 LLM。
  - 计划验证 + 自动修复 + 重规划三级保障。
  - 渐进式规划（[PlanBudgetGuard](file:///f:/project/meetingmind-agent/backend/app/services/plan_budget_guard.py)）支持极端复杂场景：先生成高层骨架，再对子任务细化。
  - 计划结构设计完整：`parallel_groups` 支持并行分组，`tool_calls` 显式声明工具依赖，`execution_order` 保证执行顺序。

  缺点：
  - 渐进式规划仅设计了 prompt，未完整实现两阶段调用逻辑。
  - parallel_groups 的生成依赖 LLM 自觉输出，缺乏结构化引导（如依赖图自动分组）。
  - 模板库覆盖面有限，新业务场景需手动添加模板。

  ### 第6层：人机确认层

  实现：
  - [confirmation_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 人工确认流程：
    - 检测 requires_confirmation 标志。
    - 设置 confirmation_status = "pending"，等待用户确认。
    - 支持 confirm/reject/cancel 三种响应。
  - [HITLService](file:///f:/project/meetingmind-agent/backend/app/agents/human_in_the_loop.py) 人机协作服务：
    - 确认请求管理、状态持久化、超时处理。
    - 支持多种确认类型（CONFIRM/RISK/DELETE 等）。
  - graph.py 中的 conditional_edges 实现 confirmation → (execute | cancel) 路由。

  优点：
  - 高风险操作强制人工确认，防止误操作。
  - 确认状态持久化，用户可异步响应。
  - 超时自动取消机制。
  - 与 [RedisCheckpointer](file:///f:/project/meetingmind-agent/backend/app/agents/checkpointer.py) 联动实现"断点续传"：确认后从断点恢复执行，无需重跑整个流程。
  - [HITLService](file:///f:/project/meetingmind-agent/backend/app/agents/human_in_the_loop.py) 支持多种确认类型（CONFIRM/RISK/DELETE/SENSITIVE），每种类型有独立的 prompt 和超时配置。

  缺点：
  - 确认界面信息不够丰富：用户只看到操作描述，看不到完整上下文（影响哪些数据、是否可撤销）。
  - 不支持多轮确认交互（如"你确定吗？"二次确认）。
  - 确认超时时间硬编码，不同风险级别无法配置不同超时。

  ### 第7层：执行工具层

  实现：
  - [execute_agent](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 执行引擎：
    - [ParallelExecutor](file:///f:/project/meetingmind-agent/backend/app/services/parallel_executor.py) 真正并行执行：依赖拓扑排序 → 波次并行（asyncio.gather + Semaphore）→ 结果汇聚 → 完整性检查。
    - 单任务超时控制（默认 60s）、错误隔离（单任务失败不阻塞其他）。
    - 全部失败触发 replan，部分失败降级继续。
  - [ToolExecutor](file:///f:/project/meetingmind-agent/backend/app/agents/tools/executor.py) 工具调用：
    - 内置工具：会议搜索、文档检索、待办提取、纪要生成、争议识别等。
    - [动态工具发现](file:///f:/project/meetingmind-agent/backend/app/agents/tools/dynamic_tool_discovery.py)：MCP Server 工具自动注册。
    - [ToolPolicy](file:///f:/project/meetingmind-agent/backend/app/agents/tools/policy.py) 工具权限控制。
  - [QualityGate](file:///f:/project/meetingmind-agent/backend/app/services/quality_gate.py) 统一质量门禁：
    - Gate 1: 结构性检查（确定性，无 LLM）。
    - Gate 2: 单次 LLM 质量评估。
    - 决策：score < 0.5 → replan | 0.5-0.7 → polish | >= 0.7 → pass。

  优点：
  - ParallelExecutor 实现了真正的 asyncio.gather 并行，多产物生成耗时降低 50%+。
  - QualityGate 单次 LLM 评估替代 replan + reflection 双重评估，延迟降低 1-2s。
  - 工具系统支持动态发现、权限控制、并行执行。
  - 执行结果通过 `execution_result` 完整记录（total/completed/failed/skipped），可观测性强。
  - 工具元数据（[ToolMetadata](file:///f:/project/meetingmind-agent/backend/app/agents/tools/metadata.py)）含风险级别和权限要求，`ToolPolicy` 做细粒度访问控制。

  缺点：
  - 并行执行的任务间数据传递通过共享 state 字典，缺乏类型安全。
  - QualityGate 的 LLM 评估 prompt 硬编码，不同业务场景无法定制评估维度。
  - 工具执行缺乏分布式调度能力，单机并行度受 GIL 和资源限制。

  ### 第8层：反思反馈层

  实现：
  - [reflection_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 三层反思：
    - Layer 0: [DeterministicErrorChecker](file:///f:/project/meetingmind-agent/backend/app/services/deterministic_error_checker.py) 确定性检查（<10ms，无 LLM）：数字一致性、实体一致性、结构完整性、内部一致性。
    - 命中硬错误 → FastRetry（跳过 LLM 评估，直接重生成）。
    - Layer 1: LLM 深度评估（[ReflectionSystem](file:///f:/project/meetingmind-agent/backend/app/agents/reflection.py) 5 维度评估 + 事实一致性校验）。
  - [ReflectionMemoryService](file:///f:/project/meetingmind-agent/backend/app/services/reflection_memory_service.py) 反思记忆持久化：
    - 异步保存（fire-and-forget，不阻塞主流程）。
    - 相似历史反思查询（Jaccard 相似度 + Redis 缓存）。
    - 用户错误模式统计。
  - QualityGate 历史反思参考注入（评估时查询相似历史反思作为参考）。

  优点：
  - 确定性错误检查实现 FastRetry 快速路径，硬错误延迟从 ~2s 降到 <10ms。
  - 反思记忆持久化形成反馈闭环，相似问题的评估准确率提升。
  - 异步写入不阻塞主流程，响应延迟影响 <10ms。
  - [DeterministicErrorChecker](file:///f:/project/meetingmind-agent/backend/app/services/deterministic_error_checker.py) 覆盖 4 类硬错误：数字矛盾、实体冲突、结构缺失、内部矛盾，检查结果有明确的 error_type 分类。
  - 反思评估结果含 `dimensions`（各维度分数）、`structural_errors`（结构性错误）、`evaluation_method`（评估方法标记），可精细定位问题。

  缺点：
  - DeterministicErrorChecker 的数字一致性检查可能误报（合理推断的数字被判为错误）。
  - ReflectionMemoryService 的相似度算法较简单（Jaccard），未使用向量相似度。
  - 跨模型交叉验证（CrossModelEvaluator）仅设计了架构，未完整实现。

  ### 第9层：安全护栏层（输出）

  实现：
  - [validate_node](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 输出验证：
    - 格式校验：answer/minutes/todos/controversies 结构完整性。
    - 内容校验：必填字段、空值检查、类型检查。
    - 引用校验：citations 完整性。
  - 输出内容过滤：敏感信息检测、隐私数据脱敏。
  - [validation_errors](file:///f:/project/meetingmind-agent/backend/app/agents/state.py) 记录所有验证错误。
  - 降级链：输出不完整时尝试修复，修复失败返回降级响应。

  优点：
  - 结构化输出验证覆盖所有产物类型（QA/纪要/待办/争议）。
  - 验证错误记录完整，便于排查。
  - 降级链设计合理，不会因验证失败而完全无响应。

  缺点：
  - 用户看到的是最终答案，不知道实际经历了几次降级，质量下滑无从感知。
  - 输出安全检测仅覆盖格式和基础内容，缺乏对 LLM 生成内容的深度安全审核（如有害建议、歧视性表述）。
  - 验证规则硬编码在代码中，不同业务场景无法定制验证策略。

  ### 第10层：响应输出层

  实现：
  - [AgentResult](file:///f:/project/meetingmind-agent/backend/app/agents/state.py) 统一响应结构：
    - 核心字段：answer、minutes、todos、controversies。
    - 元信息：workflow_type、route_reason、route_decision、citations。
    - 质量信息：retrieval_confidence、risk_level、reflection。
    - 状态信息：requires_confirmation、confirmation_status。
  - [validate_and_format_result](file:///f:/project/meetingmind-agent/backend/app/agents/nodes.py) 格式化输出。
  - API 响应：[/query](file:///f:/project/meetingmind-agent/backend/app/api/v1/endpoints/agents.py) 返回完整 AgentResult + route_decision 结构化路由信息。
  - [/query-stream](file:///f:/project/meetingmind-agent/backend/app/api/v1/endpoints/agents.py) SSE 流式响应，支持实时 CoT 思路推送。

  优点：
  - 响应结构标准化，包含完整元信息和质量指标。
  - route_decision 结构化输出，前端可展示路由决策链路。
  - 流式响应支持实时反馈，用户体验好。
  - 响应含 `citations`（引用溯源），每个产物可追溯到原始文档位置。
  - CoT 思路（[CoTThought](file:///f:/project/meetingmind-agent/backend/app/agents/state.py)）记录每步推理过程，支持前端展示 Agent 的思考链。
  - 支持 `batch_query` 批量查询，一次请求处理多个独立问题。

  缺点：
  - 响应中不包含执行降级信息（用户不知道答案是否经历了降级）。
  - 流式响应的 CoT 思路推送格式未标准化，前端需要硬编码解析。
  - 响应体较大时（含完整 citations + thoughts + route_decision），序列化开销显著。

## 第二部分：7 层横向支撑体系

> 以下 7 个层次独立于 10 层核心架构，作为横向支撑体系贯穿整个系统。

  ---

  ### 横向层1：可观测性层

  实现：
  - [AgentTraceContext](file:///f:/project/meetingmind-agent/backend/app/agents/trace_integration.py) 链路追踪：每个节点执行时生成 trace_id，记录输入/输出/耗时。
  - [app_logger](file:///f:/project/meetingmind-agent/backend/app/core/logger.py) 结构化日志：统一日志格式，支持 DEBUG/INFO/WARNING/ERROR 级别。
  - [monitor](file:///f:/project/meetingmind-agent/backend/app/agents/monitor.py) 运行时监控：Agent 执行状态、节点耗时统计。
  - [performance_metrics](file:///f:/project/meetingmind-agent/backend/app/services/performance_metrics.py) 性能指标收集。
  - [observability](file:///f:/project/meetingmind-agent/backend/app/core/observability.py) 可观测性集成模块。
  - CoT 思路（[CoTThought](file:///f:/project/meetingmind-agent/backend/app/agents/state.py)）记录每步推理过程。

  优点：
  - 链路追踪覆盖所有节点，可追踪完整执行路径。
  - CoT 思路记录详细，便于调试和用户理解。
  - 性能指标收集与业务逻辑解耦。

  缺点：
  - 缺乏可视化仪表板（如 Grafana 集成），指标只能看日志。
  - 追踪数据未持久化到外部系统（如 Jaeger/Zipkin），服务重启后丢失。
  - 无分布式追踪能力，多服务部署时链路断裂。

  ---

  ### 横向层2：成本管理层

  实现：
  - [cost_manager](file:///f:/project/meetingmind-agent/backend/app/services/cost_manager.py) Token 计算与成本跟踪。
  - [llm_service](file:///f:/project/meetingmind-agent/backend/app/services/llm_service.py) LLM 调用成本记录。
  - [PlanBudgetGuard](file:///f:/project/meetingmind-agent/backend/app/services/plan_budget_guard.py) 规划阶段 Token 预算控制。
  - config.py 中 LLM_MAX_TOKENS、EVAL_LLM_MAX_TOKENS 等配置项。
  - LLM 缓存（[cache](file:///f:/project/meetingmind-agent/backend/app/core/cache.py)）减少重复调用成本。

  优点：
  - Token 预算保护从源头控制规划输出大小。
  - LLM 缓存减少重复调用的成本。
  - 评估模型与生成模型分离配置（EVAL_LLM_MAX_TOKENS 独立）。
  - [cost_manager](file:///f:/project/meetingmind-agent/backend/app/services/cost_manager.py) 按请求追踪 token 消耗，支持成本统计。
  - 多模型支持：生成模型 + 评估模型 + 语义风险模型可独立配置，成本与质量灵活权衡。

  缺点：
  - 缺乏实时成本仪表板和告警机制。
  - 成本统计未按用户/会话维度聚合，无法做按用户计费。
  - 外部服务调用（如向量数据库、Neo4j）的成本未纳入管理。

  ---

  ### 横向层3：容错韧性层

  实现：
  - [fault_tolerance](file:///f:/project/meetingmind-agent/backend/app/core/fault_tolerance.py) 容错处理框架。
  - [exceptions](file:///f:/project/meetingmind-agent/backend/app/core/exceptions.py) 统一异常处理。
  - nodes.py 中的多级降级链：
    - IntentRouter 异常 → 降级到 ComplexityClassifier。
    - QualityGate 异常 → 降级到原 replan + reflection 串联。
    - DeterministicErrorChecker 异常 → 降级到 LLM 评估。
    - ParallelExecutor 单任务失败 → 错误隔离，继续其他任务。
  - LLM 调用重试机制（max_retries 配置）。
  - [RiskRuleService](file:///f:/project/meetingmind-agent/backend/app/services/risk_rule_service.py) 规则检测异常 → 降级到硬编码规则。

  优点：
  - 每个新增模块都有降级路径，单点故障不会中断主流程。
  - 异常处理统一，通过 _sanitize_state 保证状态一致性。
  - 并行执行的错误隔离机制完善。
  - [fault_tolerance](file:///f:/project/meetingmind-agent/backend/app/core/fault_tolerance.py) 提供统一重试框架，支持自定义重试策略和退避策略。
  - 所有降级路径都有 WARNING 日志记录，便于事后排查。

  缺点：
  - 缺乏熔断器（Circuit Breaker）：LLM 服务持续故障时会反复重试，浪费资源。
  - 降级路径缺乏可观测性：用户和运维不知道触发了哪条降级链。
  - 超时配置分散在各模块中，缺乏统一的超时治理。

  ### 横向层4：异步管道层

  实现：
  - [graph.py](file:///f:/project/meetingmind-agent/backend/app/agents/graph.py) LangGraph 异步图执行（ainvoke）。
  - [/query-stream](file:///f:/project/meetingmind-agent/backend/app/api/v1/endpoints/agents.py) SSE 流式响应。
  - [ParallelExecutor](file:///f:/project/meetingmind-agent/backend/app/services/parallel_executor.py) asyncio.gather 并行执行。
  - [ReflectionMemoryService](file:///f:/project/meetingmind-agent/backend/app/services/reflection_memory_service.py) asyncio.create_task 异步写入。
  - [long_term_memory](file:///f:/project/meetingmind-agent/backend/app/services/long_term_memory.py) 异步记忆注入。
  - Checkpointer 基于 Redis 的异步状态持久化。

  优点：
  - 全链路异步（async/await），无阻塞 I/O。
  - 流式响应支持实时反馈，用户无需等待完整执行。
  - 反思记忆异步写入不影响响应延迟。

  缺点：
  - 异步任务的持久化机制不足：服务重启时未完成的 asyncio.create_task 会丢失。
  - 缺乏消息队列（如 Celery/RabbitMQ），长任务无法离线执行。
  - 流式响应不支持断线重连，网络抖动时用户需重新发起请求。

  优点：
