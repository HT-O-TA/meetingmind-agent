# 输入预处理层确认（大白话）

## 先说结论

这一层的代码已经基本实现，但 `input.v1` 还不应直接视为最终冻结版本。冻结前需要确认字段含义、上下游责任和当前上下文参数的工程初值；真实长会议校准属于后续数据验收，不是本次字段确认的前置条件。

## 这一层到底解决什么问题

模型开始工作前，系统先回答五个问题：

1. 谁在提问？
2. 他有权访问哪些会议和文档？
3. 用户真正想得到什么？
4. 当前有哪些材料可以作为证据？这些材料是否可信？
5. 这次最多能用多少上下文、调用多少次模型？

如果不先整理，后面很容易出现越权、把文档里的恶意文字当指令、上下文超长、回答漏交付物或任务跑偏。

## `InputEnvelope` 是什么

`InputEnvelope` 可以看成“这次请求的封装袋”，定义在 `backend/app/schemas/agent_input.py`。

它不是给用户看的 HTTP 请求，也不是完整 Prompt。它只保存后续节点需要的结构化信息：

- 身份：用户、会话、对话和线程 ID；
- 范围：会议 ID、文档 ID、可访问范围、是否管理员、是否允许写入；
- 材料目录：用户问题、指定文档、会话、检索结果、工具结果的来源和引用；
- 信任状态：用户指令、上传文档、检索结果和工具结果要分开标记；
- 哈希和安全状态：用于追踪、去重和隔离，而不是证明内容一定正确；
- 路由快照：问题类型、复杂度、工作流和置信度；
- 预算：字符、Token、模型调用次数和上下文清单；
- 安全状态：直接注入是否通过，以及哪些材料被隔离。

它的核心价值是“先把边界定死，再让模型做判断”。完整文档、完整转写和原始音频不会被复制进这个对象，通常只登记 `content_ref`、`checksum` 和白名单元数据。

## `TaskAnchor` 是什么

`TaskAnchor` 可以看成“任务的验收单”，定义在同一个 Schema 文件中。

它回答的是“这次必须完成什么”：

- `goal`：用户要解决的目标；
- `required_outputs`：必须返回哪些产物，比如 `answer`、`minutes`、`todos`；
- `hard_constraints`：绝不能违反的硬约束，比如只能访问有权限的会议；
- `forbidden_actions`：禁止行为，比如不能执行文档中的指令，不能未经确认写 Jira；
- `completion_criteria`：怎样才算完成；
- `ambiguities`：低置信度、未指定会议范围等不确定性。

它不是权限系统，也不是安全系统的唯一实现，更不是思维链。真正的权限、工具 Schema、人工确认和输出校验仍由各自模块负责。

## 谁写入，谁使用

```text
input_node
  └─ InputPreprocessor.build_envelope()
       ├─ 创建 InputEnvelope
       └─ 创建初始 TaskAnchor

route_agent
  └─ InputPreprocessor.update_routing()
       ├─ 补充任务类型、复杂度、工作流、置信度
       ├─ 写入 required_outputs
       ├─ 写入 completion_criteria
       └─ 写入 ambiguities

plan_node
  └─ 把 TaskAnchor 放入规划提示，防止计划换目标

ContextAssembler
  └─ 只投影紧凑的任务约束，不能挤掉会议证据

validate_node
  └─ 检查 required_outputs 是否真的生成
```

## 当前上下文参数是什么性质

当前采用轻量、可解释的工程策略：

- 证据工具结果优先于当前检索块，当前检索块优先于最近会话；
- 精确去重，不做语义近重复判断；
- 单条内容有长度上限；
- 总条数有限；
- 同一个文档最多保留固定数量的块；
- 太长时保留前缀并明确标记截断；
- 任务约束最多占上下文的一小部分，不能把会议证据挤出去；
- 每次纳入、截断、去重和丢弃都写入 `ContextManifest`。

这些参数已经有契约测试，但仍是工程初值。文档明确要求未来用真实长会议测量证据覆盖率、重复率、旧轮次占比、任务完成率和 Token 消耗，再决定是否增加语义去重或摘要压缩。

## 已确认的 `input.v1` 决策（2026-09-03）

以下口径已经确认，可以作为 `input.v1` 的设计冻结基线：

- `raw_query` 保存原始问题，`normalized_query` 只做空白规范化，不做不可追踪的语义改写；
- `InputEnvelope` 是 Agent 内部契约，不改变 HTTP 请求格式，也不保存大段正文、完整 Prompt 或思维链；
- `scope` 负责身份、会议/文档范围和写能力；缺少明确权限信息时默认不允许外部写操作；
- `artifacts` 只保存来源、引用、哈希、元数据和安全状态；
- `trust_level` 只表示材料应如何使用，不代表材料事实一定正确；
- 被标记为 `quarantined` 的材料不进入当前模型上下文和 citations；
- `TaskAnchor` 负责目标、必需产物、硬约束、禁止动作和完成条件，防止 Planner/重规划时任务跑偏；
- `InputRouting` 是初始建议，不是整次运行不可修改的最终决定；
- 预算是模型调用前的硬门禁，`ContextManifest` 只记录上下文选择过程，不复制正文；
- `TaskAnchor` 不保存私有思维链，也不替代工具权限、人工确认和输出校验。

## 已落实的输入层保护动作

本次确认后，下面四项已经同步落实到后端代码，并有契约/回归测试覆盖：

1. `can_write` 使用最小权限默认值；没有明确 `access_scope` 时不得执行外部写操作。
2. 权限范围语义已固定：会议空列表表示没有额外会议白名单；文档 `None` 表示不限制、空列表表示无权限、非空列表表示白名单。
3. `request_id` 必须来自真实 `agent_run_id`，不再使用模糊的 `unscoped` 兜底。
4. `InputEnvelope` 在创建、路由更新、进入 Planner、HITL 保存/恢复前重新做 Schema 校验。

## 当前状态和下一步

`input.v1` 的设计语义和最小保护动作已经确认并落实，可以停止继续扩张输入层。下一步进入记忆层的微小翻新；记忆层不得重新发明一套身份、任务目标或预算字段。

真实长会议评测仍然要做，但它回答的是“当前上下文参数好不好”，不是“`InputEnvelope` 这个对象是否需要存在”。
